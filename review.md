## Findings

1. **BLOCKING: the reload is unconditional, so it can throw away a bid or form input.** `apps/web/src/lib/csp/chunk-load-recovery-snippet.client.ts:21`. The snippet calls `window.location.reload()` as soon as any `/_next/static/` script or stylesheet fails and its HEAD returns 404/410. That includes background loads the person did not start: idle preloads, `next/dynamic` components that mount on a timer, and `<Link>` prefetches whose flight payload preloads client chunks. It never checks whether the page has unsaved input, an open dialog, or a request in flight.
   - Bid panel: once the bid dialog's own chunk has loaded, an unrelated chunk failing while the dialog is open still reloads the page (`apps/web/src/components/lot-page/bid/bid-dialog.lazy.tsx`, `bid-dialog.tsx`). The typed maximum is lost. If it happens during `controller.submitting`, the person never sees whether the bid went through, and may bid again after the reload. The bid dialog has no `beforeunload` guard, so the browser does not ask before leaving.
   - Forms: only the admin form wizard (`apps/web/src/components/admin/admin-form-wizard/index.tsx:258-263`, saves a draft on `beforeunload`), the submission wizard and the source-of-funds page listen for `beforeunload`. Every other form on the site loses its input silently.
   - Next 15 already does a hard (MPA) navigation when the build id changes on a client navigation (`node_modules/next/dist/client/components/router-reducer/fetch-server-response.js:140`, `getAppBuildId() !== response.b`). What remains are failed lazy chunks on the current page. The PR's own model (`socket-chunk-recovery.client.ts`) reloads only after repeated failures of the one surface that is already dead.
   - Suggested fix: when the build files are gone, mark the page as stale instead of reloading at once. Then do one of these: reload the next time `visibilitychange` reports hidden; turn the next same-origin link click or navigation into a full navigation; or reload only when no editable element has focus, no `[role=dialog]` is open, and nothing is submitting, and otherwise show a small "Reload to update" notice. Add tests for "dialog open or input focused → no reload" and "hidden → reload".

2. **Non-blocking: the comment's claim about Next is wrong.** `apps/web/src/lib/csp/chunk-load-recovery-snippet.client.ts:9`. It says "Next's own recovery covers only the live socket surface". The socket recovery is this repo's own code (`apps/web/src/lib/socket-chunk-recovery.client.ts`). Next itself recovers navigations by build id, as described in finding 1. Rewrite the comment to say this snippet covers the lazy chunks on the current page.

3. **Non-blocking: the reload is bounded and cannot loop, including across a second deploy.** `chunk-load-recovery-snippet.client.ts:21` with `socket-chunk-recovery.client.ts:17-18`. One `sessionStorage` key is shared with the socket recovery, so there is at most one reload per tab every 10 minutes from either path, and the two never both reload. If storage cannot be read, the claim fails and nothing reloads. If a second deploy lands within 10 minutes of a reload, the page stays broken: there is no auto-reload, and the only way out is a surface's own notice (bid boundary "Reload", the socket's paused notice). That is acceptable, but should be documented. Because the key is now site-wide, its name `lax:live-socket-chunk-reload-at` is misleading; consider renaming it, keeping the old key as a fallback for one release.

4. **Non-blocking: it only reacts to genuine chunk failures, as asked.** Only a SCRIPT or LINK error whose URL contains `/_next/static/`, or a rejection named `ChunkLoadError` or whose message matches webpack's `Loading (CSS )?chunk … failed` or "dynamically imported module", triggers a HEAD. It reloads only on 404/410, never while offline, and not when the HEAD itself fails. Third-party scripts and images are ignored (tested). Two gaps:
   - A LINK error also fires for `rel=preload`/`prefetch` hints. That is harmless on its own, but feeds finding 1.
   - The `busy` flag drops further failures while one HEAD is pending, which is fine.

5. **Non-blocking: no visible change, and the route budgets are fine.** The snippet is a hashed inline head script (middleware hashes `INLINE_HEAD_SCRIPTS` at `apps/web/src/middleware.ts:40`, and the test asserts it is included). It adds about 1.3 KB to every HTML response and no route JavaScript. CI "Route JavaScript budgets" (build job) reports every group `ok`. Tracked routes are under their ratchets: Home 402.0/407.3, Sales list 454.5/455.0, Sale page 485.3/507.5, Lot page 481.3/486.8, About 352.1/356.6, Terms 349.0/353.5 KB.

6. **Non-blocking: it fits how App Platform serves `_next/static`.** No `deploymentId` or `generateBuildId` is set in `apps/web/next.config.*`, so each build gets its own id and Next's build-id hard navigation works. `deploymentId` would not help here. It only appends `?dpl=` and sends `x-deployment-id`, and Next's self-hosting guidance pairs it with keeping old assets, which App Platform does not do: old chunks are gone after a deploy. Detecting 404/410 with a HEAD is the right signal for that host, and the `indexOf("/_next/static/")` match would still work if `?dpl=` were added later. One thing to verify on staging: the edge/CDN in front of the app must not answer HEAD for a missing chunk with a cached 200 or an HTML fallback page.

7. **Non-blocking: possible race with Next's own hard navigation.** During a client navigation across a deploy, the flight decoder may preload chunks before Next's build-id check sends the browser to the target URL. If that preload 404s, the snippet's async HEAD could reload the current page and interrupt the navigation. This has not been reproduced. Making the snippet skip a reload while a navigation is pending would fall out of the deferral in finding 1.
