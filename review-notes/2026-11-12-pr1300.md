# Review: PR #1300, `books1-accounting-domain` (packages/accounting-domain)

- Date: 2026-11-12
- Commit reviewed: `493300f5` ("Add accounting-domain package: document model, ports, life cycle and money rules")
- Scope: money and design review against the approved Xero → Zoho Books plan
- Reviewer: independent; the PR branch was not changed

## Verdict: FIX FIRST

The package is tidy. It is pure, small, split per document kind, and every check passes. Four
approved rules are still not enforced by the code, though, and two of them are the
"never create twice" and "totals must match exactly" guarantees that the whole plan depends on.
These should be fixed before any adapter or runtime is built on top of the package, because each
fix changes a public type (`Line`, `DocumentRecord`, `IssueOutcome`/`LookupOutcome`, `laxReference`).

| # | Severity | Area | Short |
| --- | --- | --- | --- |
| H1 | High | References | Product missing from the LAX reference and the lookup, so Shop and lax.art collide inside one Books org |
| H2 | High | Totals | The provider-totals check is not wired: ports return no totals, and `issued`/`found` go straight to `issued` |
| H3 | High | Money | `buildInvoice`/`buildCreditNote`/`buildBill` accept any hand-made `Line` (negative net, VAT on margin scheme) and any reference |

## High

### H1. The LAX reference and the lookup do not carry the product or entity, so references collide across products

- `src/document.ts:39-47` (`laxReference(kind, sourceId)` → `LAX-${prefix}-${sourceId}`)
- `src/ports.ts:47` (`findByReference(kind, reference)`: no product or entity)

**Scenario.** Shop order `123` and lax.art order `123` are separate rows in separate tables or
databases. Both produce `LAX-INV-123`. The probe confirmed this:
`laxReference("invoice","123")` gives the same `LAX-INV-123` for both. Both products trade as
**London Art Exchange Ltd**, so both invoices go into the same Books organisation. Suppose the
lax.art send times out and lands in `unknown`. `findByReference("invoice","LAX-INV-123")` then
returns the **Shop** invoice as `found`, and `applyLookup` marks the lax.art record `issued` with
the Shop invoice's number and id. The lax.art invoice is never created and the customer's money has
no document. Even without a timeout, the "duplicate guard" will refuse or merge two different sales.
Bid ids do not collide within an org today only because Bid is the only product on its entity.
That is an accident of the current entity map, not a rule.

**Fix.** Put the product in the reference, e.g. `LAX-SHOP-INV-123` / `LAX-ART-INV-123` /
`LAX-BID-INV-123`. Make `laxReference(product, kind, sourceId)` the only way to make one. Pass the
entity (or product) to `findByReference` so an adapter can never search the wrong org. Add a test
that references are injective over `(product, kind, sourceId)`, plus a property test over random
triples. Prefix distinctness across kinds is already fine: INV/PAY/CN/BILL/CON never collide.

### H2. "Totals must match the provider exactly, mismatch → needs_review" cannot be enforced

- `src/ports.ts:14-23` (`IssueOutcome` "issued" and `LookupOutcome` "found" carry no totals)
- `src/lifecycle.ts:127-134` (`completeSending` issued → `issued`)
- `src/lifecycle.ts:150-157` (`applyLookup` found → `issued`)
- `src/lifecycle.ts:172-180` (`escalate` refuses from `issued`)
- `src/money.ts:104-111` (`compareWithProviderTotals` exists but nothing calls it)

**Scenario.** Zoho Books rounds tax at invoice level (an org setting) or treats a price as
tax-inclusive. It returns gross £120.01 where we computed £120.00. The adapter returns
`{status:"issued", number, providerId, pdfRef}`, and the record becomes `issued` (final). The
domain never saw the provider's totals, so the mismatch is lost. Moving to `needs_review` afterwards
is also impossible: the probe confirmed `escalate(issuedRecord)` gives `bad_state`. The same happens
when a lookup after `unknown` finds a document with different amounts, e.g. the H1 collision.

**Fix.** Add `totals: Totals` to the `issued` and `found` outcomes. `completeSending` and
`applyLookup` should take our `Totals` (or the document) and call `compareWithProviderTotals`. A
mismatch goes to `needs_review` with the field and difference recorded, and the provider identity
is kept, because the document exists and must not be resent. Add tests for a one-penny mismatch on
both paths, and a test that a mismatch record can never reach `startSending`.

### H3. Builders trust any `Line` and any reference, so the money rules can be bypassed

- `src/money.ts:41-47` (`Line` is a plain interface)
- `src/document.ts:139-160`, `162-182`, `184-205` (`buildInvoice`/`buildCreditNote`/`buildBill` take `readonly Line[]` unchecked)
- `src/document.ts:56` (`"bad_reference"` is declared and never used)
- `src/document.ts:117-120` (`Common.reference` is a free string)

**Scenario (probe output, abridged).**
```
buildInvoice({ product:"shop", reference:"LAX-PAY-1", contactReference:"",
  issuedOn:"2026-02-30", dueOn:"2026-13-45",
  lines:[{ description:"x", quantity:1, unitNetPence:-500, treatment:"margin_scheme", vatPence:999 }] })
→ ok: totals { netPence:-500, vatPence:999, grossPence:499 }
```
This shows a negative net, £9.99 of VAT on a margin-scheme line, a *payment* reference on an
invoice, an empty contact reference and impossible dates, all accepted. The literal type-checks
with no cast. Any caller that builds lines by hand, or rehydrates them from a database row,
skips `buildLine`.

**Fix.** Make `Line` impossible to forge. Either brand it (`Line & { readonly [lineBrand]: true }`
with only `buildLine` producing it), or have the document builders take `LineInput[]` and call
`buildLine` themselves. Validate `reference === laxReference(product, kind, sourceId)`. Taking
`sourceId` as input instead of `reference` is simpler. Validate `contactReference` (`LAX-…-CON-…`),
`invoiceReference` on credit notes and allocations (`…-INV-…`), and use `bad_reference`. Add tests
for every refusal.

### H4. `unknown` → immediate lookup → `not_found` → resend can create twice

- `src/lifecycle.ts:101-103` (`toUnknown` drops the lease)
- `src/lifecycle.ts:121-122` (an `unknown` outcome before expiry)
- `src/lifecycle.ts:142-169` (`applyLookup` has no `nowMs`)
- `src/lifecycle.ts:158-159` (`not_found` clears the duty)

**Scenario.** The HTTP client times out after 30 s, but Zoho is still processing the POST.
`completeSending(…, {status:"unknown"})` runs while the lease is still live. The runtime looks up
at once, the provider has not committed yet, and the lookup says `not_found`. `lookupRequired`
becomes false, `startSending` succeeds, and the second POST creates a second invoice. Then the first
POST commits too. Zoho does not enforce uniqueness of `reference_number`, so nothing stops it. The
approved rule is "lookup before retry", but a lookup is only meaningful once the first request can
no longer land. The domain throws away the one fact (the lease expiry) that would let it enforce
that.

**Fix.** Keep `lease.expiresAtMs` (or a `settlesAtMs = expiresAtMs + grace`) on the `unknown`
record. `applyLookup(record, outcome, nowMs)` accepts `not_found` only when
`nowMs >= settlesAtMs`; earlier it returns a refusal such as `lookup_too_early`. The runtime's HTTP
timeout must be shorter than the lease, and the README should say so. Add a test for "timeout
inside the lease → lookup not_found → refused until settled". Ideally also add a stateful
property test: random action sequences never produce two `sending` attempts without a settled
`not_found` between them.

## Medium

### M1. Non-finite lease expiry is accepted and never expires
`src/lifecycle.ts:72`. `lease.expiresAtMs <= nowMs` is false for `NaN`, so the probe got
`startSending(r, {token:"t", expiresAtMs:NaN}, 1000)` → ok. Then `expireLease(…, 1e15)` →
`lease_held` forever, and a late `issued` answer at `1e15` was **trusted** (→ `issued`). `Infinity`
is accepted too. A record stuck in `sending` is never looked up, and the "late answer is not
trusted" rule silently turns off.
**Fix.** Require `Number.isSafeInteger(lease.expiresAtMs)` and `Number.isSafeInteger(nowMs)` in
every life-cycle function. Optionally cap the lease length. Test NaN, Infinity, and fractional
values.

### M2. `DocumentRecord` can represent illegal states
`src/lifecycle.ts:22-32`. `status`, `lease`, `issued`, `failureReason` and `lookupRequired` are
independent fields. The probe ran `{...newRecord(), status:"unknown", lookupRequired:false}`, and
`startSending` gave ok, i.e. a resend with no lookup. That record is exactly what a database row
with a defaulted `lookup_required = false` column produces. `issued` with `issued: null`, `sending`
with `lease: null`, and `pending` with `lookupRequired: true` (which then gets stuck) are all
representable. The never-create-twice guarantee rests on a boolean the storage layer must persist
perfectly. `unknown` also means two things: "may exist" and "looked up, absent".
**Fix.** Use a discriminated union on `status`:
`{status:"sending", lease}`, `{status:"issued", issued}`,
`{status:"unknown", settlesAtMs}` (lookup always owed),
`{status:"absent_confirmed"}` (or reuse `pending` after `not_found`),
`{status:"needs_review", lookupOwed, reason}`, …
Then add `parseRecord(row): Result<DocumentRecord>` for rehydration, so a stored row can only come
back in a legal state.

### M3. Zero amounts are accepted
Probe: a zero-total invoice → ok. `planRefund(…, {0,0})` → ok. `splitRefundTotal(…, 0)` → ok
(`src/refund.ts:73`). `allocatePayment(0, [])` → ok (`src/allocation.ts:32`, where an existing test
even asserts it). `buildPayment` correctly refuses 0, so the rules are inconsistent. The brief asks
for zero and negative amounts to be rejected.
**Fix.** Refuse a document whose `grossPence === 0` (`zero_total`). Zero-priced *lines* such as
free delivery can stay. Refuse a refund of 0 total, and a payment of 0 in `allocatePayment`. Update
the "zero payment allocates nothing" test.

### M4. Dates are checked only by regex
`src/document.ts:58,126-130` and `src/allocation.ts:22`. Probe: `issuedOn:"2026-02-30"`,
`dueOn:"2026-13-45"` → ok. Zoho rejects them, and the record lands in `failed`, which looks like a
provider problem. Worse, a bad `dueOn` breaks oldest-first ordering in `allocatePayment`.
**Fix.** Add a pure calendar check (month 1–12, day ≤ days-in-month with leap years) shared by both
files. Test 02-29 in leap and non-leap years.

### M5. Credit notes are not bounded
`src/document.ts:162-182`. A credit note needs only one line and an `invoiceReference` string. Nothing
ties it to the original invoice's totals or treatments, or to `refund.ts` (goods/delivery,
never exceeding what was paid). The rule "refunds never exceed paid" is enforced in `planRefund`
but not on the document that actually reaches Books.
**Fix.** Add a `buildCreditNoteFor(invoice, refundSplit, …)` that derives lines from the original
invoice's goods/delivery lines. It should keep each line's VAT treatment, so a margin-scheme sale
is credited as margin scheme and a standard-rated delivery as standard. It should refuse totals
above the invoice gross minus earlier credits. Add tests.

### M6. Switch validation can skip products and throws on a missing one
`src/source-switch.ts:43-55`. Probe: `validateSwitchConfig({…, shop:{xero:"live",books:"live"}}, ["bid"])`
→ ok, so Shop's two live sources go unchecked. A config missing a product throws `TypeError`
instead of a refusal.
**Fix.** Drop the `products` parameter and iterate `PRODUCTS`. Refuse a missing product
(`missing_product`). Ideally have one `parseSwitchConfig(unknown)` that returns a `SwitchConfig`
only when valid.

### M7. Legal-entity names are copied from `@auction/branding` with no drift guard
`src/document.ts:11-23`. `@auction/branding/src/legal-entity.ts` already exports `legalEntityFor`
and registered names (ids `london-auction-xchange` with hyphens; here `london_auction_xchange` with
underscores). The new package is not in `LEGAL_NAME_ROOTS` (`scripts/check-legal-names.mjs:14`), and
unlike `packages/identity-contracts` it has no drift test. The names are correct today; the risk is
silent drift on a document that goes to HMRC-facing books.
**Fix.** Do what identity does. Add the file to the lint as an allowed mirror, and add a test
somewhere that may import both packages (e.g. the future runtime or an app test) asserting
`LEGAL_ENTITY_NAMES` equals the branding names, and that `legalEntityFor` agrees for every product.

### M8. Corrupt refund buckets are tolerated
`src/refund.ts:23-25`. `refundable` clamps `paid - refunded` at 0. Probe: `refundedGoodsPence:500`
against `paidGoodsPence:100` → ok. An over-refund that already happened is a finding, not
something to hide.
**Fix.** Refuse `refunded > paid` per bucket (`bad_amount` / `already_over_refunded`).

## Low

- **L1. Locale-dependent ordering.** `src/allocation.ts:48-50` and `src/document.ts:241-243` use
  `localeCompare`. The result depends on the runtime ICU locale. The probe got
  `["a_b","a-b","A-b","B"]`, while code-unit order is `["A-b","B","a-b","a_b"]`. Tie order in
  allocation is part of the money outcome. **Fix:** `a < b ? -1 : a > b ? 1 : 0`.
- **L2. README claims.** `README.md:19` says every function that can say no returns `Result`, but
  `vatForLine` (`src/money.ts:34-35`) and `liveSourceOf` (`src/source-switch.ts:19-23`) throw.
  Either return `Result` or correct the README. The life-cycle diagram and the
  "totals … reported" sentence will also need updating after H2/H4.
- **L3. Test strength.** The half-up property (`src/money.test.ts:42-51`) only checks ties when
  a random case happens to land on one, which is rare. Add a generator that builds ties on
  purpose (`net * bps ≡ 5000 mod 10000`). There is no stateful property test for the life cycle,
  and none for reference injectivity, which would have caught H1. Those two are the most valuable
  properties to add.
- **L4. Margin scheme data.** Returning 0 VAT for `margin_scheme` lines is right for the customer
  document. The model, however, carries no purchase price or margin, so the margin VAT owed on the
  VAT return cannot be derived anywhere downstream. `vatForLine`'s `rateBps` parameter is never
  used by `buildLine`, and `Line` stores no rate, so a reduced-rate line cannot be represented.
  Confirm with the owner that both are deliberately out of scope for this phase.
- **L5. Case-folding.** `sourceId` allows both cases (`src/document.ts:33`). If the provider's
  reference search is case-insensitive, `abc`/`ABC` collide. Normalise to one case or reject mixed
  case. Also confirm the provider's reference-field length limit against the longest reference
  (with the H1 product prefix, about 78 characters).
- **L6. Large amounts.** `netPence * rateBps` (`src/money.ts:38`) leaves the safe-integer range
  above about £45bn net. Cap line amounts well below that (e.g. 10^11 pence) and refuse above.
- **L7. Purity guard.** The new `lint:layers` rule (`scripts/check-layers.mjs`, added block) blocks
  imports only. Nothing stops a later `Date.now()`, `Math.random()` or `fetch` in `src/`. Add a
  small banned-globals check for this package. It is clean today.
- **L8. Cut-over routing.** The switch is per product, but credit notes and payments for an invoice
  issued in Xero must go to Xero even after Books is live for that product. The domain has no
  per-document "source of record". Plan it before the runtime PR, otherwise a credit note can land
  in Books against an invoice that only exists in Xero.

## Design notes (what is good)

- ISP is respected: one port per document kind plus `DocumentLookupPort`, and outcomes are
  provider-agnostic.
- `Result`/`refuse` with typed codes is consistent and easy for the runtime to branch on.
- Integer pence throughout. VAT is per line, totals are the exact sum, and there is no
  document-level rounding or adjustment line.
- The lease is plain data and the clock is the caller's. A late answer after expiry is distrusted
  (once M1 is fixed).
- Every illegal transition I tried through the public API is refused: start/complete/expire/
  lookup/escalate/requeue/cancel from each wrong state, a wrong token, a held lease, and an owed
  lookup. The gaps are records made outside the API (M2) and the missing transitions (H2, H4).
- Allocation is correct: oldest due first, never over an invoice's outstanding amount, never over
  the payment, remainder reported, settled invoices skipped, duplicates refused. The 500-run
  property test is meaningful (it checks conservation, the per-invoice cap and the order).
- The refund split checks each bucket separately, and its property test checks conservation and
  the caps.
- The layer rule is registered, and lint:deps, typecheck and biome are clean.

## Suggested order of work

1. H1 + H3 together (reference made from `(product, kind, sourceId)`, unforgeable `Line`, and
   builders that validate references).
2. H2 + H4 + M1 + M2 together (life-cycle record as a discriminated union, totals in outcomes,
   settle time on `unknown`), with a stateful property test.
3. M3–M8, then the Low items.
