## Checklist

| Area | Result |
|---|---|
| HMAC construction | HMAC-SHA256 over the base64url payload string. Key = HMAC-SHA256(`LAX_ACCOUNT_SESSION_ENCRYPTION_KEY`, `"lax:account-login-pending:v1"`) (`pending-login-cookie.ts:5-8`). The Redis session store uses `sha256(raw)` as its AES-GCM key (`redis-session-store.ts:5-7`), so the two derived keys are different and labelled. The raw secret is never used directly. Config requires the secret to be at least 32 chars (`config.ts:13`). OK |
| Constant-time compare | `timingSafeEqual`, with a length check first so a short signature cannot throw (`pending-login-cookie.ts:34`). OK |
| Encoding | `<b64url(json)>.<b64url(mac)>`. Exactly one `.` is required (`:30`). The MAC covers the encoded body string, so lenient base64 decoding of the body cannot be abused. OK |
| What the MAC covers | The whole pending JSON: state, nonce, PKCE verifier, returnTo and the reauth subject. OK |
| Expiry | Only the cookie's `maxAge: 600`. Nothing server-side (see F1). |
| `__Host-` attributes | Name `__Host-lax-account-login` when the origin is https. `secure: true`, `path: "/"`, no `domain`, `httpOnly`, `sameSite: "lax"` (`login/route.ts:38-48`). Lax is needed because the callback is a top-level cross-site redirect from the issuer. OK. On localhost (http) the name has no prefix, which is fine. |
| Tampered / unsigned / old-format cookie | `openPendingLogin` returns `undefined` and never throws (tested on junk input). The callback treats this as a missing pending login: it restarts sign-in once using the retry cookie, then shows `missing_pending`. The old name `lax-account-login-pending` is never read and is cleared on every exit path (`callback/route.ts:23-27`). Never accepted, no crash. OK |
| Deploy-time fallback | None. A sign-in that is in progress during the deploy restarts once automatically. That is the right choice: accepting the old unsigned cookie would defeat the purpose. The `LAX_ACCOUNT_LOGIN_COOKIE` constant is kept only so it can be cleared (see F3). |
| Secret logging | No logging added in the touched account files. The secret only goes to `createHmac`. OK |
| `Cache-Control` on lax_device responses | The single set site always sets `private, no-store`, which overrides any weaker header (`device-session-hook.ts:110-112`). Responses that are shared-cacheable or have status >= 400 return early without the marker (`:76`). `withAppendedSetCookie` builds a new `Response`, so the headers are mutable and `set` cannot throw on immutable `Response.redirect` headers. OK |
| Normal users | Same flow and attributes. Only the cookie name and value format change. One extra automatic redirect for sign-ins already in progress at deploy. OK |

## Findings (none blocking)

**F1 (Low): the pending-login MAC has no server-side expiry.** `apps/account/src/lib/pending-login-cookie.ts:18-21`.
Scenario: a sealed value captured from the browser (for example from a stolen disk or devtools export) still verifies after its 10-minute `maxAge`, until the session encryption key is rotated. Impact is small. To use it, an attacker would also need an unused authorization code that the issuer minted for that same flow's PKCE challenge, and those codes are single-use and short-lived.
Fix (follow-up): put `iat` (or `exp`) inside the sealed JSON and reject it in `openPendingLogin` when it is older than 600 s.

**F2 (Low / test quality): the two-step setup tests do not exercise the authorize wiring.** `apps/auth/src/services/two-factor-requirement.service.test.ts:22-46` and `password-reset-social-only.integration.test.ts:243-280`.
Scenario: both tests pass the reader's result into `decideAuthorizeTwoFactorStep` themselves. If the authorize endpoint stopped consulting `twoFactorPolicyStore`, or passed `requiredByPolicy: false`, both would still pass. The integration case also skips without `DATABASE_URL`, so it did not run in this review.
Fix (follow-up): add one test that drives `/oauth2/authorize` for the unenrolled org member and asserts the redirect to setup. Make sure CI runs the integration suite with a database.

**F3 (Info): the legacy cookie name has no removal date.** `apps/account/src/lib/session-cookie.ts:1-6`.
After one 600 s window the old cookie cannot exist any more, so the clearing call and the constant can be deleted in a later release. Add a TODO or issue so it does not stay forever.

**F4 (Info): test gaps.** `apps/account/src/app/api/auth/login/route.test.ts:55-62` does not assert `sameSite: "lax"` or `maxAge: 600`. The decoded signature allows harmless malleability (its unused low padding bits can change and it still verifies), and no test covers this. That does not matter for security. Add the two assertions.
