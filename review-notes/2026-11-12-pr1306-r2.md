### D4b. Medium (before any runtime): `dry_run` and `test_org` claims take the live document

- **Where:**
  - `packages/persistence/src/repositories/accounting/drizzle-accounting-document.work-queue.ts:16`: `SENDING_MODES = ["dry_run", "test_org", "live"]`.
  - `:62-78`: the claim filters on that list for the requesting provider only.
  - The contract at `packages/persistence/src/interfaces/accounting.ts:113` says the same.
- **Cause:**
  - There is one row per document, and whichever claim reaches it first consumes it.
  - The domain allows one live source plus another source in any non-live mode (`validateProductSwitch` refuses only two `live`).
  - The claim never asks whether the *other* provider is live for the product.
- **Probe:** run as `worker_app` through `createAccountingRepositories`, then restored.

  | Bid switch | Domain accepts? | `claimNext({provider: "books"})` |
  | --- | --- | --- |
  | Xero `live`, Books `test_org` | yes | took `LAX-BID-INV-…`, `provider=books`, `sending` |
  | Xero `live`, Books `dry_run` | yes | took `LAX-BID-INV-…`, `provider=books`, `sending` |

- **Impact:**
  - The rollout this switch exists for is "run Books in the test org (or dry run) while Xero stays live". With that rollout, a share of the real invoices, credit notes and payments would be sent to the Books test organisation, or only logged. They would become `issued` (or end in the dry-run path) and never reach the live ledger.
  - Revenue and VAT would go missing from the books, and nothing would flag it.
  - The reverse also holds once Books is live and Xero is set to `test_org`.
- **Related: the Bid seed is now claimable.** The test `accounting-persistence.integration.test.ts:211` asserts that "Xero may claim" a Bid document, because the seed is `bid.xero = live`. The legacy `finance-runtime` path already writes Bid documents to Xero. The first runtime that calls `claimNext({provider: "xero"})` would therefore create a second Xero copy of every Bid document. Round 1 noted this as Info; this PR's claim rule makes it a working path.
- **Fix (small):**
  - Hand a pending document only to the product's **live** source: `SENDING_MODES = ["live"]`. Update the interface comment and the "claims in dry_run, test_org and live" test.
  - `dry_run` and `test_org` must never take the live row. Design them in the runtime PR as a shadow that does not change the live document's state, for example a separate shadow queue or a `mode` stamped on its own rows.
  - For Bid:
    - **Option 1:** seed `bid` as `xero = off` for this new pipeline, and document that the legacy path is outside this switch.
    - **Option 2:** add an explicit rule that the new pipeline does not serve `bid` until the legacy writer is retired.
    - Either way, add a test: "Bid on Xero live, Xero claim from the new pipeline gets nothing" (or the documented equivalent).
  - Add a test: "Xero live and Books `test_org` on one product, so a Books claim gets nothing".
- **Why it blocks with M1:** nothing calls `claimNext` yet, so no money moves today. But this PR states the claim contract that the runtime will build on. Changing one constant and two tests now is cheaper than unwinding a runtime built on this rule. If the owner prefers, it may move to the runtime PR, provided the interface comment is corrected here.

### Info

- **The switch is read without a lock.** It is read in the claim statement under READ COMMITTED, with no lock (`worker_app` cannot lock it). A flip that commits during a claim lets that one claim use the old modes. The provider is stamped on the row and lookups use it, so this is safe. It is worth one sentence in the runbook: "after flipping, wait one lease before assuming no old-provider sends".
- **`MAX_LAPSED_PER_CLAIM`.** This is unchanged from round 1: no log line yet.
