## Findings

### F1 — HIGH: a buyer refund that lands while a payout run is in flight is never charged to the seller
- `packages/finance-runtime/src/payout/payout-settlement.ts:121` reads `findUnlinkedCapturedPayments` (incl. `refundedPence`, `packages/persistence/src/repositories/drizzle-payout.repository.ts:462`) under only the per-seller advisory lock. It does not lock the payment rows.
- `packages/finance-runtime/src/payout/payout-adjustment.service.ts:77` / `:161`: every refund path holds the payment row lock (`lockPaymentInTransaction`), but not the settlement lock. It then calls `findSellerClawbackFacts`. That returns `not_paid_out` while the run's sale line is uncommitted, so `sellerRefundCharge` returns `null` and nothing goes on the ledger.
- Before this PR, a refund before payout was always written to the ledger, so this window did not lose money. Now it does.
- **Scenario (reproduced on Postgres 16):** a sale with £1,000 hammer, £250 premium and 15% + VAT, so net £820. The run starts and reads `refundedPence = 0`. A staff part refund of £500 commits: `payment_refund` row added, adjustment sees "not paid out", writes nothing. The run then inserts the £1,000 sale line and no refund line.
  - Result: the seller is paid £820.00 instead of £492.00, so £328.00 is never clawed back.
  - `sumRefundLineCentsForPayment` returns 0 afterwards.
  - Control (the refund committed before the run) correctly gives a `-£328.00` refund line.
- The same window with a **full** refund pays the full net on a sale that is refunded in full.
- If a card `charge.refunded` webhook for the same refund arrives later, it sees `sellerDelta = 500` and charges the £328 then. It also announces `payment.refunded` a second time.
- Refunds with no later webhook (bank transfer, manual, reconcile) stay lost.
- **Fix:** in the run, after `lockSettlementForEntity`, lock the pending payment rows `FOR UPDATE` and read `refundedPence` under that lock (`findUnlinkedCapturedPayments … FOR UPDATE OF payment`, or a dedicated `lockPendingPayments`).
  - Lock order is then advisory → payment for the run and payment only for refunds, so there is no deadlock cycle.
  - An in-flight refund then either commits first, so the run sees it and adds the refund line, or waits until the sale line is visible, so it is charged as "paid from snapshot".
  - Add a regression test that interleaves a refund between the run's read and its insert. A gate in a wrapped `sellerTermsForTx.forRun` does this; it is what I used.

### F2 — LOW: a refund whose seller charge rounds to nothing leaves no line, so a later webhook announces it again
- `payout-adjustment.service.ts:164` returns `null` when `sellerRefundCharge` gives no charge (`due − clawedBack ≤ 0`: penny rounding, or a sale already over-clawed under the old rule). No refund line records `buyer_refund_pence`.
- After payout, `sumRefundLineCentsForPayment` (`drizzle-payout.repository.ts:691`) counts only refund lines. So the next `charge.refunded` for that payment sees the earlier buyer refund as new for the seller (`checkout-refund-handlers.ts:106`) and publishes `payment.refunded` (`:125`) with an `amountCents` that includes it again.
- Money is not double-charged, because the cumulative clawback rule absorbs it. The announcement amounts overstate.
- **Fix:** when the sale is paid out and the charge is zero, still record what was answered (a zero-amount refund line with `buyer_refund_pence`, which the CHECK allows). Or make `sumRefundLineCentsForPayment` take `max(lines answered, …)` per payment.

### F3 — LOW (defence in depth): figure-column UPDATE grant is not limited to held rows
- `packages/db/src/migrate-roles.ts` (`SELLER_TERMS_RECOMPUTE_UPDATE_COLUMNS`) lets `api_app`/`worker_app` rewrite `seller_net_pence`, `commission_pence`, `agreement_id` and `basis` on **any** row, including snapshots already paid.
- The application filters with `WHERE basis = 'held'` (`drizzle-sale-seller-terms.store.ts`), but nothing in the database does.
- A paid snapshot drives later clawbacks (`findSellerClawbackFacts` joins it live) and the payout line split (`saleLinePaymentFacts`). So a bug or a compromised role could change past figures, and the shape CHECK alone cannot catch a consistent rewrite.
- **Fix:** add a `BEFORE UPDATE` trigger on `sale_seller_terms` that raises unless `OLD.basis = 'held'`, or unless it is the owner role. Add a role probe that updating a non-held row fails.

### F4 — MEDIUM (acknowledged in the PR as out of scope; needs a finance decision before PR 4): disputes still price the seller's share from `payment.platform_fee`
- `packages/domain/src/dispute-case.ts:117` uses `amountPence − platformFeePence` (the old rule). The result goes on the ledger as given (`apps/api/src/services/disputes/dispute-line-effects.ts:94`, kind `dispute` bypasses `sellerRefundCharge`).
- For a sale paid from its snapshot, the disputed share no longer matches what the seller received. A lost dispute on the £102,500 example sale charges the seller up to £97,375.00 (old-rule net), not £67,240.00 (snapshot net).
- It also charges before payout, unlike refunds.
- The PR lists this under "Not covered here", so it does not block on its own. Track it explicitly.

### F5 — LOW (transition): part refunds charged under the old rule before this release over-claw sales paid from the snapshot
- Take a sale that was part-refunded before deploy and not yet paid out. Old code already put the full buyer refund on the ledger (e.g. −£500). After deploy the run pays the snapshot net (£820) and adds nothing, because `buyerRefundAnsweredPence` is already 500.
- The seller nets £320, not the rule's £492, and the cumulative rule never gives the difference back.
- No double charge, but the amount is wrong. Finance can size it before deploy with this query: captured payments with refund lines and no sale line.

## Other things verified OK
- **Idempotency of runs:**
  - The advisory lock serialises runs for one seller.
  - `tryInsertSaleLine` uses on-conflict-nothing; a skipped sale line also skips its pre-payout refund line, and the totals are re-added.
  - `repriceHeld` is guarded by `basis = 'held'`; `recordAtPayout` uses on-conflict on `payment_id`.
  - A second run pays nothing (integration test).
- **Idempotency of refunds:**
  - Cumulative `sellerClawbackPence` (half-up, BigInt, exact net at full refund) never charges past the net.
  - `clawedBackPence` is subtracted.
  - Aggregated open-payout lines keep `buyer_refund_pence` cumulative.
  - The payment row lock serialises refunds against each other.
  - The `sumRefundLineCentsForPayment` change correctly stops a card event after a staff refund on an unpaid sale from re-announcing (except F1/F2).
  - `payment_refund_backfill_from_payout_lines` stays safe, because seller-share lines are ≤ the buyer refund.
- **Held, LAX-owned and legacy sales:**
  - Held sales are left out of the run and re-priced each run.
  - `lax_owned` is excluded from pending lists and from the entity list.
  - Legacy payments are priced from stored invoice hammer and premium lines, with the old fee kept for audit; no invoice or hammer line → `legacy_invoice`, never guessed.
- **Negative nets:** blocked by the 0372 shape CHECK and the `negative_net` hold. Payout seller-terms totals are CHECKed ≥ 0.
- **Settlement no longer reads `PlatformFeePolicy` or `payment.platform_fee`**, except as `legacy_platform_fee_pence` for audit. `settlementAmounts()` (float maths) is removed, and the lint guards the files.
- **Migration 0374:** columns are nullable; constraints are only satisfiable on new rows (existing rows are NULL). The FK is `ON DELETE RESTRICT` and the index is partial. `lock_timeout` is set. Forward and rollback are both idempotent.
- **Event schema:** the new `payout.settlement_created` fields are optional, so V1 events still parse.

### Verdict: FIX FIRST
F1 is a regression that loses money: a refund that races a payout run is never clawed back from the seller (£328 in the reproduction; the full net for a full refund). Lock the pending payment rows in the run and add the interleaving test. F2 and F3 are small and worth doing in the same pass. F4 and F5 need finance sign-off rather than code in this PR.

### New findings

**N1 — MEDIUM (rollback only): rolling 0374 back after the release has written refund lines leaves data the previous release misreads**
- **What happens:** the rollback drops `payout_line.buyer_refund_pence` and restores 0344's top-up, which sums `abs(amount)`. Once this release has written refund lines, those amounts are the seller's share or a credit, not the buyer's refund.
- **Reproduced on Postgres 16** (rollback run inside a transaction that was then rolled back), after the F5 true-up state (old -£500 line plus the +£172.00 credit):
  - `payment_refund_backfill_from_payout_lines` inserts a phantom **£172.00** buyer refund top-up row.
  - The refund-line sum the old code reads becomes 67200p.
- **Previous release's own reading of the ledger** (`main`'s `sumRefundLineCentsForPayment` = |Σ amount|):
  - Every new-rule part-refund line (e.g. -£328 for a £500 refund) is read as £328 answered.
  - So the next `charge.refunded` for that payment charges the seller an extra **£172** at the old full rate, and announces `payment.refunded` again.
- **Fix, either:**
  - make `0374_rollback.sql` refuse (`RAISE`) when any `kind = 'refund'` line has a non-null `buyer_refund_pence` that differs from `-amount × 100`; or
  - state in the rollback header and the PR that 0374 is forward-fix-only once such lines exist, with a query to check first.
- This is not on the forward path, but a rollback usually happens soon after deploy, which is exactly when these lines exist.

**N2 — LOW (residual window): a payment that becomes payable after `lockPendingPayments` is read but not locked**
- The lock and the read are separate statements. If a payment's capture commits between them, the run reads it and pays it without holding its row.
- A refund of that payment starting before the sale line is inserted would then hit the original F1 path: not paid out, no charge.
- That needs a capture and a refund within the same run. Very unlikely, but it is cheap to close: add `FOR UPDATE OF payment` to the read itself, or have the run drop payments it did not lock.

**N3 — LOW (transition edge): the run does not top up the buyer's refund record before reading it**
- `refundBeforePayout` returns early when `payment_refund` is empty (`refundedPence <= 0`). Its comment relies on 0344's backfill having copied old refund lines.
- Refund paths re-run the backfill under the payment lock. The run does not, even though it now holds the same lock.
- A pending payment with an old-release refund line and no `payment_refund` row would get no true-up, which is F5's old over-claw, not a double charge.
- Calling `payment_refund_backfill_from_payout_lines(id)` for each locked pending payment (or once for the seller) would close it. Finance can confirm whether any such rows exist before deploy.

**Other things checked, no issue found:**
- Pence rounding: half-up BigInt, exact net at full refund, no float maths in the changed code. The 1p, 2p, 3p and 101p cases match by hand.
- VAT and not-VAT-registered: snapshot maths is unchanged since the first review. The `0beccc78` commission-only test passes.
- Webhook replay: claim by event id, then the cumulative measure against what was answered; covered above.
- `worker_app` grants: the trigger closes F3 for it; it can take the new lock.
- Migration on existing rows: the new function and trigger touch no rows. The forward migration does nothing to existing `sale_seller_terms` rows.

### Findings from the re-check

**N1 (MEDIUM, 0374 rollback misread by the previous release): FIXED**
- The guard in `0374_rollback.sql` is a `DO` block placed after `BEGIN` and before the first `DROP`. It counts `kind = 'refund'` lines where `buyer_refund_pence IS NOT NULL AND buyer_refund_pence <> -amount * 100`, and raises if there are any. Because the whole file is one transaction, the refusal changes nothing.
- It counts every line kind the release writes that the previous release would misread:
  - a share line (-£328 / 50000);
  - the £0.00 line from F2 (0 / 1);
  - the true-up credit (+£172 / 0).
- It lets through every line the previous release reads correctly: `buyer_refund_pence` null, and a full charge, where -£50 / 5000 matches.
- The `CHECK` on the column keeps `buyer_refund_pence` at 0 or above, so a negative value cannot slip past the comparison.
- The integration test (real DB, built by the full migration run) shows:
  - the rollback refuses with "2 refund line(s)…";
  - the column is still there afterwards, and the 0374 top-up records £650, not a phantom £172;
  - once the new-rule lines are deleted, the rollback succeeds, and running it again also succeeds;
  - the rollback succeeds on an empty database.
- **Regression check:** with the `RAISE` replaced by `NULL`, the refusal test fails (1 failed, 4 passed).

**N2 (LOW, payment payable after the lock): FIXED**
- `lockPendingPayments` and `findUnlinkedCapturedPayments` both filter on the same `awaitingSettlement()` and seller. So the run's read (READ COMMITTED, a newer snapshot) can only add payments that became payable after the lock. Those are now filtered out by `heldPaymentIds` and stay pending.
- **No payment can be dropped for good:**
  - The next run's lock uses the same filter, so it finds the payment.
  - `createSettlementCore` does not filter pending payments by period. The period only sets the payout's dates, and `earliestPending` is used only when there is no earlier payout.
  - So a late payment whose `createdAt` falls before the last period end is still paid next time. The PR's integration test shows this: £2,000.00 paid on the next run.
- **Bulk runs:** `payout-bulk-transfer.ts` calls `createSettlement` once per seller, so every run goes through the lock and the filter. The only caller of `createSettlementCore` without `heldPaymentIds` is the re-export from `apps/api`, and only tests use it.
- An unheld payment gets no sale line in this run. A refund on it in the meantime is therefore an ordinary refund before payout, and the next run charges it.
- **Regression checks:**
  - With the filter removed (`finance-runtime` rebuilt), the integration test fails: 2 lines instead of 1.
  - Both new unit tests also fail.

**N3 (LOW, run did not top up the buyer's refund record): FIXED**
- `lockPendingPayments` calls `payment_refund_backfill_from_payout_lines(id)` for each payment it holds, after the `FOR UPDATE`. That is before `findUnlinkedCapturedPayments` reads `refundedPence`, which is a later statement in the same transaction, so it sees the inserted rows.
- **Regression check:** with the call removed (`persistence` rebuilt), the PR's test fails: `[]` recorded instead of £500 `payout_topup`.
