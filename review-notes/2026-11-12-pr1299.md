# Security review: PR #1299 `books0-xero-token-sealing`

Reviewed 2026-11-12. Branch head `c4d9fec0` (2 commits). Merge base `fdd90ca1`. `origin/main` head `2aac65cc`; main was force-updated during the fetch, and it now has 3 commits the branch does not, including migration `0362_artwork_register_zoho_price`.

## Verdict: FIX FIRST

The encryption itself is sound. It uses the existing AES-256-GCM envelope with a fresh random 12-byte IV for every seal and a separate key read from config. Nothing logs plaintext. The backfill's compare-and-set update is correct and idempotent. The personal-data removal is complete for the current tree.

Three things block the merge:

1. A deploy without the key can permanently lose the live Xero refresh token.
2. The repository's read rule disagrees with the backfill's. During a rolling deploy this serves a stale (rotated-out) refresh token.
3. The migration journal entry collides with main.

## Findings

### F1. High: the key is optional, so a forced refresh can burn the rotated refresh token

- **Where:**
  - `apps/worker/src/env.ts:252` and `apps/api/src/env.ts:241`: `XERO_TOKEN_DEK_KEY` is optional.
  - `docker-compose.prod.yml:88,175`: `${XERO_TOKEN_DEK_KEY:-}`.
  - `packages/db/src/xero-token-sealing/sealing.ts:33-38`: the comment says the sealer "cannot lock anyone out".
  - `packages/finance-runtime/src/accounting/xero-auth-runtime.ts:68-75,121-124`: the refresh path.
- **Scenario:**
  1. The release is deployed before `XERO_TOKEN_DEK_KEY` is set. The docs allow this, and nothing fails at boot.
  2. The existing plaintext row still reads, so the worker's proactive cron refresh (`force: true`) calls `xero.refreshToken()`. Xero rotates the refresh token.
  3. `persistRefreshedTokens` calls `updateTokens`, which throws `xero_token_sealing_key_missing`. The new token set is thrown away, and the row is marked `needs_reauth`.
  4. The DB still holds the previous refresh token, which Xero has already rotated out. After Xero's short grace window the connection is dead.
  5. An admin cannot reconnect either, because `upsertConnection` also throws until the key is set.
- **Result:** the deploy causes a Xero outage, and the comment's claim is false.
- **Fix (either option):**
  - Option (a): fail fast at boot. In both env schemas, require `XERO_TOKEN_DEK_KEY` whenever `XERO_CLIENT_ID` is set, and parse it with `parseAuthDekKey` inside the schema. Use `${XERO_TOKEN_DEK_KEY:?…}` in compose for api and worker.
  - Option (b): add `XeroTokenSealer.canWrite`, and have `refreshXeroTokensIfNeeded` / `proactiveRefreshXeroTokens` and the OAuth callback refuse before calling Xero when it is false.
  - Either way, add a test: no key plus a legacy row means Xero `refreshToken` is never called.

### F2. Medium: the repository prefers the sealed value, but the backfill prefers plaintext, so a mixed-version window serves stale tokens

- **Where:** `packages/db/src/xero-token-sealing/sealing.ts:57-78` (`open`: "Sealed values win"), used by `packages/persistence/src/repositories/drizzle-xero-connection.repository.ts:24-29`. Compare `packages/db/src/xero-token-sealing/backfill.ts:47-67`: "A plaintext value, being the newer write, wins over a stale sealed one".
- **Scenario:**
  1. During a rolling deploy or partial rollback, a previous-release API or worker is still running. It only knows the plaintext columns.
  2. The new release has already written sealed tokens (on connect or refresh), or the backfill has run.
  3. The old instance refreshes and writes new plaintext `access_token` / `refresh_token`, leaving the stale `*_sealed` values in place.
  4. The new release's `findLatest()` returns the stale sealed tokens and refreshes with a rotated-out refresh token, which ends in `needs_reauth`.
  5. The plaintext also stays at rest until someone re-runs the backfill.
- **Reproduced on PG16:** after `upsertConnection(OLD-A/OLD-R)` and a raw `update … set access_token='NEW-A', refresh_token='NEW-R'`, `findLatest()` returned `OLD-A OLD-R`.
- Going the other way, an old instance reading a sealed row gets `null` tokens. So the backfill must not run while old instances remain.
- **Fix:**
  - In the repository read path, use the backfill's rule: a non-null plaintext value wins. Only an older release can write plaintext, so it is always the newer value. Optionally re-seal it on read.
  - Add a repository test for this case.
  - Document the rollout order in the script header, `.env.example` and the PR: (1) migrate, (2) deploy api and worker with the key, (3) confirm no old instances remain, (4) `--apply`, (5) `--verify`.

### F3. Medium (blocks merge): journal `idx` collides with main

- **Where:** `packages/db/drizzle/meta/_journal.json:2448`: the new entry has `"idx": 350`. Main's `0362_artwork_register_zoho_price` is also `idx` 350.
- **Scenario:** `git merge-tree origin/main HEAD` reports a content conflict in `_journal.json`. A naive "keep both" resolution leaves two entries with `idx` 350, and no test catches duplicate idx.
- **What is already fine:** `when` 1806739200000 is strictly greater than main's last entry (1806307200000). Applying main then the branch worked.
- **Fix:** rebase onto main and renumber the entry to `idx` 351, keeping the `when`.

### F4. Low: the migration test asserts the entry is the newest in the journal

- **Where:** `packages/db/src/migration-0367-xero-token-sealing.test.ts:15-21`. It hard-codes `when` and checks that it is greater than every other entry.
- **Scenario:** the next migration with a later `when` makes this test fail on main. Tests must never assert they hold the last journal entry.
- **Fix:** assert the entry exists, that its `idx` is unique, and that its `when` is greater than the entry immediately before it (or greater than 1806307200000). Do not compare it against all entries.

### F5. Low: the sealed columns accept unprefixed text, so `verify` can pass while plaintext remains

- **Where:** `packages/identity-contracts/src/auth-at-rest.ts` (`open` returns non-`v1:` input unchanged), reached through `sealing.ts:66-72`, `backfill.ts:42`.
- **Scenario:** a bad manual fix or script puts a raw token into `access_token_sealed`. The app reads it happily, and `--verify` reports `complete` even though the token is plaintext at rest.
- **Fix:** in `openOne`, throw `unreadable` unless `isEnvelopeSealed(sealed)`, and add a test for it.

- **"Reads fall back to the plaintext column only until a row is sealed":** true, but see F2.

### Info

- **Envelope:** AES-256-GCM, random 12-byte IV per seal, 16-byte tag, `v1:` prefix. This is identical to Identity's sealed secrets.
  - The key comes only from `XERO_TOKEN_DEK_KEY`, a dedicated key separate from `AUTH_DEK_KEY` (good separation).
  - There is no AAD binding to the row or column, so someone with DB write access could swap ciphertexts between rows or columns. That matches the existing Identity design, and DB write access already gives that person a lot of power. Acceptable.
- **No plaintext logged:**
  - The script prints counts and status only.
  - Errors are code strings (`xero_token_sealing_*`), so `last_refresh_error` never holds a token.
  - No logger call touches the connection or its tokens.
- **Backfill:**
  - It is idempotent: a second run gives `{sealed:0}` and leaves the rows byte-identical.
  - It is safe against a concurrent new-release refresh: the compare-and-set on all four columns skips the row (tested), and the next run picks it up.
  - It does a seal-then-open round-trip check before writing.
  - It runs one statement per row with no surrounding transaction, which is fine.
- **Plaintext cleared:** both the backfill and every repository write set the plaintext columns to null. Old values remain in dead tuples, WAL and existing backups. Xero refresh tokens rotate on the next (proactive) refresh, which makes the backed-up values useless. Recommend forcing a refresh and running `VACUUM xero_connection` after `--apply`.
- **Rollback (`0367_rollback.sql`):** safe.
  - It never writes decrypted tokens back. Sealed rows become `''` / `needs_reauth`, then NOT NULL is restored and the sealed columns are dropped.
  - It follows the repo's `SET LOCAL lock_timeout` convention.
  - The forward migration re-applies cleanly afterwards (tested).
- **Least privilege:** `api_app` holding ALL PRIVILEGES (including TRUNCATE) on `xero_connection` predates this PR. Narrowing it to INSERT/SELECT/UPDATE/DELETE is a possible follow-up.
- **Personal-data removal:**
  - All 8 emails and every buyer name from the three deleted reports were grepped across the branch tree: 0 hits.
  - A tree-wide email sweep found no other real-looking addresses in committed reports or data files (see F7 for test fixtures).
  - The new `.gitignore` rules (`docs/reports/*` except the README, plus `**/*reconciliation*.json`, `**/*reconciliation*.csv`, `**/*snapshot*.csv`) cover regeneration output. They match no currently tracked file.
  - There is no committed generator that writes elsewhere.
