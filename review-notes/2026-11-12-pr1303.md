## Answers to the specific questions

**Can a staff member end, or record against, another person's session?** No.
- Reconcile reads only the actor's own data: `listActiveByActor(actor)` and `listRecentStartedForActor(actor)`. The timeout branch requires `own.actorUserId === actorUserId`, and `endForActor` re-checks `actor_user_id` in SQL.
- With a foreign sid in the cookie, `findById` returns the foreign row, the owner check fails, and reconcile falls through to the actor's *own* sessions only. The foreign row is untouched. The unit test covers this.
- `actingLegalEntityId` on the audit row comes from the DB row (timeout branch) or the actor's own started event (cleared branch). It never comes from cookie `e`.
- `/start` and `/end` (`endOwnedSession`) and `recordFailedEnd` (`findStartedEvent({sessionId, actorUserId})`) are unchanged and still owner-scoped.

**Can a view session outlive its limits, or survive cookie clearing in a way that keeps impersonation alive?**
- Not past its TTL. `expires_at` is fixed at start and never extended (`drizzle-impersonation-session.repository.ts:25`). Every scoped use goes through `validateForRequest`, which refuses `ended` and ends `expired`.
- The PR deliberately stops ending *live* sessions when an admin request arrives without the cookie, which is the N1 second-browser fix. A view whose cookie was cleared after both `/end` and `record-failed-end` failed therefore stays open until its TTL. It is usable only by the same staff member re-presenting their own sid: no new capability, bounded by TTL, INFO.

**Can the forwarded view cookie and the account header disagree?**
- On SSR, no. Both come from one `cookies().get()` value, and only that one cookie is forwarded (`headers.set`, so it replaces any other value).
- Header injection is not possible. The value must match `^[A-Za-z0-9_-]{1,512}$` after Next's decoding, so a `%3B` or CRLF is rejected.
- Between SSR and the BFF/API the duplicate choice differs (R4), but that can only fail closed: the API requires `e === header` and a validated, owned, unexpired session.

**Can switching accounts while viewing escalate to the viewed client's real membership?** No.
- The switch probe now refuses an impersonation answer.
- The membership check on the API side comes first and is independent of the cookie.
- A plain choice is never forwarded as a session (`i.sid` is required).
- Switching to some *other* account the staff member belongs to while viewing still overwrites the view cookie without ending the session. It then lingers until TTL and is closed by reconcile. See R5 (INFO).

**Is the audit complete, with every start and end recorded once, atomically?**
- Start: row and `admin.impersonation_started` are written in one transaction (`admin-impersonation.service.ts:61-80`, unchanged).
- Manual end and replace: `endOwnedSession` uses the conditional end and publishes only on success, inside the transaction.
- The new reconcile paths behave the same way (`endAndRecord`).
- Two older paths are **not** yet in this shape: the `validateForRequest` timeout and `recordFailedEnd`. Under concurrency they can still write duplicate or mismatched end events (R2, R3). `domain_events` has no unique index on `admin.impersonation_ended` per aggregate. I checked `\d domain_events` on the migrated DB: there are partial unique indexes only for bid and user events.

## New findings

### R1: LOW (fail-closed, new): reconcile can end a view that started a moment ago
`apps/api/src/services/impersonation-audit.service.ts:64` (snapshot) and `:96-105` (loop). The cause is in `endAndRecord` `:120`, where `endForActor` has no expiry predicate.

**Scenario.**
1. Staff send an admin request from a tab or browser that has no current view cookie (or carries an old, replaced sid).
2. `listActiveByActor` runs and returns its snapshot.
3. Concurrently, `/admin/impersonation/start` commits a new session S and its started event, from another tab or a server action.
4. `listRecentStartedForActor` now returns S. S is not in the stale `liveIds`, has no end event, and `endForActor` happily ends the live row.

**Effect.** S is ended with `cookie_cleared_after_failed_end` milliseconds after it starts. The new view immediately gets `invalid_impersonation_session` and the audit records an early "cleared". Row and audit agree, and it fails closed. The window is small (between two queries), so this is not exploitable for access. It is a reliability and audit-accuracy issue.

**Fix.** Close only sessions that are actually expired:
- add `lte(expires_at, now)` to the end used by the cleared path (for example `endExpiredForActor`), or
- re-check liveness inside the transaction (`SELECT … FOR UPDATE` then the expiry check).

Add a unit test where `listActiveByActor` returns `[]` but the session row is still live: it must not be ended.

**Related (INFO).** Every open session that is not live is by definition expired. So after this PR the "cleared" path only ever closes *timed-out* sessions, yet labels them `cookie_cleared_after_failed_end`. The same session is labelled `timeout` if the browser still has the cookie. Consider `timeout_swept`, which is already in `ImpersonationEndReason`, for the no-cookie path so that the label reflects what happened.

### R2: LOW (audit duplicates, pre-existing, now the odd one out): the expiry path ends and records in two steps
`apps/api/src/services/impersonation-session.service.ts:70-72` (`validateForRequest` → `this.end(row.id, "timeout")`, autocommit, result ignored), then `impersonation-audit.service.ts:27-48` `recordSessionTimedOut` (`hasEndedEvent` check, then insert, with no row lock). The callers are `legal-entity-access.service.ts:84`, `container/create-platform-identity-services.ts:112`, `container/create-user-profile-services.ts:120` and `routes/payments.ts:62`.

**Scenario.** A page renders several parallel SSR API calls just after the view expires. Each call sees `expired`, so all call `end()` (one wins, the rest no-op). All then call `recordSessionTimedOut` concurrently, all see no end event, and all insert. The result is **N `admin.impersonation_ended` events** for one session.

A crash between `end()` and the record leaves an ended row with no event. Reconcile can no longer repair it, because `endForActor` returns `false`, so that end is never audited.

**Fix.** Route expiry through the same `endAndRecord` shape this PR introduced: in one transaction, `endForActor(sid, actor, "timeout")`, and publish only if it returned `true`. Then `validateForRequest` only reports `expired`. Alternatively, add a partial unique index `(aggregate_type, aggregate_id) WHERE event_type = 'admin.impersonation_ended'`, like the existing `bid.outbid` ones, and treat a conflict as "already recorded".

### R3: LOW (audit mismatch, pre-existing): `recordFailedEnd` publishes even if it did not end the row
`apps/api/src/services/admin/admin-impersonation.service.ts:166-185`. The code checks `hasEndedEvent` outside the transaction, then calls the unconditional `end(sessionId, "cookie_cleared_after_failed_end")` (a no-op if already ended) and **always** publishes.

**Scenarios.**
- The row was already ended with `timeout` by `validateForRequest` and the timeout event is not yet written (R2 window), or was lost. Then the audit says "cleared" while the row says `timeout`.
- It races with a reconcile or another `recordFailedEnd`. Then a duplicate end event is written.

The round-2 notes described `recordFailedEnd` as already ending the row "in the same transaction". It does, but not conditionally, so it does not meet the bar this PR sets for reconcile.

**Fix.** Use `endForActor(sessionId, actorUserId, …)` inside the transaction and publish only on `true`. Otherwise return `{ ok: true, alreadyEnded: true }`.

### R4: INFO (fail-closed): SSR and BFF/API now pick different copies of a duplicated cookie
- SSR uses `cookies().get()`, which is the **last** copy. I checked Next 15.5.21 `RequestCookies`: `a=first; a=second` → `second`.
- The BFF (`proxy-policy.ts:77`, `viewSessionCookieHeader`) and the API use the **first** copy.
- The PR removed the "first duplicate, as the BFF and the API do" test and comment.

Within each hop, header and cookie now agree. Across hops, a browser carrying both a host-only cookie and a `Domain=` cookie can see SSR render one context while client-side BFF calls send a client-held `X-Legal-Entity-Id` alongside the other cookie. The API then refuses (`e !== header`, `actor_mismatch`, or no sid gives `not_a_member_of_legal_entity`). This never grants another entity's context: it is a confusing state or a broken view.

**Optional fix.** Pick one rule everywhere. For example, have `readActingCookieValue` parse the raw `cookie` header with the first-match rule, keeping `cookies()` only for values set earlier in the same server action. Alternatively, when SSR detects more than one `lax_acting_legal_entity_id` pair, treat the choice as absent and expire both (`expireSharedActingCookie`).

### R5: INFO: switching to another member account (or clearing the choice) while viewing still orphans the view
`acting-context.actions.ts` `switchActingLegalEntity(X)` or `(null)` overwrites the view cookie without calling `/admin/impersonation/end`. The session stays live until TTL and is later closed by reconcile, labelled "cleared" (see R1 note). This is not an escalation: X is a real membership. **Fix (optional):** when the current choice carries `i.sid`, end the view (or refuse the switch) before writing the plain choice.

### Out of scope, noted (pre-existing, not in this diff)
`sales.reader.ts:73-86` and `:111-125`, `saleroom.reader.ts:15-24`, `lots.reader.ts` and `password-status.reader.ts` forward **every** browser cookie (`jar.getAll()`, including the session cookie) to `getServerApiBase()`. They bypass the "only the view cookie crosses" policy enforced in `withViewSessionCookie` and `sanitizedProxyRequestHeaders`.
- They send no `X-Legal-Entity-Id`, so the API's cookie readers do not scope these calls.
- They do leak unrelated first-party cookies to the API.

Worth a separate cleanup.
