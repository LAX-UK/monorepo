## Verdict: SHIP

The allocation rule is correct for the AD-5b invariant. For the same person, Portfolio "Paid so far" equals Money paid less refunded, and "Total due" equals Money "Owed by you". This holds for paid, part-refunded, refunded, unpaid and cancelled orders. Money figures are unchanged. Only Portfolio moves.

There are no blockers. Finding 1 (framing and merch folded into a work's "Price") is the one I would fix next, in a follow-up or before merge if it is cheap. It does not break reconciliation, only what one work's row says.

## What I checked

### Rounding drift (property test)

I ran 20,000 random orders through `allocateOrder` with a seeded generator (test kept out of the repo; the code is below). Each order had 0–4 lines, prices 0–30,000p (odd pence included), random held/released flags, delivery 0–5,000p, unshown extras 0–9,998p, `totalPence` null 25% of the time, and 0–3 refunds against a line, against the whole order, or against an unknown line such as a frame.

Every case satisfied all of these:
- The sum of price plus shipping across lines equals the order total exactly.
- The sum of refunded equals min(refunds, total).
- Each line's refund is at most what it was charged.
- At most one line carries shipping.
- An order with zero lines gives `[]`.

All arithmetic is integer, so there is no drift.

One caveat. If `totalPence` is less than the sum of the lines (a discount), the shares add up to the lines, not the total: the guard is `uncovered = max(0, …)`. Today `shop_order` has no discount column, so this cannot happen. Add an assert or a test if discounts ever arrive.

### Double counting and attribution

- Refunds are grouped by `orderId` before allocation. A refund whose `orderLineId` points at another order's line is treated as a whole-order refund on its own order and never reaches the other order. I tested this.
- A duplicate line id would double-count goods. That cannot happen: `shop_order_line_edition_active_uid`, `shop_fulfilment_order_uid` and `shop_certificate_edition_uid` keep edition rows one per line, and settled lines exclude held line ids.
- Failed and cancelled refunds are ignored on the Portfolio side. Money also leaves them out of its subtotals (`portfolio-money.vm.ts` filters out `cancelled`, and failed refunds are never emitted). The rule is the same on both sides.

### Privacy

- Settled lines, pending lines, orders and refunds are all filtered by `shopOrder.identitySubjectId = subject`.
- The editions join still restricts the purchase to the subject's own order, so a later owner never sees the previous buyer's price. The integration test covers this.
- No other person's lines enter the allocation.

### Money unchanged

`orderEntries`, `refundEntries`, `originalEntries` and `saleEntries` are untouched. In the contract tests, only Portfolio expectations moved.

### Other order states

- **Pending (unpaid) orders:** `owed` is the sum of that line's charges. Delivery and unshown charges sit on the first line, so per-order due equals the order total.
- **Cancelled and expired orders:** neither side counts them.
- **Fully refunded orders:** the edition gives no row, settled rows with nothing kept are dropped, and net is 0 on both sides.

### Display only

The PR changes no writes, charging or refund paths: only the reader, the adapter, the view models and one TSX minus sign.

## Findings (most important first)

### 1. Framing and merchandise charges are folded into another work's "Price" (should fix)

- **Where:** `apps/shop-api/src/application/lax-portfolio/order-allocation.ts:61`, together with `listSettledOrderLines` and `listPendingOrderLines`, which drop `kind = 'framing'` and lines without an artwork.
- **Scenario:** an order has print A at £100, print B at £200, framing for B at £60 and a tote bag at £20. A is the carrier, so A's work page shows "Price £180" and B's shows "Price £200". The order total and the Portfolio total are right, but A's row overstates A's price and B's framing sits on A.
- **Fix:**
  - Allocate each framing line to the line named by its `framingForLineId`.
  - Leave only truly unattributable charges, such as merch, on the carrier.
  - Optionally, emit merch and framing as a separate cost line rather than inside `price`. Adding a new `LAX_COST_LINE_KINDS` value is not backward compatible: `Value.Check` in `parseLaxPortfolioResponse` rejects unknown enum values, which nulls the whole Portfolio response for older account builds. Ship it in a separate, account-first change.

### 2. A returned work with money kept shows as "Sold" (minor UX)

- **Where:** `apps/shop-api/src/application/lax-portfolio/shop-portfolio.adapter.ts:297` (`settledLineItem` returns status `"sold"`).
- **Scenario:** a work is returned and released, and the refund leaves something kept, such as unrefunded delivery or a part refund. The buyer sees the work as "Sold" although they never sold it. A resale shows both this "Sold" row and the payout row.
- **Fix:** acceptable for now because the money is correct. A "returned" status, or a note on the row, would need the same account-first enum rollout as finding 1.

### 3. Deploy order: older account builds overstate "Paid so far" (low, transient)

- **Where:** `packages/lax-ecosystem/src/lax-portfolio-contract.v1.ts:161`.
- **What changed:** `paid.lines` changed meaning from net of refunds to gross, with the new optional `refunded` field. Schema-wise this is backward compatible: `Type.Object` allows extra properties, so older parsers accept it. But an account build from before this PR ignores `refunded` and sums gross lines, so its Portfolio reads above Money by the refunded amount until it is redeployed. The fetch is `no-store`, so there is no long-lived cache.
- **Fix:** deploy account together with or before shop-api, or note the window in the release.
- The other direction (new account reading an old shop-api response) is safe.

### 4. The settled-lines limit includes held lines (low)

- **Where:** `apps/shop-api/src/infrastructure/drizzle-portal-portfolio.repository.ts:154–174` (limit 500); held lines are filtered out afterwards at `:340`.
- **Scenario:** a buyer with more than 500 paid lines loses older released or resold lines, and Portfolio then reads below Money.
- **Fix:** exclude held lines in SQL (`releasedAt IS NOT NULL` OR the edition owner is not in the person's parties), or accept the limit and document it.

### 5. Nits

- `paidLines` is renamed to `paidAmounts` in the `@lax-ecosystem` public exports. All in-repo consumers are updated. Mention it if anything outside the repo imports the package.
- The delivery carrier is "first held line", so reselling or returning the first work moves its delivery charge onto another work's row afterwards. This is by design and documented; it is just surprising.
- `costBasisLines` now includes framing and merch through the carrier `price`, and is gross of refunds. It has no current consumers.

## Property test used (temporary, not committed to the PR)

```ts
import { describe, expect, it } from "vitest";
import { allocateOrder, allocateOrders } from "./order-allocation.js";

let seed = 1323;
const rnd = (n: number) => { seed = (seed * 1103515245 + 12345) & 0x7fffffff; return seed % n; };

describe("review property", () => {
  it("allocations sum to order total and refunds to min(refunds,total) when total >= goods", () => {
    const failures: unknown[] = [];
    for (let i = 0; i < 20000; i++) {
      const n = rnd(5);
      const lines = Array.from({ length: n }, (_, k) => ({ id: `l${k}`, pricePence: rnd(30001), held: rnd(2) === 0 }));
      const goods = lines.reduce((s, l) => s + l.pricePence, 0);
      const ship = rnd(3) === 0 ? 0 : rnd(5001);
      const extra = rnd(2) === 0 ? 0 : rnd(9999); // framing / unshown lines
      const total = rnd(4) === 0 ? null : goods + ship + extra;
      const tot = total ?? goods + ship;
      const refunds = Array.from({ length: rnd(4) }, () => ({
        lineId: rnd(3) === 0 ? null : rnd(2) === 0 ? `l${rnd(n + 1)}` : "frame",
        amountPence: 1 + rnd(Math.max(1, Math.floor(tot / 2) | 1)),
      }));
      const shares = allocateOrder({ totalPence: total, shippingPence: ship, lines, refunds });
      if (n === 0) { if (shares.length) failures.push({ i, msg: "zero lines" }); continue; }
      const charged = shares.reduce((s, x) => s + x.pricePence + x.shippingPence, 0);
      const refunded = shares.reduce((s, x) => s + x.refundedPence, 0);
      const refundSum = refunds.reduce((s, r) => s + r.amountPence, 0);
      const ok = charged === tot && refunded === Math.min(refundSum, tot)
        && shares.every((x) => Number.isInteger(x.pricePence) && x.refundedPence <= x.pricePence + x.shippingPence && x.pricePence >= 0)
        && shares.filter((x) => x.shippingPence > 0).length <= 1;
      if (!ok) failures.push({ i, lines, ship, total, refunds, shares, charged, refunded });
    }
    expect(failures.slice(0, 3)).toEqual([]);
  });

  it("total below goods (discount / data drift): shares overstate the order", () => {
    const shares = allocateOrder({ totalPence: 900, shippingPence: 100, lines: [{ id: "a", pricePence: 1000, held: true }], refunds: [] });
    const charged = shares.reduce((s, x) => s + x.pricePence + x.shippingPence, 0);
    expect({ charged, shipping: shares[0]?.shippingPence }).toEqual({ charged: 1000, shipping: 0 });
  });

  it("refund against a line of ANOTHER order is not attributed (refunds keyed by orderId)", () => {
    const shares = allocateOrders({
      lines: [ { id: "a", orderId: "o1", pricePence: 1000, held: true }, { id: "b", orderId: "o2", pricePence: 1000, held: true } ],
      orders: new Map([["o1", { totalPence: 1000, shippingPence: 0 }], ["o2", { totalPence: 1000, shippingPence: 0 }]]),
      refunds: new Map([["o1", [{ lineId: "b", amountPence: 300 }]]]),
    });
    expect([shares.get("a")?.refundedPence, shares.get("b")?.refundedPence]).toEqual([300, 0]);
  });

  it("duplicate line id in input double-counts goods", () => {
    const shares = allocateOrders({
      lines: [ { id: "a", orderId: "o1", pricePence: 1000, held: true }, { id: "a", orderId: "o1", pricePence: 1000, held: true } ],
      orders: new Map([["o1", { totalPence: 1500, shippingPence: 500 }]]),
      refunds: new Map(),
    });
    expect(shares.get("a")).toBeDefined();
    expect([shares.get("a")?.pricePence, shares.get("a")?.shippingPence]).toEqual([1000, 0]);
  });
});
```
