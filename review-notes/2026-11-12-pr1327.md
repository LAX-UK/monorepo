### What checks out
- **Permissions are enforced server-side.** `GET /admin/v1/home-cover` needs any staff login (`requireShopStaffAuth`) and is listed in the guard test's OPEN_TO_ANY_STAFF. Picture search, PUT and DELETE each call `requireShopStaffCapability(…, "editorial.publish")`, and only `editor` holds that capability. PUT and DELETE need an idempotency key and record the actor.
- **A saved picture must be the Shop's own** (`drizzle-home-cover.pictures.ts`). The key must be an `active` `shop_media_asset` of a kind other than `artist_application_image`, or an edition image (`shop_artwork_image`). Anything else loads as `picture_unknown`. The 10 MB cap is checked against the object head before the bytes are read. Staff media kinds already exclude application images, and the only routes that touch media are admin routes. The integration test covers an upload, an application image, a stray key and a missing key.
- **Readability check.** The save measures the desktop and wide sizes and refuses `picture_cannot_carry_type` when the desktop scrim is null. The public and admin presenters apply the same check on read, so a stored picture that later fails under tighter rules is not drawn.
- **The Shop home is unchanged when nothing usable is set.** `readStaffCover` returns null when there is no cover, when the read throws, or when `photoFromCover` refuses the picture. `isUsableStaffCover` makes the plate win. `srcSetFor` is used only when the slide is a photo (`cover-slide.tsx` ~L290); today's home draws a plate, so its markup does not change. Public reads use `no-store`, and the BFF validates the response with `parsePublicHomeCover`.
- **No restyling.** The only change to shared marketing-ui is the new `cover-photo.ts` (a moved file) and a subpath export.
- **The moves change no behaviour.** The analyser files moved from worker to `packages/image-processing/src/cover` as pure renames (0 changed lines). `photoFromCover` and `toPhotoSlot` are identical, token for token, to the removed `apps/web` copy. The worker, web, marketing-ui and image-processing tests are green.
- **Grants follow least privilege.** `shop_home_cover` is added to `SHOP_COMMERCE_TABLES` only; the invariant test asserts it is also on the API and worker deny lists. The shop-role contract passes.
- **Service and ports.** Measuring happens outside the transaction, under an advisory xact lock. The audit stores a before/after summary. Ports, store and presenters are split cleanly; the public catalogue routes depend only on `PublicHomeCoverReader`.

### Verdict: **FIX FIRST** (fixes 1 and 2 are small; the rest can follow)

1. **The "Featured on home" page goes down whenever the cover read fails** — `apps/shop-admin/src/app/(staff)/editorial/featured/page.tsx:18,31`
   *Scenario:* shop-admin is deployed before the shop-api that serves `/admin/v1/home-cover` (a 404), or the cover read returns a 5xx (for example a malformed `analysis` row). `AdminFailedPage` then replaces the whole page, and editors lose the prints, artists and categories editor that works today.
   *Fix:* treat a cover read that is not ok (other than unauthorized) as a failed state inside `HomeCoverSection` only. Pass `cover: AdminHomeCover | null` plus a failure flag, and always render `HomeFeaturesEditor`. Add a page test for this.

2. **The route tests do not cover every role the brief names** — `apps/shop-api/src/routes/admin/v1/home-cover.routes.test.ts:57-87`
   *Scenario:* only `editor` (allowed) and `read_only` (refused) are exercised. Nothing would catch a future grant of `editorial.publish` to `fulfilment`, `finance` or `catalogue_editor`.
   *Fix:* use `it.each(["fulfilment","finance","catalogue_editor","read_only"])`: each role gets 200 on GET and 403 on PUT, DELETE and `/pictures`, with nothing saved and nothing audited.

3. **Keyboard moves of the focal point are not announced** (a11y, minor) — `packages/staff-ui/src/forms/focal-point-picker.tsx:62,106`
   *Scenario:* a screen-reader user presses an arrow key. The position text sits only in an `aria-describedby` span, which is not re-read when it changes, so the user gets no feedback.
   *Fix:* add a visually hidden `aria-live="polite"` region that shows `describeFocal(value)`, or model the control as two sliders with `aria-valuetext`. Add a test.

4. **Kit rules: raw colours, and the component is undocumented** (minor) — `focal-point-picker.tsx:115`
   *Scenario:* `border-white` and the `rgba(0,0,0,.65)` arbitrary shadow skip the kit's `light-dark()` tokens. `FocalPointPicker` is not in `packages/staff-ui/README.md`, and no Kit line was added to `docs/design/staff-design-standard.md`, which the README requires in the same PR.
   *Fix:* keep the theme-independent marker (it has to show on any photo), but name it as a token or a documented exception, and add the README entry and Kit line.

5. **A test for unconfirmed uploads is missing** (minor) — `apps/shop-api/src/infrastructure/home-cover/home-cover.integration.test.ts:94`
   *Scenario:* a `pending` or `rejected` `shop_media_asset` must be refused. The code does this (`status = 'active'`), but no test checks it.
   *Fix:* add both rows to the "reads only the Shop's own pictures" case and expect `null`.

6. **A replay downloads and measures again** (nit) — `apps/shop-api/src/application/home-cover/home-cover.service.ts:123`
   *Scenario:* `measure()` runs before `withAdminIdempotency`. A retried save with the same key downloads the picture (up to 10 MB) and measures it again. If the picture became unusable in between, the retry returns 400 instead of the stored result.
   *Fix (optional):* look up the idempotency record before measuring, or accept and document this behaviour.
