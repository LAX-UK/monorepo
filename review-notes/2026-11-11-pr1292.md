# Security review: PR #1292 `fix-view-as-client-context` ("view as client" cookie forwarding)

Reviewer: independent security review (automated routine), 2026-11-11
Diff: `git diff origin/main...origin/fix-view-as-client-context` (7 files, +207/-1)

## Verdict: **FIX FIRST**

The web-side change is tight. It forwards one cookie, by exact name, only when the value is base64url and carries a UUID `i.sid`. It never forwards the rest of the Cookie header, and it adds no CRLF or header-injection path. I found no way for a client member, a non-staff user, or a staff member without a valid session to act as another entity through it.

However, the PR makes several API code paths reachable from the web app for the first time. Until now they were dead, because the cookie never reached the API. Those paths trust the cookie's `sid` and `e` without checking who owns the session (F1). The impersonation audit trail is also still not intact while a session is live (F2). F1 is a small, contained fix and should land with this PR or just before it.

## Findings

### F1: MEDIUM, impersonation end/replace paths act on any `sid` without an ownership check, and audit events take the entity id from the client (newly reachable)
- `apps/api/src/services/admin/admin-impersonation.service.ts:116-141` (`endImpersonation`)
- `apps/api/src/services/admin/admin-impersonation.service.ts:59-79` (`startImpersonation`, `session_replaced` branch)
- `packages/persistence/src/repositories/drizzle-impersonation-session.repository.ts:39-48` (`end` filters only on `id` and `endedAt IS NULL`; there is no actor filter)
- Made reachable by `apps/web/src/lib/data/http/server-request-headers.ts:90-96` and `apps/web/src/lib/bff/proxy-policy.ts:76-78`. The server actions `endAdminImpersonationAction` and `startAdminImpersonation` use `authedServerFetch` with the default flags, so the cookie now reaches `/admin/impersonation/{start,end}`.

**Exploit scenario.** Staff user A holds `requirePlatformAdminFull` and learns staff user B's impersonation session id. Session ids show up in audit and event views (`session_id` in `admin.impersonation_*` payloads). A sets `lax_acting_legal_entity_id` in devtools (the cookie is `httpOnly:false`) to `base64url({"v":1,"e":"<any entity uuid>","i":{"sid":"<B's sid>"}})`, then clicks "End view" (`POST /admin/impersonation/end`) or starts a new view (`/start`).
- B's session row is ended (`manual` or `session_replaced`).
- An `admin.impersonation_ended` event is written with `actorUserId = A` and `actingLegalEntityId` set to whatever `e` A chose.

A can also do this to their own session with a false `e`, which records a manual end against an unrelated entity. That breaks the integrity of the impersonation audit trail. This is not privilege escalation: the attacker is already a full platform admin, and `validateForRequest` is still correct, so nobody gains client access. But it lets one staff member terminate another's session and write misleading audit records.

**Fix.** In both paths, load the row (`findById`) and require `row.actorUserId === actorUserId` and `row.endedAt == null`. Take `actingLegalEntityId` from `row.targetLegalEntityId`, never from the cookie's `e`. If the actor doesn't match, return `no_active_impersonation` (for end) or skip the replace (for start). Add tests for an actor mismatch and for a mismatched `e`. Optionally, have `repo.end` take `actorUserId` as well.

### F2: MEDIUM (audit integrity, partly pre-existing): live sessions still get spurious `cookie_cleared_after_failed_end` audit events
- `apps/api/src/services/impersonation-audit.service.ts:50-60` (`reconcileFromAdminRequestCookie`), run on every platform `/admin/*` request (`apps/api/src/routes/admin.ts:100-108`)
- `apps/web/src/lib/data/http/server-request-headers.ts:134-136`: the view cookie is attached only when `!skipActingLegalEntityHeader`.

Most admin SSR calls pass `skipActingLegalEntityHeader: true`, so they never carry the view cookie. That covers `lib/data/http/authed-fetch.server.ts` (the back-compat wrapper always skips), every `getServerHc()` call (`hc-server.ts:64-66`), `admin-submission.service.ts`, `admin-documents.service.ts`, `admin-saved-view.service.ts`, `admin-stripe-connect.service.ts`, `admin-qr-codes.service.ts`, `actions/admin-atg.ts`, and others.

**Scenario.** Staff start a view session and then load any admin page or action backed by those helpers. The API sees no cookie, decides the browser cleared it, and publishes `admin.impersonation_ended` / `cookie_cleared_after_failed_end` for the open session. It publishes only the event and doesn't end the DB row, so `validateForRequest` keeps passing. Client-scoped requests then keep succeeding under a session the audit log already shows as ended, and the later real end or timeout is recorded as a second "ended" event. Before this PR the same thing happened on every admin request, so this is not a regression. But the start/end/timeout audit trail the PR is meant to restore is still not intact.

**Fix.** Send the view-session cookie on every SSR API call, independent of `skipActingLegalEntityHeader`. It is safe to do that:
- The API reads the cookie only together with a matching `X-Legal-Entity-Id` (`e === header`) or a matching `/legal-entities/:id`.
- The API always validates the actor and expiry server side.
- The SSR base is always the API: no caller passes `baseUrl`, and `getServerApiBase()` uses INTERNAL_API_URL, then NEXT_PUBLIC_API_URL, then localhost.

Separately, and better: make `reconcileFromAdminRequestCookie` decide from `listActiveByActor(actor)` instead of from whether a cookie is present. Also stop it returning early for any syntactically valid `sid` without checking the owner. Today a stale or foreign `sid` cookie suppresses reconciliation for the actor's own open sessions.

### F3: LOW, an expired session silently falls back to the staff member's own context on submissions reads
- `apps/web/src/lib/data/http/authed-server-fetch.ts:50-62` (`authedServerFetchWithEntityFallback`), used by `submissions.reader.ts`.

When the view session expires, the first call returns 403 `impersonation_session_expired`. The retry drops the header and cookie, and `createSubmissionsLegalEntityContext` falls back to the staff member's personal entity. The client-area UI then shows staff data under the client's banner instead of the expiry state. This leaks nothing across entities, but it is confusing and hides the timeout. **Fix:** don't retry when the 403 code is `impersonation_session_expired` or `invalid_impersonation_session`.

### F4: LOW / INFO, duplicate-cookie handling differs between the SSR path and the BFF/API paths
- SSR: Next `cookies().get()` returns the **last** duplicate (checked: `RequestCookies` on `a=FIRST; a=SECOND` gives `SECOND`).
- BFF helper (`view-session-cookie.ts:16-24`), API regex (`impersonation-cookie.ts:11-13`) and client `parseActingLegalEntityId` take the **first**.

Each path is consistent with itself: on SSR, the header and the forwarded cookie come from the same value, and on the BFF path, the header from `document.cookie` and the forwarded cookie both use the first value. Because the API always checks `e === X-Legal-Entity-Id` and the session owner, a tossed cookie (for example a `Domain=` cookie from a sibling subdomain) causes at worst a 403 or a disagreement between SSR and the client, never another entity's context. Also, the BFF helper returns `null` when the first match is invalid and doesn't fall through to a later valid one. That fails closed, which is good. **Optional fix:** pick the duplicate in one shared way, for example by reusing `parseActingLegalEntityId`'s choice, and keep `expireSharedActingCookie` in place.

### F5: INFO, hardening
- `view-session-cookie.ts:4,21`: there is no length cap. Browsers cap a cookie near 4 KB, so this is not exploitable, but a cap of about 512 chars costs nothing.
- `apps/web/src/lib/legal-entity/acting-context.actions.ts:222-227`: the impersonation cookie is set without `secure` (unlike `actingAccountCookie`, which sets `secure` in production). It has been readable from JS by design since before this PR. A stolen `sid` is useless without the actor's own bearer token, because `validateForRequest` checks `actorUserId`. Still, add `secure: process.env.NODE_ENV === "production"`.
- `switchActingLegalEntity` overwrites a view cookie with a plain choice without ending the session, which is left to time out (pre-existing).

## Attack checklist (what was checked)

| Question | Result |
|---|---|
| Client member, or anyone else without staff rights, uses a forged view cookie | Blocked. `resolveLegalEntityContextFromHeader` checks membership first, then `canAccessPlatformAdminRoutes` before it reads the cookie (`require-legal-entity-context.ts:29-35`). New test at `.test.ts:274` covers it. |
| Staff member without a valid session | Blocked. `validateForRequest` checks the row exists, the actor matches, the entity matches, the session hasn't ended and hasn't expired. A missing `impersonationSessions` dependency fails closed (`!validation?.ok`). `e` must equal the header (test `.test.ts:298`). |
| Staff using another staff member's `sid` | Blocked for access (actor mismatch). **Not blocked for end/replace (F1).** |
| Encoding / whitespace / case / CRLF / long values | Web accepts only `^[A-Za-z0-9_-]+$` after a trim, so `%`, CR/LF, `;`, `,` and spaces are all rejected (test covers `%0d%0a`). The name match is exact and case-sensitive on both sides, and the output is rebuilt as `name=value`. `decodeActingContextCookie` requires `v===1` and UUID `e` and `i.sid`. No length cap (F5). |
| Forwarded Cookie overriding or merging with other cookies (session, identity, CSRF) | No. `cookie` is not in the proxy allow-list, so `result.set` replaces it with the single cookie, and the test checks that `identity`/`lax_bid_session` are dropped. The API reads only the acting cookie: grep finds no other `Cookie`/`getCookie` reads in `apps/api/src`. Auth is the BFF bearer, not cookies. On SSR, `headers.set("Cookie")` would replace a caller's `init` Cookie, but no caller passes one. |
| SSR leak to hosts other than the API | None. `buildAuthedSsrHeaders` is used only by `authedServerFetch` (`getServerApiBase()`, and no caller passes `baseUrl`) and `createServerHc` (`getServerApiBase()`, with skip=true). BFF upstream is `config.apiBaseUrl` built from approved paths. The bearer already goes to those same hosts. |
| Audit trail on start/end/timeout | Start is intact. Timeout is intact: `validateForRequest` ends the row with `timeout` and `onImpersonationExpired` / `recordSessionTimedOut` emits the event, and this is now reachable. End has the ownership gap (F1). Live sessions get spurious "cleared" events (F2). |
| CSRF on the BFF while impersonating | Unsafe methods require `Origin === publicOrigin` and, when present, `Sec-Fetch-Site: same-origin` (`route.ts:34-40`). The cookie is `SameSite=Lax`. Server actions get Next's built-in Origin check. GET side effects are limited to idempotent timeout bookkeeping. OK. |
| Account switching | The plain choice (bare UUID or `{v,e}` without `i`) is never forwarded, and the test checks this. Switching still travels as `X-Legal-Entity-Id`. No SW1-SW12-tagged tests exist in the repo; ran the legal-entity, account, switch and acting suites (below) and all pass. |
| Plain account-choice value reaching the API as a cookie | No path found. Both forwarding points go through `viewSessionCookieHeader`, which requires `i.sid`. Browser JS never calls the API directly (BFF only). |
