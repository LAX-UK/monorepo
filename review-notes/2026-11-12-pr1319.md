# Review: PR #1319, re-offer sweep missed-invoice hardening (fixes F2/F3 of review-notes-pr1310)

- Branch `reoffer/sweep-missed-invoice-hardening` @ `7e2f02bf`, compared with `origin/main` (which includes #1316 `lot_moved`)
- Reviewer: independent MONEY review, 2026-11-12. The PR branch was not modified.

## Verdict: FIX FIRST

F2 is fixed, and so is the first half of F3 (pinning the buyer account). The second half of F3 (counting
only live payment statuses) overshoots. With this PR, the sweep **automatically re-raises a payment and sends a
"payment due" notice** to a re-awarded buyer whose payment was cancelled on purpose: they relinquished the win,
a stale checkout was cancelled, or a capture was blocked while Stripe holds their money. On `main` no automatic
path does this. The general `ensure-lot-invoices` cron needs the lot to have no payment in any status, and this
sweep needed no payment of any status for the account. That is a new way to invoice a buyer who has walked away
(about to be defaulted), and to ask a buyer to pay twice (finding A). Two smaller findings come with it: some
reasons that can be recovered are marked dead forever (B), and the alert is sent after the mark (C).

## Findings

### A: MEDIUM, blocker. A deliberately cancelled payment now makes the sweep re-invoice the buyer

- **Where:** `packages/persistence/src/repositories/drizzle-reoffer-sweep.reader.ts:11-17` and `:79-90` (`inArray(payment.status, LIVE_PAYMENT_STATUSES)` inside the `NOT EXISTS`). The PR's own test pins this behaviour: `reoffer-clock.integration.test.ts:757` "counts only live payments: a cancelled one hides nothing".
- **Mechanism:** `ensureForLot` (`packages/finance-runtime/src/lot-invoice-initiation.service.ts:148-155`) checks only open and refunded payments. `raise` (`drizzle-bid-invoice.repository.ts:149-200`) reuses the live invoice ("a retry after the last payment expired") and inserts a **new `pending` payment**. Then `ensureForLot` stages the "payment due" notice.
- **Scenarios.** Re-awarded buyer C has a live invoice and their own payment, which is `cancelled`, while C is still the winner:
  1. **C relinquishes the win** (`cancelPendingAsBuyer`, `apps/api/src/services/payment/payment-buyer-ops.ts:99-116`) before staff record the default. Within 15 minutes the sweep raises a fresh pending payment and emails C "payment due" for a lot they gave up. This is the defaulted-buyer case the brief excludes.
  2. **A stale checkout is cancelled** (`DrizzleStalePaymentCanceller.cancelIfUntouchedSince`, `:57`), then Stripe completes the late checkout. Money is taken and lands in finance's blocked-capture inbox, and the payment stays `cancelled`. The sweep raises a new pending payment and asks C to pay **again**. Finance's "reinstate" then fails with "A newer payment exists for this lot. Refund this one instead." (`payment-blocked-capture-ops.ts:84-89`). C is charged twice until the refund, and is told to pay a second time.
  3. A plain stale cancel causes an unprompted extra "payment due" notice. If the price has changed since then, `raise` throws `BidInvoiceTotalMismatchError` on every run, so `failed` and Sentry fire every 15 minutes.
- None of this is reachable on `main`. The old sweep's `NOT EXISTS` matched any status, and `listSoldLotIdsMissingPayment` (`packages/persistence/src/repositories/lot/lot-lifecycle-queries.ts:51-66`) needs no payment of any status. The listing also has no age bound, so on first deploy every old re-awarded lot in these states would be picked up.
- **Fix:** a missed invoice means the account has no payment that stands for a live invoice. A cancelled payment should stop hiding the row only when its invoice was voided, which is what a buyer default does. That is the one case F3 was really about: the same account's earlier, defaulted payment.
  ```ts
  notExists(
    db.select({ id: payment.id }).from(payment)
      .leftJoin(bidInvoice, eq(bidInvoice.id, payment.invoiceId))
      .where(and(
        eq(payment.lotId, lotReoffer.lotId),
        eq(payment.buyerLegalEntityId, lotReoffer.offeredLegalEntityId),
        or(ne(payment.status, "cancelled"), isNull(bidInvoice.voidedAt)),
      )),
  )
  ```
  A payment with no invoice (`invoice_id` null) still hides the row, which fails safe. `worker_app` can already SELECT `bid_invoice.voided_at` (checked with psql), so no grant change is needed. Tests to add:
  - (a) C has a live invoice and a cancelled payment: **not** listed.
  - (b) A cancelled payment whose invoice is voided: listed.
  - (c) Replace the assertion at `:757` with (a) and (b).

### B: LOW-MEDIUM. Recoverable reasons are marked dead forever, so the invoice is silently never raised after the fix

- **Where:** `packages/domain/src/reoffer-invoice-outcome.ts:22-30` treats every non-`raised` answer as terminal, including unknown future reasons and the `"unchanged"` fallback. `drizzle-reoffer-sweep.reader.ts:73` then filters on `isNull(close_reason)`.
- **Scenario:** re-awarded lot L comes back `missing_seller_legal_entity`, `payment_amount_exceeds_limit` or `invalid_payment_amount`. One Sentry warning fires and the offer is marked. Staff fix the seller entity or the limit. Nothing ever lists L again:
  - This sweep skips the marked offer.
  - The general cron skips L, because the defaulter's cancelled payment exists.
  - There is no re-arm path, runbook or admin work item.

  The invoice is never raised: a false negative, which the brief ranks worse than re-listing.
- **Fix:**
  - Mark as terminal only an explicit allowlist of reasons that mean an invoice exists or the award has gone: `payment_already_exists`, `already_refunded`, `lot_moved`, `no_winner`, `lot_not_found`, `lot_not_ended`, `missing_buyer_legal_entity`.
  - For every other reason, including unknown ones and `"unchanged"`, use a back-off mark such as `invoice_not_raised:retry:<reason>`. The listing re-includes those offers when `updated_at < now() - 24h`, and the sweep warns once per retry. That is one warning a day, not one every 15 minutes, and the invoice is raised as soon as the data is fixed.
  - Document the re-arm SQL (`UPDATE lot_reoffer SET close_reason = NULL WHERE …`) in the runbook.

### C: LOW. The mark is written before the alert, so a crash between them loses the only report

- **Where:** `apps/worker/src/jobs/reoffer-sweep.ts:100-111`. The comment says "Mark first, so a crash re-reports at most once". In fact, a crash or SIGTERM after `markInvoiceNotRaised` and before `log.warn` or `Sentry.captureMessage` reports the row **zero** times, and the row is never listed again.
- **Fix:** log and capture first, then mark. A crash then produces at most one duplicate warning, which is the safe direction.

### INFO

- When `markInvoiceNotRaised` returns `false` (two concurrent sweeps), the sweep still counts and warns. That gives a duplicate warning at most, which is fine.
- The Sentry tag `reason` comes from `ensureForLot`'s fixed set, so it has bounded cardinality. That holds as long as the reasons stay enum-like.
- F1 (the stale read in `ensureForLot`) is fixed on `main` by #1316. This PR adds no new caller.

## Required before merge

1. A: change the payment `NOT EXISTS` so a cancelled payment counts as dead only when its invoice is voided, and add tests (a) and (b).
2. B: mark permanently only the allowlisted reasons. Give every other reason a daily back-off re-list.
3. C: alert before marking.
