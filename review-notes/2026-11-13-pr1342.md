## What is good

- **Try again is the life cycle's own requeue, under the row lock.** `tryAgain` reads the document, then calls
  `transitions.apply({action:"requeue", requestedBy})`, which locks the row (`select … for update`), re-reads it through
  the domain and re-decides. The pre-check (`canTryAgain`, `ALREADY_QUEUED`) is advisory; the authority is the locked
  transition. So a TOCTOU between the read and the apply cannot force a send — the domain re-checks under the lock, and on
  a lost race the service re-reads and reports `already_queued`. The integration test sends twice and proves one row, one
  `pending`, one `requeue` event.
- **Same document, same LAX reference, never a new one.** `requeue` is `failed → pending` or
  `needs_review(clear, issued=null) → pending` on the *same* row; it writes no new document. A `needs_review` holding a
  provider document (`issued !== null`) is refused, and so is `lookup = owed`. The integration test asserts the reference
  is unchanged and that `count(*) where lax_reference = …` stays 1.
- **Cannot double-send or re-queue a `sending` document.** `ALREADY_QUEUED = {pending, sending}` short-circuits to
  `already_queued` with no transition, and the domain `requeue` refuses every status except `failed` / `needs_review`. An
  `unknown` document (awaiting a lookup) is refused too. So staff action cannot collide with the sender's lease the way
  pr1340 F2 describes — it never acts on a leased row.
- **Idempotency + permission on the write.** The route carries `requireAccountingQueueWrite` (`finance.platform.write`)
  and `guards.idempotent("accounting.try-again")`; the GET carries the mount's `finance.read`. The action is also routed
  through the `/admin/*` CSRF/origin check and the dangerous-action step-up gate like every other finance mutation.
- **Nothing here can reach Books or flip the source switch.** The API container builds no Books adapter; `createBooksDocumentLinks`
  only reads `ZOHO_BOOKS_ORG_CONFIG` to *format a URL string*, and returns `null` (no link) for a rehearsal, a company with
  no org, or settings that will not parse. The switch tables are not writable here. The page is Books-only: the projector
  skips products whose switch is not Books (`books_not_selected`), so `accounting_document` holds no Xero rows and the
  state-only tab filters cannot surface another provider's work.
- **Column grants protect what the document says and where it is aimed.** Verified by direct SQL as `api_app`:
  `UPDATE … SET gross_pence`, `SET target_mode`, `SET provider`, any `DELETE`, any `INSERT` of a new document, and any
  `UPDATE`/`DELETE` of history are all `permission denied` / `42501`. Amounts, reference, payload, and the
  provider/mode a document is aimed at are immutable to the Bid API. (The outcome/identity columns are a narrower matter —
  F1.)
- **Alert and working-day maths.** Overdue is `workingMinutesBetween(LONDON_WORKING_CALENDAR, oldest, now) >
  WORKING_DAY_MINUTES` (9h), not wall-clock (M4 caught). Budget warns exactly once, on call `floor(limit*0.8)+1`
  (M5 caught). The watch only counts `pending` for modes the sender serves *and* some product aims Books at, so with Books
  off nothing reads as missed. The throttled cron monitor checks in at most every 5 min and passes the frequent ticks
  through, so a missed check-in means the sender stopped.
- **Failed-jobs source is read-only and permission-gated** (`integrations.books`, M9 caught); rows link to Finance ›
  Accounting and carry no retry/discard, matching "try again is done on the Accounting page".
- **pr1340 F1/F2 are not made worse.** Try again touches neither the lookup/verify path (F1) nor the sender lease (F2). It
  only moves a never-leased `failed`/`needs_review` row to `pending`; the existing sender then claims it normally. Locked-
  period items are allowed to be tried again by design (after someone unlocks the period in Books and confirms), which the
  confirm copy states.
- Layering holds: domain owns `queueTabFor`/`canTryAgain`/`isLockedPeriodReason`; persistence owns the SQL tab map and the
  browser/attention readers; finance-runtime owns the queue service and the Books link formatter; the API route only
  orchestrates. New interfaces are small and single-purpose. Copy is plain, sentence case, and empty/loading/error/
  pagination states all exist and reuse the staff kit (no new styles; UI-guardrail lint clean).

## Findings

### F1 — LOW (defense in depth; not reachable through any API route): the `api_app` column grants let the role forge an `issued` outcome, an arbitrary Books document id, and fabricated history rows

- Where: `packages/db/src/migrate-roles.ts` `API_ACCOUNTING_REQUEUE_COLUMNS` (all of
  `WORKER_ACCOUNTING_DOCUMENT_UPDATE_COLUMNS` except `provider`) and the `INSERT` grant on `accounting_document_event`.
- The requeue's single `UPDATE` sets a full life-cycle column set (it nulls `provider_id`, `provider_number`, `pdf_ref`,
  `mismatch_*`), so those columns must be grantable; column-level `UPDATE` cannot constrain the *value*. Proven by SQL as
  `api_app` on a throwaway DB:
  - `update accounting_document set state='issued', provider_id='ATTACKER-9', provider_number='INV-FORGED'` → **succeeds**;
    the row then reads `issued | ATTACKER-9 | INV-FORGED` and the page would show "in Books" with a link built from that id.
  - `insert into accounting_document_event (… action='complete_sending', detail='{"requestedBy":"not-real"}')` →
    **succeeds**. The append-only trigger blocks only `UPDATE`/`DELETE`, and `api_app` needs `INSERT` to log its own
    requeue, so fabricated history events are possible.
- Impact is bounded and, in my judgement, **not ship-blocking**: no API route writes these columns — the only writer is the
  domain `requeue`, which produces `pending` and nulls the identity columns. Reaching the forge needs arbitrary `api_app`
  SQL (a SQL-injection or a compromised API process), which already commands the payments tables, so this is incremental
  defense-in-depth, not a new reachable hole. What it *does* forge is LAX's belief that a document was issued in Books and
  the staff-facing Books link/id — a reconciliation/trust problem, not a change to amounts, reference or aim (all blocked).
- The PR's own words are accurate about the parts that matter ("cannot alter what a document says, where it is aimed";
  history "append-only: nobody gets UPDATE or DELETE") — I confirmed all of those hold. The gap is only that the *outcome
  and provider-document identity* are writable and that the contract test does not say so.
- Fix (optional, for the wiring PR or later): if the `issued` outcome and history authenticity want DB-level containment,
  route the requeue through a `SECURITY DEFINER` function (or a trigger that restricts `api_app`'s `UPDATE` to transitions
  ending in `pending`) so the broad column grant is not needed. At minimum, add the forge cases
  (`set state='issued', provider_id=…`) to `accounting-persistence.integration.test.ts` / the contract test as **allowed**,
  so a future reader is not misled into thinking they are blocked.

### F2 — LOW (test gives false assurance; no current role is affected): the write-permission test never exercises the write guard

- Where: `apps/api/src/routes/admin/accounting.routes.test.ts` "refuses people without the finance write permission" uses
  roles `read_only` and `sales_manager`. Both lack `finance.read`, so the mount-level `finance.use("/finance/*",
  requireFinanceAccess)` returns 403 *before* `requireAccountingQueueWrite` runs. Removing the route's write guard (M2)
  leaves every test green.
- Today this is harmless: the only roles with `finance.read` are `administrator` and `finance`, and both also hold
  `finance.platform.write` (`staff-capability-matrix.ts`), so there is no role that can read the page but not act. The guard
  is correct; it is simply unproven, and would silently stop protecting the action if a future finance read-only role were
  added.
- Fix: assert the guard with a role that has `finance.read` but not `finance.platform.write` (add a fixture/stub role, or
  assert at the capability level that `ACCOUNTING_QUEUE_WRITE_ACCESS` is strictly narrower than `FINANCE_ACCESS`).

### F3 — LOW (no test; read-only, no money/auth impact): `createBooksDocumentLinks` is never unit-tested, so the "no link for a rehearsal" rule is unguarded

- Where: `packages/finance-runtime/src/books/books-document-links.ts`. The queue-service test stubs `booksLink: () =>
  null`, and there is no test file for the real builder. Dropping `|| targetMode === "dry_run"` (M6) is not caught.
- Impact is cosmetic and read-only: a dry-run issued document carries a fake provider id, and the regex `^[0-9]{1,32}$`
  guard already rejects a non-numeric fake id, so most rehearsals still get no link; the risk is only a misleading dead
  link to a real Books org, never a write. Worth a small test because this is the one place that decides whether a
  rehearsal points at a real organisation.
- Fix: add a unit test for `createBooksDocumentLinks` covering `dry_run` → `null`, unknown org → `null`, unparseable
  config → `null`, and a live/test id → the expected `books.zoho.eu` URL.

## Verdict: SHIP

The authorisation, idempotency and lease-race handling on "Try again" are sound; it requeues the same document under the
same reference, cannot double-send, cannot reach Books, and does not worsen pr1340's F1/F2. Amounts, reference and aim are
immutable to the Bid API. The findings are all LOW: F1 is defense-in-depth not reachable through any route, and F2/F3 are
test-coverage gaps. None blocks merge; F2 and the F1 contract-test note are cheap and worth doing before the wiring PR
grants this role any live reach.
