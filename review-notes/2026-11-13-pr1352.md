## N1: classifying the create outcome across retries

The code keeps a per-attempt `.catch` inside `executeWithStripeRetries`. It sets `createMayHaveSent` when an attempt fails with `StripeConnectionError`, `StripeAPIError` or `idempotency_key_in_use`. The outcome is unknown when that flag is set or when the last error is itself unknown. A run of nothing but 429s is a definite non-send. Non-Stripe errors still roll the step back with no marker; that is pre-existing and was already noted in the #1345 re-check.

Probes against real Postgres:

- **N1a.** This is the #1345 P5 case. The first create reaches Stripe and makes the transfer, but the answer is lost. Attempts 2 and 3 get 429.
  - The payout stays `scheduled` with `stripe_transfer_outcome_unknown: rate_limit …`.
  - A −£100 line goes on a **new** payout; the original keeps £820.00.
  - The next attempt adopts the one transfer (`in_transit`, `stripe_transfer_id` = that transfer).
  - Stripe holds one transfer, of 82000.
- **N1b.** Every create gets 429.
  - The payout is marked `stripe_transfer_failed:`, with no transfer.
  - It takes the −£100 line.
  - The next attempt creates exactly one transfer, of 72000 (the new net).
- **N1c.** A connection error that never reached Stripe, then 429s. The outcome is classed unknown. That is conservative: the next run's `decideConnectTransfer` sees no transfer and creates exactly one (82000).
- No probe ever produced two live transfers.

Mutation: classifying on the last error only (dropping `createMayHaveSent ||`) fails 2 of the 4 finance-runtime retry-outcome tests, and fails probes N1a and N1c.

**N1: resolved.** Remaining severity: none. The N1c behaviour is the intended safe side.

## N3: one payout lock order across sellers

This table lists every path that moves payout lines or locks payouts, and the order it takes them in.

| Path | Order |
|---|---|
| Group charge refund (`PaymentGroupChargeEvents.reconcileRefunds`) | event claim → group → **all** member payments in id order → `lockOpenPayoutsForSellers` (all member sellers) → each member: payment (re-entrant) → `postLine` → payout (already held) |
| Group refund repair, apply (`GroupRefundRepairService.repairGroup`) | group → payments in id order → Stripe list (no payout held yet) → `lockOpenPayoutsForSellers` → give-backs and lines. A dry run takes no payout lock |
| Dispute over a group charge, or allocation (`DisputeLineEffects.reconcile`) | case → `lockPaymentsInTransaction` (id order) → `lockOpenPayoutsForSellers` (paying lines' sellers) → lines |
| Single refund, card webhook, refund reconcile job, give-back | one payment → `postLine` → one payout (one seller: no up-front lock needed) |
| Staff adjustment (`addAdjustment`) | one payout `FOR UPDATE` only |
| Settlement (`createSettlement`) | advisory lock → seller's pending payments in id order → its **own new** payout. It never locks an existing payout |
| Transfer step (`withLockedPayout`) and transfer webhook | one payout only |

All of these follow one global order: settlement advisory lock, then payments (id order), then payouts (legal entity id, then payout id). No path takes a payout and then a payment, and none takes two payouts outside that order.

`lockOpenPayoutsForEntities` sorts with `ORDER BY legal_entity_id, id FOR UPDATE`. In Postgres the LockRows node sits above the Sort, so rows are locked in the sorted order. The lock covers every payout that `findOpenPayoutForEntity` could return for those sellers, which is a superset of the rows `postLine` will take.

Mutations, each with a rebuild:

| Mutation | Result |
|---|---|
| `lockOpenPayoutsForSellers` made a no-op | `payout-cross-seller-lock.integration` fails, and probes Q1 and Q2 deadlock |

Residuals:

- **R1 (Info, test gap).** No test covers the up-front payout lock in the applied group refund repair, so removing it fails nothing. The PR body says so. The code is right, and the path is staff-triggered and rare. A unit assertion like the charge-events one, checking that the call happens after `lockInTransaction` and before any give-back, would pin it.
- **R2 (Info, acknowledged in the PR body).** The lock set is read when the lock statement runs. Suppose another transaction commits a new open payout for one of the sellers after that, or a locked payout stops taking lines while this transaction waits. `postLine` then locks that seller's newer payout outside the global order. A deadlock needs a third concurrent multi-seller transaction on that exact row. If one happens, Postgres aborts one side, and the webhook retry or reconcile queue recovers it. No money risk.
- **R3 (Info).** `reconcileRefunds` locks the open payouts of every member seller even when the event changes nothing for them (a replay, or a delivery-only refund). This only costs lock contention, and only for the length of a short transaction.

**N3: resolved.** Remaining severity: Info (R1 to R3).

## N4: negative scheduled payouts

As its last step, the payout run lists `scheduled` payouts with no `stripe_transfer_id` and net < 0. It skips any payout already attempted in the run and hands the rest to `initiateTransfer`. That function reads the net again, and when it is negative it moves the payout to `clawback_pending` **under the payout's lock**, with a `status`/net compare-and-set. This happens **before any Stripe call and before the Connect-readiness check**. It emits `payout.clawback_required`, which goes to staff ops (notification fanout).

Probes against real Postgres:

| Probe | Result |
|---|---|
| **N4a.** A −£40 payout made by a dispute line with no open payout, with Connect **not ready** | → `clawback_pending`, `negative_net_amount`, no transfer id. **Zero Stripe calls.** One `payout.clawback_required`. The staff summary (`summarizeMatching`) shows `clawbackPending: 1`, `clawbackCount: 1`, `blockerPayoutCount: 1`, `scheduled: 0`, so it is counted once, in clawback, and not also as scheduled. A second run moves nothing and emits nothing |
| **N4b.** +£60 lands on the −£40 payout after the run lists it but before the step reads it | the step reads +£20 and sends **one** transfer of 2000 (`in_transit`). No clawback event. The net was settled correctly within the same run |
| **N4c.** +£30 lands after the step reads −£40 but before it takes the lock | `payout_changed`: the payout stays `scheduled` at −£10, with no event. The next run moves it to `clawback_pending` at −£10. Net equals lines throughout |
| **N4d.** A scheduled +£10 payout taken negative by staff adjustments (−£2, then −£20) | → `clawback_pending` at −£12, with no transfer |
| PR test: lines that net the payout to exactly 0 before the run | it stays `scheduled` at 0.00 and keeps taking lines, with no event |
| PR test: after clawback, a new line | goes on a new payout, and the clawback payout's net is unchanged |

Mutations: removing the sweep fails 2 unit tests and 2 integration tests (P8 and "runs again"). Running the sweep before settlement fails "after every positive payout of the run has been sent". Making the list `<= 0` fails "leaves a negative payout that later lines netted".

Residuals:

- **R4 (Info, unchanged from main).** "Netting" happens only on the negative payout itself. Settlement always writes a seller's new sales to a fresh payout (`createSettlementCore`) and never folds in an open negative one. So a seller who has a −£40 payout and £95 of new sales in the same run is sent £95, and the −£40 goes to `clawback_pending` for staff to recover. Main behaves the same, except that on main the −£40 sat in `scheduled` unseen. This PR makes it visible, which is an improvement. Folding open negative payouts into the settlement would be a separate design change.
- **R5 (Info, deploy note).** The first run after deploy will move **every** historical negative scheduled payout to `clawback_pending` in one run. Each emits one `payout.clawback_required` staff email. Before deploying, consider counting them in production with `SELECT count(*), sum(net_amount::numeric) FROM payout WHERE status='scheduled' AND stripe_transfer_id IS NULL AND net_amount::numeric < 0`, so the staff inbox is expected.
- **R6 (Info).** "Never triggers a transfer" holds for a payout that is still negative when the step reads it. A payout that later lines took positive is sent at its correct net (N4b), the same as the resume pass would send it on the next run.

**N4: resolved.** Remaining severity: Info (R4 to R6).
