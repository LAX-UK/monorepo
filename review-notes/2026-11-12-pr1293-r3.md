### N1: fixed
- `carryOut` (`deal-artwork.service.ts:172-192`) now calls `register.offer(toId, …)` **before** `deals.setArtwork(…)`, and `withdraw(old)` after.
  - The offer takes `FOR UPDATE` on the artwork row up front. The deal row's foreign key then needs only a key-share lock on a row this transaction already holds exclusively, so there is no lock upgrade and no cycle. Competing deals take turns.
  - A stale deal version raises `DealMovedOn`, which rolls back the whole transaction, including the hold. The concurrency test "same deal, two different artworks" asserts it end to end: the loser's artwork is still `held`, and the loser gets `stale_version` with `currentVersion: 2`.
- Other orderings checked by reading the code:
  - Change racing a cancel: the change locks the new artwork, then waits on the deal row; the cancel holds the deal row and touches only the old artwork. No cycle. Covered by the third concurrency test (green 20/20).
  - Two changes between artworks held by each other's deals: the register refuses at the first `offer` check, before any wait on a second row, so nothing waits in a cycle.
- Unit test for the stale path now asserts "nothing published" instead of "offer not called". That matches the new order.
- Still open, as the second review noted, and **not introduced here**: `enquiry-conversion.service.ts` inserts the deal with `artworkRegisterId` before offering, so two conversions racing for one artwork can deadlock the same way. Suggest the same fix in a follow-up.

### N3: fixed
- A first reason recorded after the deal has stopped allowing artwork changes (agreed and later) now needs a non-blank note (`reason_required`). Covered by a new test for agreed, paid and released: refused without a note, recorded as `linked` with the note when one is given.

## New findings

### N5 (Low): the concurrency test still leaves `domain_events` rows behind
- **Where:** `deal-artwork.concurrency.integration.test.ts`, `cleanUp`.
- **What:** `register.offer` writes an `artwork_register.offer_changed` row to `domain_events`. `cleanUp` removes `artwork_register_event` but not `domain_events`, so each run leaves 4 rows that point at artworks that no longer exist.
- **Evidence:** I snapshotted the row count of all 273 public tables before and after the 20 runs. Everything matched except `domain_events`: 0, then 80.
- **Impact:** test database only. A suite that counts `domain_events` globally, or a worker pointed at that database, would see orphan events. Nothing I ran was affected (api private-sale 25 files, persistence repository, domain).
- **Fix:** delete `domain_events` (and `domain_event_delivery`, which references it) for the run's artwork ids in `cleanUp`, before the artwork rows go.
- Related, info only: `cleanUp` switches off user triggers on four tables for one transaction. That is fine on a disposable test database, but the file should keep its "needs the table owner, disposable DB" note.
