## Verdict: **FIX FIRST**

One high-severity defect: the SQL filter and the domain rule disagree, and the case they disagree on is an **urgent** one. An artwork the register shows as sold with no recorded place (`offer_state='sold'`, `offer_ref_kind IS NULL`, which the register models as "sold, where unknown") is left out of Needs attention, the view count, the nav badge, the bell and the daily check. The deal page and the "All"/"Settled" rows do show it as urgent. I reproduced this on Postgres 16. The other findings are medium or low.

## Findings

### 1. HIGH: SQL filter drops "sold, place unknown" (NULL ref), so an urgent item is hidden from the list, counts, bell and daily check
- **Where:** `packages/persistence/src/repositories/drizzle-private-sale-deal-query.repository.ts:45-49` (`settlementFollowUpOpen`)
- **Scenario:** a deal settles, then the register shows the original as `sold` with `offer_ref_kind`/`offer_ref_id` NULL. `transitionOffer` allows `sold` with `ref: null`, and `soldWhere()` maps it to `"unknown"`. The predicate is `NOT (state='sold' AND ref_kind='private_sale' AND ref_id=deal.id)`. Here that is `NOT (TRUE AND NULL AND NULL)`, which evaluates to `NULL`, so the row is filtered out. The domain `settlementFollowUp()` returns `"urgent"` for the same facts. The result is a possible double sale that never reaches Needs attention, `counts.needs_attention`, `urgentFollowUps`, the nav badge, the header bell or the daily "raised" event. It is visible only to someone who opens the deal or scans the All/Settled view.
- **Fix:** make the predicate NULL-safe and identical to the domain rule. For example: `NOT (offer_state = 'sold' AND offer_ref_kind IS NOT DISTINCT FROM 'private_sale' AND offer_ref_id IS NOT DISTINCT FROM deal.id::text)`, or `NOT COALESCE(..., false)`. Add `{ state: "sold", ref: null }` → urgent to the integration matrix, so SQL and domain stay pinned to the same truth table. Better still, add a test that runs every (kind × state × ref) combination through both the SQL and `settlementFollowUp()` and asserts they agree.

### 2. MEDIUM: the 500 cap can silently stop the daily check from raising new deals, urgent ones included
- **Where:** `apps/api/src/services/private-sale-deal/deal-settlement-follow-up.service.ts:30,43`; ordering at `drizzle-private-sale-deal-query.repository.ts:158`
- **Scenario:** the check reads the 500 **oldest-updated** open follow-ups, and that set includes deals already raised. Raised deals stay open until someone fixes the register, so once 500 unresolved deals pile up, every new deal (normal or urgent) falls past the limit and is never raised. Nothing logs that the limit was hit. `result.urgent` also counts only within the window.
- **Fix:** do not spend the window on deals already raised. Add `NOT EXISTS (raised event for deal)` to the check's query, or order `urgent` first. Log or emit a metric when `open.length === limit`, so truncation is visible.

### 3. MEDIUM: list counts and urgency are taken from the same capped, oldest-first window
- **Where:** `apps/api/src/services/private-sale-deal/deal-query.service.ts:87,122,128`
- **Scenario:** `counts.needs_attention` is `min(n, 500)` while the view itself has no cap. `urgentFollowUps` counts only urgent rows among the 500 oldest. If one recent urgent deal sits behind 500 older normal ones, the badge shows "warning" rather than "danger" and the bell hint says "needs marking sold" rather than "may have been sold twice". The PR ships exactly this cap; volumes are low today, but the brief asks that the cap never hide an urgent item silently.
- **Fix:** add a `countSettlementFollowUps(scope)` with a single aggregate (`count(*)`, `count(*) FILTER (WHERE <urgent predicate>)`) and no cap. The CASE has to mirror the domain rule, so give it the same truth-table test as in finding 1. It is also cheaper than loading 500 rows on every page load (finding 5).

### 4. LOW: Try again on a settled deal whose artwork is a print, or whose register row is gone, reports "already marked"
- **Where:** `apps/api/src/services/private-sale-deal/deal-mark-sold.service.ts:63,112`
- **Scenario:** the guard checks only `stage === 'settled' && artworkRegisterId`. `lock.markSold` returns `not_governed` for a print or a missing entry, and the code maps every non-`skipped`, non-`moved` status to `already_marked`. A direct POST therefore returns 200 and writes an `artwork_mark_sold_retried` event with `outcome: "already_marked"`, which the audit log then misstates. The UI never offers the button in this case, so the impact is limited to the API and the audit trail.
- **Fix:** map `not_governed` explicitly, either to `not_settled` (rename it to `not_applicable`) or to a distinct outcome, and test it.

### 5. LOW (perf): the nav count runs a full deal-list request on every admin page render
- **Where:** `apps/web/src/lib/admin/private-sales/private-sales-nav-count.server.ts:28`
- **Scenario:** for every person with private-sale read access, every admin layout render calls `GET /admin/private-sales?view=needs_attention&limit=1`. The API then runs the list query with 4 joins, `countByStage`, and `listSettlementFollowUps` returning up to 500 rows. This runs per page load, outside the shared nav cache.
- **Fix:** add a dedicated `/admin/private-sales/attention-count` endpoint backed by the aggregate from finding 3, or a short per-user cache.

### 6. LOW: `canRetry` is true on urgent items, and the page is then not view-only
- **Where:** `apps/api/src/services/private-sale-deal/deal-settlement-follow-up.presenter.ts:46`; `apps/web/src/components/admin/private-sales/deal-view.tsx:86`
- **Scenario:** for an urgent item the API returns `canRetry: canDo(viewer,"manage")`, which is true for managers. The web view model ignores it, because `settlementNotice` forces `canRetry:false` for urgent. `deal-view` still reads the raw flag, so a manager on an urgent settled deal with no other actions gets a page that is not view-only and has nothing to act on. The contract says "this person may ask the register to mark sold again", which is false for urgent.
- **Fix:** in the presenter, `canRetry: severity === "normal" && canDo(viewer, "manage")`, and add a presenter test.

### 7. LOW (design note): severity rising from normal to urgent after the first raise is not re-raised
- **Where:** `deal-settlement-follow-up.service.ts:48`; marker keyed only on dealId
- **Scenario:** a deal is raised as normal on day 1. On day 3 Zoho records a gallery sale and the item turns urgent. The design (one event per deal) means no new event, metric or log line is emitted, so the only signal is the derived UI. This matches the approved design, but it is worth confirming that it was intended. A cheap option is to key the claim on `(dealId, severity)` so an escalation to urgent is audited once.

## Areas checked with no defect found

- **Permission/scope:** the route is guarded by `requirePrivateSaleDealsManage`, and the service re-checks with `canDo(manage)` and `canSeeDeal`. The server action checks `PRIVATE_SALE_DEALS_MANAGE_ACCESS`. `listSettlementFollowUps` applies `scopeConditions(viewer.scope)` (owned / stages / all), so the badge and bell counts cover only deals the person can list, and the integration test pins owned and stages scope. The nav count is per person and is not written to the shared nav cache. The bell needs manage access and the badge needs read access, which is consistent.
- **Register lock and idempotency:** Try again goes through the existing `ArtworkRegisterDealLock` → `ArtworkOfferLock.markSold` inside a savepoint. Optimistic version retries mean a double click, or a race with the settlement's own mark-sold, ends as `unchanged`/`already_marked`. An artwork held elsewhere or sold elsewhere returns `skipped` or `DealArtworkRefused`, and nothing is forced. Every attempt, including `failed`, is written to the audit log in the same transaction. The savepoint keeps a register DB error from aborting the audit insert.
- **Daily check claim:** `pg_advisory_xact_lock(hashtextextended('…raised:'+dealId,0))` followed by a SELECT on `domain_events` under the default READ COMMITTED isolation (`DrizzleTransactionRunner` sets none). The second caller's SELECT takes a fresh snapshot after the lock is granted, so it sees the first caller's committed event and exactly one event is written. The lookup is served by `domain_events_aggregate_idx`. Note: the integration test exercises the claim sequentially on one connection only; a two-connection concurrent test would pin the guarantee.
- **Audit/PII:** both events carry only `dealId`, `reference`, and `severity`/`outcome`. They are allowlisted in `EXCEPTION_PATHS`, registered with `piiClassification: "none"`, and labelled in `domain-event-labels.ts`.
- **Prints and unlinked deals:** excluded in both SQL (`kind='original'`, inner join on the register) and the domain rule, and the integration test covers both.
- **UI copy and states:** the normal notice is a warning with Try again and the settled date. The urgent notice is a danger notice with the register's own message and link, and the external link opens in a new tab with `noopener`. The list row label reads "Possible double sale" or "Not marked sold", and the empty state copy is fine. Minor: after an `artwork_unavailable` failure the inline failure text can repeat the register message that the refreshed urgent body now shows.
- **SOLID:** responsibilities are well separated: the domain rule, a reader, a marker port, a presenter, a command service, and a cron service. `PrivateSaleDealDesk` gains a fourth delegate interface. The `refusal(res, messageFor)` injection is clean.
- **Tests:** they are meaningful (truth-table-style domain test, scope test, clear-on-fix test, retry outcomes against a real lock). The gaps are the NULL-ref case (finding 1), the cap behaviour (findings 2 and 3), `not_governed` (finding 4) and the concurrent claim.

## Required before merge
1. Finding 1: NULL-safe predicate, plus a test proving the SQL and the domain rule agree.

## Recommended
2. Findings 2 and 3: an uncapped aggregate count; keep already-raised deals out of the check window or rank urgent first, and log truncation.
3. Findings 4 and 6: small fixes with tests.
