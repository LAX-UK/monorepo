## Behaviour checked (no defect found)

- **Order of buffered ops.** `on`, `off`, `emit`, `timeout().emit`, `io.on` and `io.off` go into one list in call order. They're replayed synchronously right after `io()` returns and before `real` is assigned, so nothing can interleave. `io()` doesn't connect synchronously, so every listener is in place before the first `connect` or `connect_error`. Correct.
- **Ack callbacks before connect.** The ack function is passed through in the args and replayed into socket.io's own `sendBuffer`. Same as before.
- **`off()` before load.** It's replayed in order, so `on(A); off(A)` ends with no listener and `join; leave` is sent as join then leave. That's the same as socket.io's pre-connect buffering. `off(event)` with no listener removes all listeners for that event, same as socket.io.
- **Handlers added during load.** They're recorded into `pending`, and `real` stays `null` until replay finishes, so none are lost.
- **Multiple subscribers.** Listener identity is kept, so a later `off(event, fn)` on the real socket removes the right one. Covered by a test.
- **Reconnect / rejoin.** After load every call passes straight through. `connect` listeners (`use-live-lot-bid`, `use-clerk-lot-live-price`, `saleroom-live-provider`, `socket-adapter`) re-emit join on reconnect as before. The `hadConnected = socket.connected` capture is `false` before load, just as it was while the old socket was connecting. Socket.IO's own Manager reconnection is untouched because `socket-connection.ts` keeps the same options.
- **Auth ticket (60 s, one-time).** `auth` is a callback that socket.io calls at handshake time, and it calls `resolveSocketHandshakeAuth()` → `POST /api/auth/ws-ticket` then. Nothing fetches the ticket before the chunk arrives, so a slow chunk load can't make the ticket expire. Each reconnect fetches a fresh ticket, as before.
- **Health indicator.** `socket.io.on("reconnect")` (clock re-sync), `reconnect_attempt` → "connecting", `connect` → probes, and `disconnect` → "offline" are all replayed. The latency probe only uses `timeout().emit` when `connected`, so it always goes straight through. `socket.connected` is `false` until load, so the initial state is "connecting", as before.
- **Reimplemented backoff.** `retryDelayMs` is the same formula as socket.io-client 4.8.3 `contrib/backo2.js`: `min=1000`, `factor=2`, `jitter=0.5`, `max=5000`, the same odd/even sign trick, and `attempt` is incremented before `reconnect_attempt`, so the first one reports `1` as Socket.IO does. It only runs while the chunk fails to load. Once the chunk is in, Socket.IO's own backoff takes over. See L1 and L2 for small differences.
- **SSR.** `getSocket()` runs during render: `RealtimeHealthProvider` and `LotPortsProvider` call it inside `useMemo`, and the saleroom hooks call it inside `useMemo` and default params. So it runs on the server too. Before this PR that called `io()` on the server synchronously. Now the server does the same thing through `import()`. This is a pre-existing behaviour (a module-level server socket per Node process with `{}` auth, since `resolveSocketHandshakeAuth` returns `{}` without `window`), not a regression. See I1.
- **HMR (dev).** Editing `socket.ts` resets the module singleton and leaves the old real socket alive, the same as the old `io()` singleton did. Editing `socket-connection.ts` has no effect after load. No new leak.
- **Typing.** `LiveSocket` exposes only `on/off/emit/timeout/connected/io.on/io.off`, and typecheck passes, so no caller uses `once`, `id`, `disconnect` or similar.
- **Lenis.** Untouched (no diff outside the socket files, docs and budget JSON).

## Findings

### M1 — Medium: if the socket chunk can't be fetched (deploy skew), live surfaces never connect and never recover without a manual refresh

Before: `socket.io-client` was inside each live page's own JS, so if the page rendered, the client was there.
After: the client is a separate content-hashed chunk fetched when a live surface first mounts. There's no skew protection: no `deploymentId`/`generateBuildId` in `next.config.ts` and no `ChunkLoadError` handler anywhere in `src`. That opens this path:

1. A bidder opens a non-live page, or any page under build A. Next prefetches the lot or sale route JS.
2. A deploy replaces the app instances, and build A's `98870.<hash>.js` now 404s.
3. The bidder client-navigates to the lot or sale page. The route JS is already cached, so Next's hard-reload-on-ChunkLoadError doesn't fire. The page mounts, `getSocket()` → `import()` → 404.
4. The facade retries forever (1–5 s). Every retry 404s. The health dot shows **"connecting"** indefinitely, never "offline". Prices, the saleroom state and the lot-ended events stay frozen until the user reloads.

Marketing lot and sale pages don't mount `useUserNotifications` (only `workspace-shell` does), so for a public visitor or bidder on the marketing frame the chunk is typically first fetched when the lot or sale page mounts. That's exactly the risky step. Bids still go over HTTP and the server rejects bids that are too low, so this is stale live UI rather than wrong bids. That's why it's Medium, not High.

Suggested fix (small, inside `socket.ts`): after N consecutive `ChunkLoadError`s (say 3, which is about 5 s), do one guarded `window.location.reload()`, guarded with a `sessionStorage` flag so it can't loop. Alternatively, report the health state as "offline" with a refresh prompt. Optionally, also start `import("@/lib/socket-connection")` at idle on every page so the chunk is in memory before a deploy window.

### L1 — Low: after about 84 minutes of continuous load failure, about half of the retries fire with no delay

`retryDelayMs` computes `1000 * 2 ** attempt` with no cap before the jitter. From attempt 1016 onward `ms` is `Infinity`, and the "minus" branch yields `Infinity - Infinity = NaN`. `Math.min(NaN, 5000)` is `NaN`, and `setTimeout(fn, NaN)` fires right away. I measured it: the first bad attempt is 1016, and 47 of 86 attempts after that are bad, roughly 84 minutes in at the 5 s cap. The result is a near-busy loop of `import()` attempts and `connect_error`/`reconnect_attempt` callbacks in a tab left open while the chunk can't be fetched (offline laptop, M1).

socket.io-client 4.8.3 has the same arithmetic (`Math.min(ms, max) | 0` turns NaN into 0), so this matches upstream "exactly", latent bug included. It still costs nothing to fix in the facade: cap `attempt`, or compute `Math.min(ms, max)` before the jitter.

### L2 — Low: facade failure events differ slightly from Socket.IO's

- The facade emits the manager's `error` and the socket's `connect_error` on every failed load, and `reconnect_attempt` before each retry. Socket.IO emits `reconnect_error` (not `error`) for failed *re*connects. It never emits `reconnect` or `reconnect_failed` for the chunk phase.
- No current caller listens to `connect_error`, `error` or `reconnect_error`, and `reconnect` (clock re-sync) correctly doesn't fire for the first connect. So there's no behaviour change today. Worth a comment so a future listener doesn't assume full parity.

### L3 — Low: `timeout(ms).emit` recorded before load starts its timer at replay, not at the call

The ack timeout effectively becomes `ms` plus the chunk load time. The only `timeout()` user (the latency probe) runs only when `connected`, so it's never buffered. No current impact. Document it, or reject buffered timeout-emits with an error.

### I1 — Info (pre-existing): a server-side socket is opened during SSR

The health adapter, lot ports and saleroom hooks call `getSocket()` during render, so the Next server process opens an unauthenticated WS client to `NEXT_PUBLIC_WS_URL`. That already happened before this PR (`io()` was called on render). The PR keeps it as it was; it's not a regression. It's a candidate for a `typeof window === "undefined"` no-op facade in a follow-up.

### I2 — Info: `pending` grows without bound while the chunk can't load

Each mount and unmount of a live card adds `on/off/joinLot/leaveLot` ops with their ack closures. On success they're all replayed, and the server receives a burst of join/leave pairs. This matches socket.io's own unbounded pre-connect `sendBuffer`, so it's the same as before. It only matters together with M1 or L1.

### I3 — Info: the tests don't cover two edge cases

There's no test for L1 (many failures) or for the deploy-skew 404 path in M1. There's also no integration test that runs a real caller (for example `useLiveLotBid`) against `createLazySocket` with a fake loader. All caller tests mock `getSocket`.

### Verdict: FIX FIRST

The facade is careful and correct for the normal path. Ordering, acks, `off`-before-load, listener identity, the ticket timing and socket.io's own reconnection are all preserved, and the bundle goal is met (socket.io-client is out of the first-load JS of home, lot and sale). It's held back by one thing on a live-bidding path: **M1**. A chunk that can't be fetched (most realistically right after a deploy) leaves lot and sale pages silently stuck on "connecting" with stale prices and no automatic recovery. That's a failure mode that didn't exist before. Add a bounded fallback (a guarded reload, or "offline" plus a refresh prompt, after a few `ChunkLoadError`s) and preferably the L1 cap in the same change. With that, and with checks 1–9 passing on test.lax.bid, this is a SHIP.

### L1: backoff could reach zero delay. Fixed in `1384710d`

- The exponent is capped at 8. 1 s × 2³ already passes the 5 s ceiling, so the first retries are unchanged and still match `backo2`. The result is clamped to at least 500 ms, so a retry can never fire with no delay or with a `NaN` delay.
- Evidence: `retryDelayMs` "never returns a zero, NaN or out-of-range delay…" covers attempts 0–3000 × 9 random values. With the cap removed it fails at **attempt 1015** (`0 * Infinity = NaN`). "matches Socket.IO's default backoff" pins 1000/2000/4000/5000 and 1495. A facade-level test (I3) runs 1200 consecutive failures and checks that every scheduled delay is between 500 and 5000 ms.

### L2: failure events now match Socket.IO's. Fixed in `f553b8aa`

- I checked this against the `socket.io-client` 4.8.3 Manager source (`open` → `onError`, `reconnect()`). Every failure emits the manager's `error(err)` and the socket's `connect_error(err)`. A failed *retry* also emits `reconnect_error(err)`, after the next retry is scheduled, which is the same order as upstream. `reconnect_attempt(n)` fires before each retry. When the client finally loads after failures, `reconnect(n)` fires on the real manager's first `open`, which is when Socket.IO fires it. It doesn't fire if the real manager has started its own reconnection by then, and it doesn't fire when the first fetch succeeds. `reconnect_failed` is never emitted, because retries never stop, which matches the default `reconnectionAttempts: Infinity`. The payloads are the same `Error` and attempt number. This is documented in the `socket.ts` header and the budgets doc.
- Evidence: "raises the same events, in the same order and with the same arguments, as Socket.IO" checks the exact sequence `error, connect_error, reconnect_attempt 1, error, connect_error, reconnect_error, reconnect_attempt 2, reconnect 2`. Two more tests cover the two cases where no `reconnect` fires. The ordering test fails on the pre-fix code.

### L3: `timeout(ms).emit` before load. Fixed in `996d05bc`

- These are now socket.io's semantics, where the timer starts at `emit` even while disconnected. The deadline is set at the call. If the client is still loading at `ms`, the ack gets `Error("operation has timed out")` and the message is removed, so it's never sent. If the client arrives first, only the time left goes to `socket.timeout(left).emit`.
- Evidence: "counts the ack timeout from the call…" (2000 ms call, client after 1500 ms → `timeout(500)`) and "times the ack out on schedule while the client is still loading, and never sends it". Both fail on the pre-fix code.

### I2: pending buffer is now bounded. Fixed in `2c6f5437`

- Policy: listener ops are kept as their net effect. `off(e, fn)` cancels the first buffered `on(e, fn)`, which is the emitter's first-match rule, and a bare `off(e)` cancels all of them. A bare `io.off(e)` is kept, but only the latest one, because it also removes Socket.IO's own manager listeners. Messages are capped at `MAX_PENDING_EMITS = 100`, and the oldest is dropped first. A dropped `timeout().emit` ack times out at once. A dropped plain ack is never called, as in Socket.IO for a message it never sent. Callers re-join on `connect`, so only stale join/leave churn is lost. Failure notices are now derived from the buffer, so the separate listener mirrors are gone.
- Evidence: there are 4 tests under "the buffer while the client is loading". One runs 1000 mount/unmount cycles: on arrival there's 1 listener op and exactly 100 emits, ending with the newest `joinLot`. The others cover the overflow ack behaviour, emitter-equivalent cancellation and listener order, and the bare `io.off`. All 4 fail on the pre-fix code.

Ad-blocker false 404: would reload once, then the 10-min guard holds it to the "paused" notice (bounded, and `98870`-style names don't match filter lists). **Safari private mode (no sessionStorage):** `storage()` throws → caught → null → `claimReload` returns false → the reload never fires, so no loop; the "paused" + Refresh notice is the fallback. Correct, conservative behaviour.
  - *SSR:* `socket.ts` statically imports the `.client` module, which is evaluated on the server, but it has no top-level `window`/`navigator`/`sessionStorage` (all inside function bodies) and the server branch of `getSocket()` passes `{}`, so no recovery is wired server-side. Safe.
  - *Double connections / leaks:* `start()` guards on `loading || real`; `createSocketConnection` runs once. `scheduleRetry` removes its `online` listener on fire; `reportReconnectOnOpen` removes both its manager listeners on either firing. No leak found.
- **L1 (backoff zero/NaN delay) — FIXED.** Exponent capped at 8 and the result floored at 500 ms. Removing the cap makes `retryDelayMs` "never returns a zero, NaN or out-of-range delay" and the facade "keeps every retry ≥500 ms through >1000 failures" fail (NaN at attempt 1015). *Nit:* the 500 ms floor itself has no test that reverts red (the cap alone prevents the NaN); belt-and-suspenders, not a defect.
- **L2 (failure events vs socket.io-client 4.8.3 Manager) — FIXED.** Verified against `node_modules/socket.io-client/build/cjs/manager.js`: every failure emits manager `error` then socket `connect_error`; a failed *retry* also emits `reconnect_error` (after scheduling the next attempt); `reconnect_attempt(n)` fires before each retry; `reconnect(n)` on the eventual open, suppressed if the real Manager already began its own reconnection. The facade's `start()` error order and `reportReconnectOnOpen` match this exactly. Mutations (drop `reconnect_error`, drop `reportReconnectOnOpen`, swap `error`/`connect_error`) each fail the "same events, same order, same arguments" test. *Nit:* the `reconnect_attempt` listener cleanup in `reportReconnectOnOpen` has no test that reverts red (a latent, harmless listener-leak guard).
- **L3 (`timeout(ms).emit` buffered before load) — FIXED.** Deadline is captured at the call; on replay only the time left is passed, and if the client is still loading at `ms` the ack gets `operation has timed out` and the message is dropped (never sent). Mutations (use full `ms` at replay; keep the timed-out emit in the buffer) each fail their tests.
- **I2 (buffer policy) — FIXED as designed, with one new gap (N1 below).** `off(e, fn)` cancels the first buffered `on(e, fn)`; bare `off(e)` cancels all; bare `io.off(e)` keeps only the latest; emits capped at `MAX_PENDING_EMITS = 100`, oldest dropped first (a dropped `timeout().emit` acks `operation has timed out` at once; a dropped plain ack is never called). Mutations (no cap; `off` removes all matches; keep every bare `io.off`; keep bare socket `off`) each fail their tests. ### New finding

#### N1 — Low (new, introduced by the I2 cap): the 100-emit cap can silently drop `joinUser`, which is never re-sent on connect

`useUserNotifications` (used by `use-unread-notifications` in `workspace-shell` and by the notifications inbox) emits `joinUser` **once** on mount and has **no `connect` listener** — unlike every lot/sale caller, it does not re-join on (re)connect. The I2 buffer caps emits at 100 and drops the **oldest** first. Because the notification hooks mount with the shell, `joinUser` is typically the *first* buffered emit, so on overflow it is the first dropped — and nothing re-sends it. Result: the user silently stops receiving live outbid/notification events (inbox + unread count) until that component remounts. Reproduced with a probe: `joinUser` + 51 lot-card mount/unmount pairs (103 emits) buffered before the client resolves → `joinUser` dropped, 0 of 100 surviving emits are it.

This contradicts the I2 note that "only stale join/leave churn is lost" — true for `joinLot`/`joinSaleroom` (re-joined on connect), **not** for `joinUser`. Severity is **Low**: the trigger is narrow (needs ≥100 emits buffered *before* the chunk loads, i.e. heavy lot-card churn during an unusually slow chunk load), it affects live notifications only (never bids or prices), and in the deploy-skew path the page reloads and re-buffers fresh. Not a release blocker, but a real new correctness gap. Fix options: exempt `joinUser`/`leaveUser` from the drop (keep user-room ops), or add a `connect` re-join to `useUserNotifications`.

*Related, pre-existing and out of scope:* `useUserNotifications` also does not re-emit `joinUser` on a genuine WS reconnect (the socket drops and reconnects). The PR does not touch that hook, so this is not introduced here, but the same follow-up (a `connect` re-join) would close both.
