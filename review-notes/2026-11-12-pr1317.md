# Review: PR #1317, re-offer PR 7 (seller agreement in the LAX Bid workspace)

Branch `bs1-reoffer-seller` @ 49999935, reviewed against `origin/main`. Reviewed for money, security and design. The PR branch was not changed.

## Verdict: FIX FIRST

The PR is mostly sound. Identities are never shared, cross-organisation reads are not found, answering is checked on the server and is a signed-in POST, and every date goes through `@auction/datetime` in London time. Three things should still be fixed before merge:

1. The proceeds panel says its figures come from the consignment agreement and include VAT. They don't, and they won't match the eventual payout.
2. Viewers and consignors can see the seller's proceeds. Everywhere else, only members with `entity.payouts.read` can.
3. An overdue request stays in Needs you indefinitely, because no job lapses it yet.

## Must fix

### F1. The proceeds panel says "commission and VAT, from your consignment agreement", but the figure is neither (money)

- **Where:**
  - `apps/web/src/lib/seller/seller-reoffer.vm.ts:288-302` (`moneyOf`: the "Commission and VAT on it" row and the "Estimated from your consignment agreement" note)
  - The data comes from `apps/api/src/container/create-reoffer-services.ts:84-87`.
- **What happens:**
  - `proceedsPence` = `hammer − round(hammer × legal_entity.platformFeeBps)`, which defaults to 500 bps.
  - It never reads `consignment_agreement.commission_percent`, the rate the seller actually signed, and it adds no VAT.
  - Settlement works differently. `create-pending-for-winner.pipeline.ts:298` and `lot-invoice-initiation.service.ts:190` take the fee from the buyer's payment total (hammer + premium + VAT), and `saleLineBreakdown` then gives net = payment amount − fee.
  - So the "Estimated proceeds" shown here does not match what Sold & payouts will later show for the same sale.
- **Example:**
  - An agreement at 15% commission + VAT, offer £82,000.
  - The page shows "Commission and VAT on it −£4,100.00" and "Estimated proceeds £77,900.00".
  - Under the signed agreement the seller would expect about −£14,760 (15% + 20% VAT).
  - The settlement path computes something different again.
  - The seller agrees to the re-offer based on this number (RA "price + what you receive").
- **Fix (both parts):**
  - (a) Make the copy honest now: label the row "LAX fees" and drop the "VAT" and "consignment agreement" wording.
  - (b) Better: compute `proceedsAtOffer`/`proceedsAtOriginal` from one shared function, the one settlement uses, fed by the lot's consignment agreement. That needs an owner decision on whether settlement or the agreement rate is the source of truth.
  - Add a test that pins the estimate to the settlement net for the same hammer.
  - The PR says "No money rule changed", which is true, but this PR is the first to show these numbers to sellers under that label.

### F2. Viewers and consignors see the seller's proceeds (security / data exposure)

- **Where:**
  - `apps/api/src/services/reoffer/reoffer-reads.service.ts:87-89` lets anyone with `entity.consignments.read` read the view. That includes **viewer** and **consignor**.
  - The view carries `estimatedProceedsMinor`, `originalProceedsMinor` and `originalHammerMinor`.
  - `seller-reoffer.vm.ts:153,167` (`showMoney: true` in `waiting`/`agreed`) shows the "What it means for you" panel whatever the viewer's role.
- **Policy it breaks:** `entity-capabilities.ts` allows `entity.payouts.read` for owner, admin and finance only ("consignors therefore see sales, not payouts"). `SoldAndPayoutsService.canRead` enforces exactly that.
- **How to reproduce:**
  - Sign in as a viewer of the seller organisation.
  - Open `/selling/payouts/offers/<id>`. Record pages bypass `workspacePageRefusal`, and the API returns 200.
  - The panel shows the seller's commission and net proceeds.
- **Fix:**
  - In `sellerView`, null out the proceeds fields, or return a narrower schema, unless `entityActorCan(actor, "entity.payouts.read")`.
  - In the view model, show the money panel only when those fields are present.
  - Add an API test (viewer/consignor gets no proceeds fields) and a view-model test.

### F3. An overdue request stays in Needs you indefinitely

- **Where:** `packages/persistence/src/repositories/drizzle-needs-you-facts.reader.ts:243-269`. It filters on `status = 'requested'` and `lot_reoffer.status = 'awaiting_seller'`, but not on `due_at`.
- **Why that matters:**
  - Nothing moves a request to `seller_lapsed`. There is no re-offer job in `apps/worker`, and the "clock" mentioned in `reoffer-consent.service.ts:163` and `seller-reoffer.vm.ts:80` does not exist yet.
  - The API correctly refuses a late answer with `consent_window_ended` (silence is never yes, which holds).
- **What the seller sees:** after 17:00 on day 3, Home keeps showing "May we offer X to the next bidder? … answer by Fri 13 Nov, 17:00" with "Review and answer", and the Consignments count stays up. The page itself says "This request has closed".
- **Fix:**
  - Add `or(isNull(sellerConsent.dueAt), gt(sellerConsent.dueAt, now))` to the reader, passing `now` in from the service.
  - Or ship the lapse job in the same release.
  - Add an integration test with a past `due_at`.

## Verified OK

- **Identities:**
  - `sellerReofferViewSchema` is `.strict()` and has no bidder, user or hidden-max fields.
  - The integration test checks the JSON for the IDs and names of the second bidder and the buyer.
  - `answeredBy` hides the staff-only `house_stock` channel, and the validator rejects it.
- **Price** is `offerMinor` from the consent terms snapshot (the underbidder's placed bid, chosen in the start service). It is never the hidden maximum. This PR does not change it.
- **Other organisations:**
  - Reads filter on `sellerLegalEntityId`, so another organisation's request is not found.
  - The answer re-checks `lot.sellerLegalEntityId` under the row lock.
  - The Needs you reader is scoped to the legal entity, and the integration test covers `otherSeller`.
- **Only owners and admins can answer, on the server.** `answerInWorkspace` checks `entity.consignments.after_sale`, and impersonation is passed through. The web `canAnswer` only hides the buttons.
- **Answering is a signed-in POST only.** The server action posts to `/legal-entities/reoffer-requests/:id/answer`. There is no GET that answers, so email links only open the page.
- **Stale or closed requests:** the settled codes close the sheet, show a toast and refresh, so the seller is never offered a second try. Locally, a past `answerDueAt` reads as "No reply".
- **Consent window:** 3 working days ending at 17:00 London (`sellerConsentWindow`). Dates are formatted with `formatWhen`/`formatWeekday`/`formatDayMonth` from `@auction/datetime` in `LONDON_TIME_ZONE`.
- **Integer pence:** the view model works in minor units and only divides by 100 when formatting.
- **LAX-owned stock:** `not_needed` is left out of the list and gets a "Nothing to answer" state on the page.
- **Needs you:** a single table row, counted under Consignments; one request links to its page and several link to Sold & payouts. Consignor, viewer and finance are excluded, and the reader is not even called for them.
- **Design:** the states live in one table (`STATES`), so a new state is a new row. Loader, action, view model and components are cleanly separated, and the API change adds fields only.
