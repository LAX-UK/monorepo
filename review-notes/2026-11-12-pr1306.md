# Review: PR #1306 `books2-accounting-tables` (migration 0368 and repositories)

- Date: 2026-11-12
- Branch head reviewed: `9fa5bb87` ("Accounting: persist documents, history and the source switch (migration 0368)"), on `origin/main` `fd4738b4`.
- Scope: money and database. The PR branch was not changed.

## Verdict: FIX FIRST

Most of the PR holds up under test:

- **The queue never hands out a document twice.** 12 concurrent claimers took 300 documents, with no duplicates and no errors.
- **An expired lease always becomes `unknown`.** It is never handed out again.
- **A state change and its history row are written together.** Making the history write fail rolled back the claim.
- **History is append-only for every role.**
- **The grants and the seed are right.**

Three things should be fixed before merge. All are small.

- **D1 (Medium).** One CHECK has a NULL hole. An `issued` row can carry a totals mismatch, which is a state the domain cannot express.
- **D2 (Medium).** The database does not require `provider` on a row that has been, or may have been, sent. Lookup-before-retry depends on knowing which provider to ask.
- **D3 (Medium, merge order).** Together with PR #1305, the build breaks, and storage refuses most partial credit notes.

D4 (the claim ignores the source switch) must be settled before any runtime is wired to `claimNext`. It can go in this PR or in the runtime PR.

## Findings

### D1. Medium: `accounting_document_mismatch_ck` lets an `issued` row carry a mismatch

- **Where:** `packages/db/drizzle/0368_accounting_tables.sql:92`:
  `("mismatch_field" IS NULL OR ("provider_id" IS NOT NULL AND "review_lookup" = 'clear'))`.
- **Cause:** on an `issued` row, `review_lookup` is NULL. So `"review_lookup" = 'clear'` is NULL, the whole expression is NULL, and a CHECK passes on NULL.
- **Probe:** this was inserted as the owner and **accepted**:

  ```text
  state='issued', provider='books', provider_id='z1', provider_number='N1',
  mismatch_field='netPence', mismatch_difference_pence=1
  ```

  `parseRecord` ignores `mismatch` for `issued`, so the row loads as a clean `issued` document with the mismatch hidden in its columns.
- **Impact:** a document whose totals disagree with the provider can sit in `issued`, the final state, and nobody reviews it. That is the H2 protection bypassed at the storage level.
- **Fix:** write it as `"review_lookup" IS NOT DISTINCT FROM 'clear'` (or `coalesce("review_lookup", '') = 'clear'`). Add this exact row to the "refuses illegal rows" integration test. Also re-read every other `=` against a nullable column in the CHECKs. I found no other hole: `settle_ck` and `review_ck` are covered by the `IS NOT NULL` pairings.

### D2. Medium: `provider` is not required on rows that were or may have been sent

- **Where:** `0368_accounting_tables.sql:58` (`accounting_document_provider_ck` only limits the values) and `:66-74` (`provider_id` implies `provider`, but `sending` and `unknown` have no rule).
- **Probe:** these rows were inserted as the owner and **accepted**: `state='sending'` with `provider` NULL, and `state='unknown'` with `provider` NULL.
- **Why it matters:**
  1. Lookup before retry is only safe if the lookup goes to the provider the first request went to.
  2. If `provider` is NULL, or is overwritten, the runtime has to guess, typically "whatever is live now".
  3. Suppose the switch flipped in between. The new provider answers `not_found` and the document is requeued and sent again, while the first copy may exist in the old provider. That breaks "never create a document twice".
  4. The work queue does set `provider` on claim (`persistMove`, `move.provider`), so the repositories are right today. The database just does not hold the rule.
- **Fix:**
  - Add a CHECK: `"state" NOT IN ('sending', 'unknown', 'issued') AND NOT ("state" = 'needs_review' AND "review_lookup" = 'owed') OR "provider" IS NOT NULL`.
  - Have the lookup path read `stored.provider`, never the switch. Say so on `IAccountingDocumentTransitions`.
  - Consider refusing a claim by a *different* provider for a document that has been sent before (`attempts > 0`) unless its last outcome was a definitive `failed`.

### D3. Medium (merge order): conflicts with PR #1305

- **Where:**
  - `packages/persistence/src/lib/accounting-document-row.ts:125` calls `parseRecord(recordInput(row))`.
  - `packages/persistence/src/lib/accounting-document-payload.ts:36` requires each stored line's VAT to equal `buildLine`'s exclusive VAT.
- **Probe:**
  1. A scratch merge of `books1b-accounting-domain-followups` into this branch fails to build: `TS2554: Expected 2 arguments, but got 1` (#1305 makes `parseRecord(row, nowMs)` required).
  2. With that patched locally, `readDocumentPayload` accepts a 6p credit note but refuses 3p and 501p credit notes with "a line's VAT differs from the rule". #1305 makes credit lines tax-inclusive.
- **Fix:**
  - Whichever PR merges second passes `this.clock.now().getTime()` into `rowToRecord`. That means threading the clock into `rowToStored` and the reader.
  - Validate credit-note lines with the domain's own rule instead of `buildLine`.
  - Best: have the domain export one `parseDocument(row)` and call it here, so the storage layer stops re-implementing line rules. See the #1305 notes (F1–F3), because the credit-note VAT rule is still moving.

### D4. Medium (before any runtime): the claim ignores the source switch and the product

- **Where:**
  - `packages/persistence/src/repositories/accounting/drizzle-accounting-document.work-queue.ts:49-62`: the query selects any product.
  - `packages/persistence/src/interfaces/accounting.ts:99-104`: `ClaimRequest` has `provider` but no products.
- **Scenario:**
  1. The seed has Bid on Xero live and Books off.
  2. A Books worker calls `claimNext({provider: "books"})`.
  3. It receives the oldest Bid document and stamps `provider='books'` on it. Nothing in this PR stops that.
  4. When the runtime sends it, the same Bid invoice may be written to Books while the existing Xero path writes it to Xero. That is two live sources for one product.
- **Fix:**
  - Either have `claimNext` take the products it may serve and filter on them, or join `accounting_source_setting` inside the claim transaction (`FOR SHARE`). Hand a document to provider *P* only where P's mode for that product allows a send (`dry_run` hands out nothing that calls a provider, `test_org` only to a test organisation, `live` only to the live source).
  - Add an integration test: Bid on Xero live means a Books claim gets nothing.

### L1. Low: `worker_app` has table-wide UPDATE on `accounting_document`

- **Where:** `packages/db/src/migrate-roles.ts:1163-1165`.
- **Detail:** the worker can rewrite `payload`, the totals, `product` and `lax_reference` of any row, including an `issued` one. The CHECKs keep totals internally consistent but not equal to what was sent.
- **Fix:** grant column-level `UPDATE (state, attempts, lease_token, lease_expires_at, settles_at, review_lookup, needs_review_reason, provider, provider_id, provider_number, pdf_ref, mismatch_field, mismatch_difference_pence, last_error_class, updated_at)`. Add a role-contract assertion that `UPDATE … SET payload` is refused.

### L2. Low: `api_app` has UPDATE on `accounting_source_setting` before any route uses it

- **Where:** `migrate-roles.ts:997-999`.
- **Fix:** grant it with the staff route that needs it, as column-level `UPDATE (xero_mode, books_mode, updated_at, updated_by)`.

### L3. Low: the reference CHECK is looser than the domain

- **Where:** `0368_accounting_tables.sql:43` (`[a-z0-9_-]{1,64}`).
- **Detail:** the domain requires the first character to be a letter or digit (`/^[a-z0-9][a-z0-9_-]{0,63}$/`). Probe: `LAX-SHOP-INV-_a` is accepted by the database.
- **Fix:** use `[a-z0-9][a-z0-9_-]{0,63}`.

### L4. Low: totals CHECK does not mirror `zero_total` or contacts

- **Where:** `0368_accounting_tables.sql:52-54`.
- **Probe:** a zero-total invoice and a contact with totals of 100/20/120 are both accepted.
- **Fix:**
  - `("kind" = 'contact') = ("gross_pence" = 0 AND "net_pence" = 0)`. A contact's `expectedTotals` is all zeros, and every other kind is refused at zero by the domain.
  - For `payment`, require `vat_pence = 0`.

### L5. Low: the rollback drops the duplicate guard with no check

- **Where:** `packages/db/drizzle/0368_rollback.sql`.
- **Detail:** today this is fine, because it is dry run and the comment says so. Once any row has a `provider_id`, or is `sending`, `unknown` or `needs_review`, dropping the table loses the only record that the provider already holds a document. A later re-run would then create it again.
- **Fix:** start the rollback with a `DO` block that raises if any such row exists, with a message pointing to the runbook.

### L6. Low: the upgrade test still pins the last journal entry

- **Where:** `packages/db/src/migration-main-upgrade.integration.test.ts:26` (`FINAL_FOLDER_MILLIS`, used at `:64` and `:1235`).
- **Detail:** this is a main pattern that the PR bumps, as earlier PRs did. Every concurrent migration PR conflicts on it, and a stale value fails CI after a rebase.
- **Fix:** derive the value from `_journal.json` (`Math.max(...entries.map(e => e.when))`).

### Info

- **A refusal can still commit.** `persistMove` (`accounting-document-move.ts:94-122`) and the registry return a `bad_stored_document` or `bad_document` refusal *after* writing, so the transaction commits. Example: a claim whose updated row fails `rowToStored` leaves the document `sending`, and the caller sees a refusal. It is fail-closed (the lease lapses into `unknown`, then a lookup), but it could cycle. Consider throwing inside the transaction instead.
- **`MAX_LAPSED_PER_CLAIM`.** `claimNext` returns `null` after settling 100 lapsed leases, even when pending work exists. That is fine, but worth a log line.
- **The seed's Bid "live".** It is correct for today, but nothing reads this table yet. The runtime PR must not read `bid.xero = live` as permission for the new pipeline to write Bid documents to Xero alongside the existing finance path.

## What is good

- The CHECKs give one shape per status, and the probes found only the D1 NULL hole. A lease exists exactly when the row is `sending`. A provider document appears only on `issued` or `needs_review/clear`. A settle time exists exactly when a lookup is owed. A mismatch is never zero.
- Every move goes through the pure domain function on a row locked `FOR UPDATE`, in one transaction with its history row. A lookup that changes nothing writes nothing.
- The append-only trigger covers the owner and TRUNCATE. Together with `ON DELETE RESTRICT`, history cannot be lost by accident.
- The tests are honest: they run as `worker_app`, include concurrent claimers and simultaneous transitions, and bypass the repository to prove the database holds each rule on its own.
