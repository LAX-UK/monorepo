# Review: PR #1309, signed-in devices list (plan PR 4, SD11–SD13)

Branch `account/signed-in-devices-list` @ e13718d0 vs `origin/main` @ a2dd250a. Reviewer: independent security and design review. The branch was not modified.

## Verdict: FIX FIRST

Two small fixes are needed. Isolation between people holds: the list returns only the caller's own records, and no one else's data or token identifiers reach the API payload. The problems are a side effect on new-device security emails and a too-broad definition of a "live" token.

## Must fix

### 1. Renaming "Unknown device" to "Unknown browser" changes every known-device fingerprint for unrecognised agents, which sends spurious "new sign-in" emails
- `packages/identity-contracts/src/device-label.ts:13` changes the fallback label.
- `apps/auth/src/services/known-device.ts:32` hashes `formatDeviceLabel(userAgent)` into the known-device fingerprint (`security-notice.service.ts:228`).
- **Scenario:** a person has signed in before from an agent the parser does not recognise (null UA, an in-app webview, curl-like or custom UA), and has other devices on record. After deploy, the next sign-in from that same agent hashes `...\nUnknown browser\n<region>`. That fingerprint was never seen, so `isNewDevice` is true and a "new-device-login" email goes out for a device they already use. The email is rate limited per day, but each affected person still gets a false security alert, and the 90-day memory for that device is reset. The new wording also reaches the security notice's `deviceLabel` (`security-notice.service.ts:94`) and the data-request and subject-export views, which were not part of the approved list copy.
- **Fix:** keep the fingerprint input stable. Either give `fingerprintDevice` its own label function, or pass a fixed fallback such as `formatDeviceLabel(ua, { unknown: "Unknown device" })`. Alternatively, keep the contract function as it was and substitute "Unknown browser" only in `account-sessions.vm.ts`. Add a test that pins `fingerprintDevice({userAgent: null, ...})` to its value before this change.

### 2. Products count rotated-out (consumed) refresh tokens as live
- `apps/auth/src/infrastructure/drizzle-identity-session-repository.ts:58-66`: the filter is `refresh_token_expires_at > now()` only.
- Rotation keeps the predecessor row with `refresh_consumed_at` set and its original refresh expiry (`drizzle-refresh-token-family-repository.ts:88-92`). Introspection already treats such a row as inactive (`oauth-token-management.service.ts:115-118`).
- **Reproduced** on Postgres 16 with a throwaway probe test (not committed): one token for LAX Bid under the sign-in, with `refresh_consumed_at` set. `listForSubject` still returns that product in `clientIds`.
- **Real path:** a product revokes its current access token with `token_type_hint=access_token`. `revoke` then calls `deleteToken(row.id)` on the successor only (`oauth-token-management.service.ts:79-83`). The consumed predecessors stay, so the browser keeps showing "LAX Bid" until the original refresh expiry, up to the refresh lifetime. This contradicts SD13 ("products from live, unexpired tokens").
- **Fix:** add `isNull(oauthAccessToken.refreshConsumedAt)` to the `where`, and add an integration case for a consumed row.

## Should fix (non-blocking)
3. **Data minimisation in the payload** (`account-identity.service.ts:138`, contract `account-sessions.ts:66`). `products` carries every client id with a live token, including staff and mobile client ids such as `lax-shop-admin`. These are the caller's own, and LAX Account filters them to the four public products server-side (`deviceProductNames`), so neither the raw ids nor anyone else's data reaches the browser. Filtering to `DEVICE_LIST_PRODUCTS` client ids on the issuer side would stop internal client ids leaving the sign-in service at all. A low-risk change.
4. **Country names** (`apps/account/src/server/domain/account-sessions.vm.ts:47`) use `Intl.DisplayNames(["en"])`. The address book already has `countryName` in `account-addresses.vm.ts:134` using `en-GB`. Reuse that helper (keeping the `name !== code` guard) so a country reads the same everywhere in Account.
5. **The "signed out everywhere else" notice** (`signed-in-devices-list.client.tsx:143`) counts `sessions.others.length` from the page as it was rendered. That count is only used to choose singular or plural, which is fine, but the server's own result message is no longer used. Worth confirming that the approved copy wants a message built on the client.

## Checked and OK
- **Caller-only scoping.** The subject comes from the verified bearer (`authenticateAccountCaller`), and `sid` must be a live sign-in of that subject (`RecentSessionGuard.findLive`). Sessions, lineage and tokens are all filtered by `user_id = subject`. Probes run on Postgres:
  - Ben's token naming Ann's sid is ignored (covered in the PR's integration test).
  - A lineage row owned by Ben that names Ann's session as successor is not followed: `previousIds=[]`, `clientIds=[]`.
  - There is no staff impersonation concept in the auth service, so a staff session cannot widen the subject.
- **No token or IP leak.** The route still picks fields one by one (`account-identity.routes.ts:141-152`). No token, refresh hash, IP address or other person's identifier is added.
- **Contract v2 compatibility.** `deviceKind`, `country` and `products` all default, so new Account parses old auth (the v1 gateway test passes). Zod strips unknown keys, so old Account parses new auth. A bad country, or a device kind other than laptop/phone/tablet, fails the parse. The issuer only stores `normaliseCountry` output (`^[A-Z]{2}$`, excluding XX/T1), so that failure cannot happen from stored data.
- **Country derivation.** It comes from the edge headers `cf-ipcountry` / `x-vercel-ip-country`, normalised at write, and is a code only, never an address. It is display-only for the person's own row. Note: a spoofed header outside the edge only affects the person's own label.
- **Step-up and sign-out.** The revoke routes and the services they call are untouched. The confirm dialogs only gain `loadingLabel: "Signing out…"`.
- **PII in logs.** No new logging in the diff.
- **Dates.** They go through `@auction/datetime` (`formatWeekday`, `formatDayMonth` via `lib/format-date.ts`), with relative age under 7 days and "Active now" under 15 minutes. There is no raw `toLocale*` call.
- **UI states.** List, one, many with "Show N more", none ("You're not signed in anywhere else."), working, error, success, sign in again and unavailable all keep their paths. The icon is decorative (`aria-hidden`), and Sign out keeps its `aria-label`.
- **Copy.** The approved SD copy table is not in the repo or the PR. The strings were checked against the PR description and the plan's wording as summarised there. Verbatim match with the table is unverified.
