# Review: PR #1293 deal page Artwork section (pd3-private-deal-artwork-section)

- **Reviewer:** independent automated review, 2026-11-12

## Verdict: **FIX FIRST**

The core mechanics are correct and well built:
- One transaction holds the new artwork and releases the old one.
- Refusals roll everything back.
- Optimistic versions guard the deal row.
- Stage rules live in the domain and the server enforces them.
- The Agree guard is wired in.

Two issues need fixing before merge, both small:
1. **(M1)** The new audit table is not append-only, unlike its sibling history tables.
2. **(M2)** A recorded "not in the register" reason can be rewritten after Agreed, with no staff reason. This goes against the approved rule that the artwork is fixed from Agreed.

## Findings

### M1 (Medium): `private_sale_deal_artwork_history` is mutable, so audit integrity is not enforced
- **Where:** `packages/db/drizzle/0363_private_sale_deal_artwork_history.sql:5-22`. The schema doc at `packages/db/src/schema/private-sale-deal.ts:~224` says "Append-only".
- **What:**
  - The sibling tables `private_sale_deal_stage_history` (0295, lines 195-213) and `private_sale_deal_party_history` (0329) both have a `BEFORE UPDATE OR DELETE` guard trigger. The new table has none.
  - `db:roles` gives `api_app` the default `ALL PRIVILEGES`. I checked this on PG16: after migrate and db:roles, `api_app` has `INSERT, SELECT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER`.
- **Scenario:** Any API code path, bug or SQL injection running as `api_app` can rewrite or delete who/when/why/before/after for an artwork change. The approved design requires this record to be the audit.
- **Fix:**
  - Add `private_sale_deal_artwork_history_guard()` and its trigger, mirroring 0295. Keep the one allowed UPDATE: `actor_user_id` set to NULL by the `ON DELETE SET NULL` FK, with every other column unchanged.
  - In `0363_rollback.sql`, drop the trigger and the function.
  - Extend `migration-0363-*.test.ts` and the repository integration test so an UPDATE or DELETE raises.
  - Optionally, put the table on an api_app INSERT/SELECT list, as is done for `API_PAYMENT_REFUND_TABLES`.

### M2 (Medium): the unlinked reason can be changed after Agreed, with no staff reason, and can undo the Agree guard
- **Where:** `packages/domain/src/private-sale-deal/artwork.ts:60-65` (`planDealArtworkMove`, the `!held` branch). Also affected:
  - `apps/api/src/services/private-sale-deal/deal-artwork.service.ts:134` (only `change` requires a note)
  - `deal-query.service.ts` `artworkAccessOf` (`canLink` is true at agreed through released when nothing is linked)
- **What:** With no register artwork held, any target `not_in_register` at any stage from `proposed` to `released` is planned as `record_reason`. That covers every stage except settled and cancelled. No note is needed, and the history records it as `linked`.
- **Scenario:**
  1. A deal is agreed on `sellers_own_work`.
  2. At `paid`, a Specialist sends `PUT /artwork {notInRegister:{reason:"in_zoho_not_linked"}}`.
  3. The PUT is accepted with no reason, and the deal is now in a state the Agree guard forbids.
  4. The flip the other way, `in_zoho_not_linked` to `sellers_own_work`, is the only path that satisfies the Agree guard without the register lock. It also needs no note today.
  5. The design says "Change/Remove only while Proposed/Offer with a reason".
- **Fix:**
  - In the domain, when `!held` and a reason is already recorded, treat a different reason as a change. Refuse it (`stage_locked`) unless `canChangeArtwork(stage)`.
  - Require a note (`reason_required`) when replacing an existing reason, and record the action as `changed`.
  - Linking a register artwork stays open until settled, as approved.
  - Add domain matrix tests at agreed, paid and released.

### L1 (Low): conflict found inside the transaction returns `stale_version` with no `currentVersion`
- **Where:** `deal-artwork.service.ts:202`
- **Scenario:** Two staff save at once. The loser gets 409 with no `currentVersion`. The pre-transaction check at line 125 does include it. The UI cannot offer "reload to the latest" in the same way for both cases.
- **Fix:** Return `currentVersion` from the conflict result: `missOrConflict` already reads the row.

### L2 (Low): new env URLs accept any scheme; not documented
- **Where:** `apps/api/src/env.ts:107,109`. The value is rendered as an external link in `apps/web/src/components/admin/private-sales/lock-refusal-notice.tsx:28`.
- **What:**
  - `z.string().url()` accepts `javascript:alert(1)`. I verified this with the repo's zod.
  - This is operator config, not user input, so it is not an open redirect.
  - Paths that come from the API are built server-side with `encodeURIComponent`, so `//host` cannot appear in the internal-link branch.
  - When the vars are unset, the link is omitted (`href: null`). That is safe, and `deal-lock-links.test.ts` covers it.
  - Neither var is in `.env.example` or `.env.production.example`.
- **Fix:**
  - Refine both to `https:` (allow `http://localhost` in dev).
  - Check that `ZOHO_CRM_RECORD_URL_TEMPLATE` contains `{recordId}`.
  - Add both to the env examples.

### L3 (Low): column doc contradicts behaviour
- **Where:** `packages/db/src/schema/private-sale-deal.ts:240` says the note is "required to change or remove". Remove only requires the enum reason, and the note is optional, both in the validator and in the UI (`remove-deal-artwork-dialog.tsx`).
- **Fix:** Make the doc match, or require the note on remove. As a reading of "with a reason", the enum reason satisfying it is acceptable.

### L4 (Low): no concurrency test
- **What:** By reasoning, the race-safety holds:
  - `setArtwork` uses `SELECT … FOR UPDATE WHERE version = expected`, and READ COMMITTED re-checks the row after the wait, so a concurrent second writer gets a conflict and rolls back.
  - `applyStageChange` is conditioned on `version`, so cancel versus change and agree versus remove cannot interleave.
  - The register's `moveOffer` uses `expectedVersion` with a re-read and retry, so two deals racing for one artwork means one is refused.
  - None of this is exercised with two real concurrent transactions.
- **Fix:** Add a Postgres integration test that runs two `set` calls in parallel:
  - same deal, different artworks: one succeeds and one gets `stale_version`
  - same artwork, two deals: one succeeds and one gets `artwork_unavailable`
  - change versus cancel: the artwork is never left held by a cancelled deal

### Info
- `deal-artwork.service.ts` `refusalOf`: a `DealArtworkRefused` with `entry === null` (the remove path) would be rethrown as a 500. This can't happen today, because `withdraw` never throws it, but a comment or explicit branch would be safer.
- `deal-query.service.ts:294`: one `findById` per artwork named in history (N+1). Fine at today's sizes; consider `findByIds`.
- Migration numbering: the stack has 0357 (idx 351) and then 0363 (idx 357). Main is at `0355` (idx 348). The journal idx/when will need re-sequencing when the stack lands after other in-flight migrations. The `when` ordering test will catch a mistake.

## Checked and OK
- **Authorisation and scope:**
  - Both routes use `requirePrivateSaleDealsManage`.
  - The service re-checks `canDo(viewer,"manage")` and `canSeeDeal` (so an out-of-scope deal returns `deal_not_found`, not 403, with no existence leak).
  - The web server actions check `PRIVATE_SALE_DEALS_MANAGE_ACCESS`.
  - Route tests cover the view-only roles returning 403 without the desk being called.
  - `recordHref` is only given to managers.
- **Lock atomicity:**
  1. The deal row is written first, taking the row lock.
  2. Then `offer(new)` runs, then `withdraw(old)`, then the event, all in one `runInTransaction`. Register calls run in savepoints.
  3. Any throw (`DealArtworkRefused`, `DealRegisterUnavailable`, `DealMovedOn`) rolls back everything.
  4. The integration test "keeps everything as it was when the register refuses" passes.
- **Release on cancel:** `REGISTER_EFFECT_BY_STAGE.cancelled` is `withdraw` and blocking, and it uses the current `artworkRegisterId`. A changed-away artwork is withdrawn at change time.
- **Settlement only marks sold:** this PR adds no `markSold`.
- **Never in two places:** `offer` refuses an artwork that is held elsewhere. Non-originals and missing entries are refused before the transaction (`artwork_not_original` / `artwork_not_found`), so `not_governed` cannot silently "link without a lock".
- **Audit content:**
  - The history row stores actor, `clock_timestamp()`, reason, and from/to for both id and unlinked reason, with `from` read under `FOR UPDATE`.
  - The domain event carries ids and enum reasons only. The free-text note and names are not in it, so it carries no PII.
- **Server-side stage rules:** enforced in the domain's `planDealArtworkMove`, apart from M2. `remove` refuses anything that isn't a held-artwork removal.
- **Agree guard matrix:**
  - Linked passes.
  - `sellers_own_work` passes.
  - `in_zoho_not_linked` blocks.
  - Nothing recorded blocks.
  - Covered in `transitions.test.ts` through `dealBlockers(…, "agree")`.
- **Migration:**
  - Additive only, with `lock_timeout`.
  - `IF NOT EXISTS` on the table and index, so re-running is a no-op (verified).
  - The rollback is idempotent (verified twice).
  - Re-applying after rollback works.
  - The CHECKs reject a bad `action` and a bad reason (verified).
  - FKs: RESTRICT for the deal and artworks, SET NULL for the actor.
  - `db:roles` re-run is fine.
  - `worker_app` has no grant, and needs none, because no worker reads this table.
- **Layering:**
  - The pure domain plan, the service, the repository, the route and the desk facade are cleanly split.
  - `DealLockLinks` keeps deployment addresses in config.
