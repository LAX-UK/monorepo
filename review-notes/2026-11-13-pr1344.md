## Findings

### F1 — HIGH — Public forms fail silently when the validation chunk can't load
`apps/web/src/lib/forms/lazy-resolver.ts`. When `load()` rejects, the resolver rethrows. react-hook-form 7.72 `handleSubmit` does not catch resolver errors: it never resets `isSubmitting`, never calls `onValid`, and the rejection is unhandled. Confirmed in the browser (section 2):
- Contact: the button stays "Sending…" (`aria-busy`) and no message is shown.
- Search: submit does nothing.
- Press filter, newsletter and private-sales enquiry use the same mechanism.

On `main` these forms validate and submit in the same scenario. Realistic triggers:
- A deploy that removes old chunks while a tab is open. `output: "standalone"` images ship no old chunks and there is no `deploymentId` skew protection.
- Mobile users who lose connectivity after first paint.

This breaks the plan's "no visible change / no blank UI on chunk error" rule. The repo already has a pattern for this (`*.lazy.failure.test.tsx`, and #1341 reports a failed socket fetch as a connection error and retries), and the new code doesn't follow it.

Suggested fix: on load failure, resolve instead of throwing. Either:
- return `{ values: {}, errors: { root: { type: "load", message: submitFailureCopy… } } }` so the form shows its failure notice and the button resets; or
- fall back to passing the values through, since the server actions re-validate (`private-sales/actions.ts` uses `enquiryFormSchema`).

Add failure tests at the form level (contact and search): button not stuck, a message shown, and a retry that works.

### F2 — MEDIUM — Branch conflicts with `main`; ratchets need re-measuring
`git merge-tree` against `origin/main` (`8f46e2d5`) conflicts in `scripts/route-js-baseline.json`, `scripts/route-js-budgets.json` and `docs/engineering/route-js-budgets.md`. #1341 lowered the same budgets and ratchets. After the rebase, the baseline and budgets must be re-recorded from a build of the combined tree, not hand-merged. The numbers in this PR were measured without the socket split.

### F3 — LOW — Account and checkout first load grows slightly
102 of 114 routes grew. Account pages grew 2.2–5.9 KB (`/settings`, `/notifications` +5.9) and checkout +2.4 KB. Everything is within budget and the PR documents it, but the PERF plan's goal is to shrink. Worth a follow-up `splitChunks` look so the public win isn't partly paid for by signed-in users.

### F4 — LOW — Tracing is decided by the page the session first loaded
A visitor who lands on a public page and client-navigates into `/home`, `/bids` etc. gets no account-page transactions for that session; before this PR they did, at 5%. This is documented in code. Please confirm it's acceptable for account tracing coverage, given most sign-ins start from a public page (OIDC redirects usually force a full load, which limits the impact).

### F5 — NIT — Small clean-code points
- `zodFormResolver(schema, errorMap?)` and `publicFormResolver(schema, errorMap = publicFormErrorMap)` are the same function with different defaults. One could wrap the other.
- `parseBidSchema` (`lib/data/http/bid.schema.ts`) is now only referenced by tests.
- `searchFilterSchema` is exported but only used inside its module.
- `lot-bid-update.ts` duplicates the Zod `bid_placed` contract by hand. The equivalence tests guard it, but any contract change now needs two edits. A comment in `lot-realtime-events.ts` pointing at it would help.
- `BROWSER_TRACED_SEGMENTS` is a hand-kept list. It is guarded by a test that reads the route folders, which is fine.

### F1 — fixed
- `lazy-resolver.ts` no longer throws when the chunk fails. The check resolves as invalid with the form's own failure message, and the next check imports again.
- The error key is `lazyResolver`, not `root`. react-hook-form 7.72 `handleSubmit` runs `unset(errors, "root")` before testing `isEmptyObject(errors)`, so a root-only error would have called `onValid` with empty values. Read it with `lazyResolverFailure(errors)`.
- Messages:
  - Contact (through `useActionForm`'s `rootError`) and private-sales enquiry: the existing `submitFailureCopy` notice, "We couldn't send your message / Your text is still here. Try again…".
  - Newsletter: its existing failure banner, `newsletter_submit_failed`.
  - Search box and press filter: "Search didn't load. Check your connection and try again." under the field. These forms had no failure copy, so this is new.
- Tests, modelled on `*.lazy.failure.test.tsx`: `contact-form`, `search-filter-form`, `newsletter-signup-form`, `press-filter-form` and `enquiry-card` `.lazy.failure.test.tsx`. Each checks:
  - the button is not stuck (no "Sending…" or `aria-busy`);
  - the message is shown;
  - no action or navigation runs;
  - after the chunk becomes available, the next submit imports once more and sends, navigates or validates.
- `lazy-resolver.test.ts` was updated (6 tests).

  - calls `client.addIntegration(browserTracingIntegration({ instrumentPageLoad: false }))`;
  - lets that navigation get its span.
- `lazyLoadIntegration` was not used. It fetches from Sentry's CDN, and the integration is already in the shared bundle (`@sentry/nextjs` imports it statically), so there is nothing to load.
- Public pages stay untraced until then.
- The sampler now decides a navigation span by the path it opens (`ctx.name` for navigation/pageload ops). Next starts the span before the address changes, so before this change the "public spans dropped" rule judged a navigation by the page being left. The rate is unchanged at 0.05.

  - with no client or DSN, nothing happens;
  - a real browser SDK run: `init` on `/sales`, a public navigation leaves no span and no integration, then a navigation to `/bids` gives a recording `navigation` span named `/bids`.
