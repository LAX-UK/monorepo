## What is good

- Money is whole pence end to end; `penceToPounds` is `p/100` (shortest double, serialises to 2dp), `poundsToPence` refuses
  any fraction of a penny instead of rounding it away (`money-format.ts:12-17`), and an unreadable amount becomes `unknown`.
- No adjustment field is ever sent; lines are qty 1 at a 2dp rate, so Books only rounds VAT.
- Idempotency: unique LAX-reference custom field + duplicate-code → lookup → adopt (`writer.ts:43-74`); a lookup is believed
  only when the detail read-back carries the exact reference (`lookup.ts:59`). Absence only from an empty list or 404.
  Ambiguity fails closed (rejected), unclear fails to `unknown`. POST retries only on 429. Good.
- Config is validated at start-up, no hard-coded ids in mappers, two entities cannot share one Books org
  (`org-config.ts:174-175`), an unconfigured entity (Bid) is refused before any request.
- No logging in the adapter; tokens/PII stay behind the client's `redact.ts`. Fixtures are synthetic ids only.
- Nothing is wired into an app; no test touches the network.

## Findings

### F1 — HIGH (entity separation): org chosen from `doc.entity`, dependencies looked up by `product` — can post across orgs
- Where: `src/adapter/gateways.ts:55`, `:80`, `:114`, `:149`, `:181` use `this.deps.orgs[doc.entity]`;
  `src/adapter/lookup.ts:31` uses `orgs[legalEntityFor(product)]`.
- Scenario (reproduced against `SimulatedBooks`): a Shop invoice with `entity: "london_auction_xchange"` (stale row, a
  hand-built object, a future builder bug). Requests sent:
  `GET /contacts?org=<Shop>` → `GET /contacts/<id>?org=<Shop>` → **`POST /invoices?org=<Bid>`** carrying the Shop org's
  `customer_id`. The simulator rejected it only because the contact id is unknown there; the POST still went to the wrong
  org, and an id collision or a contact that exists in both orgs would book Shop revenue in the Bid company.
  The domain builders set `entity = legalEntityFor(product)`, but the ports accept any object of the type, and the adapter
  is the last line before a ledger.
- Fix: one `orgFor(doc)` helper used by every gateway and the lookup: refuse (`rejected`, `zoho_books_entity_mismatch`)
  when `doc.entity !== legalEntityFor(doc.product)`, then select by that single entity. Add a contract case
  "entity/product disagree → rejected, zero requests sent". `api.ts:9` `orgFor` already exists but is unused.

### F2 — HIGH (VAT / entity facts): LAE is not VAT-registered in Zoho, but the adapter and fixtures assume it is
- Where: `src/adapter/org-config.ts:91-92` (a `standard` tax id is mandatory for every org); `src/adapter/mappers/common.ts:32-44`
  sends `tax_id` whenever one is configured; `src/testing/org-fixtures.ts:392-398,413` gives London Art Exchange a 20% standard
  tax; the contract (`adapter-contract.ts:32-45,125-130`) asserts Shop invoices carry 20% VAT and match.
- Scenario: LAE's Books org has no VAT taxes, so either (a) the config cannot be written truthfully and Shop never starts, or
  (b) someone puts a tax id in to get past start-up and Books charges/records output VAT for a non-registered company, or
  (c) Books ignores it and every Shop document totals net while LAX says net+VAT → every document `needs_review`. The test
  suite currently encodes the wrong fact, so it would not catch any of these.
- Fix (adapter only, no product logic): add `vatRegistered: boolean` per org. When `false`: require every `taxIds` entry to be
  `null`, never send `tax_id`, and refuse (`zoho_books_mapping_vat_on_unregistered_entity`) any line with `vatPence > 0`
  before sending. Model LAE as unregistered in `org-fixtures.ts` and add contract cases for it. Whether Shop/Art documents
  should carry VAT at all is a domain question for the owners/accountant — raise it, don't patch it here.

### F3 — MEDIUM (to the penny): credit-note VAT is re-derived by Books, not the VAT LAX stated
- Where: `src/adapter/mappers/common.ts:37,43` sends only the gross for a `tax_inclusive` line; Books then works VAT out as
  `gross × 20/120`. `accounting-domain/src/money.ts:55-60` says an adapter "must send the gross with the stated VAT, never
  re-derive VAT". The domain allocates credit VAT cumulatively (`cumulativeVat`), which differs from Books' per-line
  inclusive rounding.
- Scenario: invoice line net £0.21, VAT £0.04, gross £0.25; credit £0.03 → LAX VAT 0p, Books 1p; the finishing credit of
  £0.22 → LAX 4p, Books 4p ⇒ Books has credited 5p of VAT on a 4p invoice. My script found a 1p difference in ~11% of partial
  credits (nets up to £199.99, splits g/3, g/7, 1p). The domain's totals check will route these to `needs_review`
  (it is not silent), but the review queue will fill and the VAT return will drift by pennies. The contract's only credit
  case (`adapter-contract.ts:231-255`, £60 of a £120 line) happens to agree, so the suite gives false confidence.
- Fix: in the Books test org, confirm whether a line-level tax amount override is accepted; if so send `vatPence`. If not,
  the owners/accountant must choose (accept review, or align the domain's allocation with Books' rule — product logic, not
  this PR). Either way add a contract case with a known 1p disagreement asserting it is reported, never adjusted.

### F4 — MEDIUM (dry-run guarantee): the adapter has no write guard of its own
- Where: `src/adapter/index.ts:40-55`, `writer.ts:36`, `gateways.ts:208`. Any holder of a `ZohoBooksClient` + configs can POST/PUT.
  Today the guarantee holds only because nothing is wired (verified: no app depends on the package) and the mode lives in
  `accounting-domain/src/source-switch.ts`.
- Scenario: the runtime PR builds the adapter with the live org config and calls a port from a `dry_run` code path → a real
  document in the live company.
- Fix (before the wiring PR, not necessarily here): wrap `ZohoApi` in a `WriteGate` that refuses `post`/`put` unless an
  explicit `mode ∈ {test_org, live}` was passed at construction and the organisation id is on an allow-list; default
  `dry_run` returns `rejected: zoho_books_writes_disabled` with zero requests. Add a test that the default adapter sends no
  write.

### F5 — MEDIUM (functional, money flow): bills go to contacts created as `customer`
- Where: `src/adapter/mappers/contact.ts:7,21` hard-codes `contact_type: "customer"`; `gateways.ts:151-158` uses the same
  contact as `vendor_id`. `SimulatedBooks.price` (`simulated-books.ts:190-193`) accepts any contact, so the contract passes.
- Scenario: seller payout bill for an artist who was only ever created via `upsertContact` → Books refuses a customer as a
  vendor (to confirm in the test org) → every payout bill `rejected`.
- Fix: carry the role (customer / vendor / both) on the contact port or create vendor contacts separately; make the
  simulator refuse a bill whose vendor is not a vendor.

### F6 — LOW: payment and bill bodies omit `currency_code`; bill bypasses the shared line mapper
- `mappers/payment.ts:30-42`, `mappers/bill.ts:45-54`: no `currency_code` (invoice/credit note send `GBP`). Books falls back
  to the contact's currency — fine while everything is GBP, wrong silently if a contact is ever non-GBP. Send `payment.currency`/`bill.currency`.
- `mappers/bill.ts:41` recomputes `quantity * unitNetPence` and ignores `line.basis`; use `lineNetPence` and refuse a
  `tax_inclusive` bill line, so the rule lives in one place.
- `mappers/invoice.ts:37` / `credit-note.ts:40` hard-code `is_inclusive_tax` while `common.ts:37` chooses per line by
  `line.basis`. A mixed document would send a gross as an exclusive rate (VAT charged twice). Builders prevent it today;
  assert every line's basis matches the document flag and refuse otherwise.

### F7 — LOW: payment mapper defaults a missing invoice id to `""`; payment read-back checks amount only
- `mappers/payment.ts:38` `?? ""` — unreachable today (gateway resolves every id first) but would send an unapplied
  allocation instead of failing; return a mapping refusal instead.
- `kinds.ts:46-49`: an adopted payment (duplicate path) is compared on `amount` only, so a Books payment with the same
  reference but different allocations is accepted as ours. Consider reading `invoices[].amount_applied` back and
  comparing allocations in the adopt path.

### F8 — LOW (test quality): the fake is looser than the adapter in ways the contract never probes
- `fake-accounting.ts:295` ignores `kind` in lookup; `:310` checks dependencies by `doc.entity` (the adapter by `product`, F1);
  no check of contact type (F5), allocation ids, or entity/product agreement. Contract has no case for: Bid org not
  configured, lookup `unknown`/`ambiguous`, timeout on payment/credit note, a 1p credit disagreement (F3), LAE without VAT (F2).
- Fixtures give both orgs the **same** tax ids (`org-fixtures.ts:382-398`), so a mapper reading the wrong org's tax config
  would still pass. Give each org distinct tax ids and assert them in `adapter.test.ts`.

### Open items already listed in the PR README (agree, must be confirmed in the Books test org before any send)
Custom-field list filter, the duplicate-value code, credit note/payment read-back field names, inclusive tax rounding (F3),
applying a credit note via `?invoice_id=`. The lookup fails safe if the filter is ignored (one row → reference mismatch →
`unavailable`; two rows → `ambiguous` → rejected).

## Verdict reasoning
Nothing here can write to a live org today, and idempotency, rounding and the error model are careful. But F1 is a
cross-org posting path in the adapter itself, and F2 means the code and its test suite assume LAE charges VAT when it is not
registered — both go against the stated rules for this migration and should be fixed before this becomes the base for
the wiring PR. F3–F5 can be tracked as owner/accountant questions and follow-ups.

### Verdict: FIX FIRST
