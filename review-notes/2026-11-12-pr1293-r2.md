## Verdict: **FIX FIRST**

All six findings from the first review are fixed, and the fixes are correct. I verified the trigger, the grants, the stage matrix and the env validation against a real PG16.

One new problem blocks the merge. The concurrency test added for L4 **fails every time**: 10 of 10 runs, on a clean PG16. It fails because it found a real deadlock:
- Two staff link the same register artwork to two different deals at the same moment.
- Postgres aborts one of them with `40P01 deadlock detected`.
- That error is not a refusal the service knows, so it reaches the client as a **500** instead of `artwork_unavailable`.

The data stays correct: one deal holds the artwork and the other rolls back. But the PR's own new test is red, and the user sees an error page instead of the "held elsewhere" message. The fix is small (N1 below).

## New findings

### N1 (Medium, blocks merge): deadlock when two deals link the same artwork at once; the new concurrency test fails 10/10
- **Where:**
  - `apps/api/src/services/private-sale-deal/deal-artwork.service.ts:168` (`setArtwork` first) and `:179` (`register.offer` after)
  - `packages/persistence/src/repositories/drizzle-private-sale-deal.repository.ts:178-197`
  - `packages/persistence/src/repositories/artwork-register/drizzle-artwork-register.repository.ts:378` (`SELECT … FOR UPDATE` on `artwork_register`)
  - Test: `deal-artwork.concurrency.integration.test.ts:169` ("same artwork, two deals")
- **What:**
  1. `setArtwork` writes `private_sale_deal.artwork_register_id = X` and inserts a history row with `to_artwork_register_id = X`. Both foreign keys make each transaction take **FOR KEY SHARE** on artwork row X.
  2. Both concurrent transactions get that lock, because key-share locks are compatible with each other.
  3. Each then calls `register.offer`, which needs `SELECT … FOR UPDATE` on the same row. FOR UPDATE conflicts with the other transaction's key-share lock, so each waits for the other: a lock-upgrade deadlock.
  4. Postgres aborts one transaction after `deadlock_timeout` (1 s) with `40P01`.
  5. `ArtworkRegisterDealLock.run` rethrows the error unchanged, and `refusalOf` then rethrows it too, so the request fails with an unhandled error: a **500**.
- **Scenario:**
  1. Two Specialists, working on deals PS-A and PS-B, both press "Link artwork" for the same original within about a second of each other.
  2. One waits about 1 s and gets a server error instead of "This artwork is held for PS-A".
  3. The data stays correct: the loser rolls back.
- **Evidence:**
  - `vitest run deal-artwork.concurrency.integration.test.ts`: `× same artwork, two deals … 1049ms`, caused by `error: deadlock detected (40P01) … while locking tuple (0,45) in relation "artwork_register"`.
  - It failed on 10 of 10 runs. The other two tests in the file pass.
- **Fix (verified):**
  - Hold the artwork **before** writing the deal row's FK. In `carryOut`, call `scope.register.offer(toId, …)` before `scope.deals.setArtwork(...)`. Keep `withdraw(old)` after.
  - Alternatively, `SELECT … FOR UPDATE` the target `artwork_register` row first.
  - I made the first change locally, never committed and reverted afterwards. The concurrency file then passed **5/5**, and the same-deal and change-versus-cancel tests stay green.
  - With offer first, the deal row's version check still guards the deal. A `DealMovedOn` rolls back the savepointed offer along with everything else.
  - Update the "deal row goes first" comment.
- **Also consider:** mapping `40P01` and `40001` from the register to `artwork_register_busy` (retryable) as a backstop, instead of a 500.
- **Same pattern, already in the base branch, not introduced here:**
  - `enquiry-conversion.service.ts:142` creates the deal with `artworkRegisterId` and offers at `:166`.
  - Two conversions racing for one artwork can deadlock the same way.
  - Worth fixing in the same way (offer, or lock the row, before the insert), in this PR or as a follow-up.

### N2 (Low): the concurrency test commits rows permanently
- **Where:** `deal-artwork.concurrency.integration.test.ts` (header comment: "The rows these tests write are kept"). The change to `enquiry-conversion.integration.test.ts` exists because of it.
- **What:**
  - Each run commits users, a legal entity, item submissions, deals, artworks and append-only history to the shared test DB.
  - The rows can never be deleted: the history trigger and the RESTRICT FKs prevent it.
  - The enquiry-conversion assertion had to be narrowed from "no `item_submission` rows at all" to `legalEntityId = clientEntityId`. That narrowing is correct and isolated: the fixed `clientEntityId` is inserted inside the rolled-back outer transaction, and the conversion's parties resolver returns exactly that id.
  - The risk is any other suite that counts globally on `item_submission`, `private_sale_deal` or `artwork_register`. Everything I ran passes with these rows present: api private-sale (25 files), persistence repository, db role contracts.
- **Fix:** acceptable as is, given the ids are unique per run. Optionally, give the suite its own schema or database, or document that it must run on a disposable DB.

### N3 (Low): a reason can still be first recorded after Agreed, with no note
- **Where:** `packages/domain/src/private-sale-deal/artwork.ts:67`
- **What:** when nothing is held and **nothing** is recorded, `record_reason` is allowed at any stage where linking is allowed, with no note.
- **Scenario:**
  1. A deal reached Agreed before this PR's Agree guard existed, so it has no artwork and no reason.
  2. At `paid`, the API accepts `notInRegister: in_zoho_not_linked`, a state the Agree guard now forbids.
  3. It is recorded as `linked` with no reason.
- **Impact:** small. It only fills in information on deals from before the guard, and adds no lock or escape from one.
- **Fix:**
  - Optionally, from Agreed onwards allow only `sellers_own_work` (the value that satisfies the guard), or require a note.
  - Otherwise, accept it and note it in the domain comment.
