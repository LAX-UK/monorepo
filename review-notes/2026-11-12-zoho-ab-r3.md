### B-3 race and money-path analysis (checked, OK)

- **Payment completing while the sweep runs:**
  - The sweep finds the session `already_complete` and reconciles under event id `reaper-reconcile:<session>`. The Stripe webhook arrives with `evt_…`.
  - Both take `FOR UPDATE` on the order, so they run one after the other.
  - The first throws `paid_while_money_paused`, rolls back, and records it (order becomes `payment_failed`, and the session is kept on the order).
  - The second sees the order closed. `recordUnappliedShopPayment` locks `shop-session:<id>` and dedupes across reasons (`existsForShopPayment`), so **only one finance task** is opened.
- **Stripe idempotency:** `checkout.sessions.expire` is naturally idempotent. A repeat sweep after a partial failure re-expires (already expired) and then proceeds. The `money-pause:order:<id>` claim is taken only in the local transaction, and repeats return `duplicate`/`unchanged`. The test "repeat is a no-op" passes.
- **Never fulfil:** the check sits before any order, edition, stock, payout or event write inside the same transaction, and the failure is non-retryable. Verified by `checkout-money-pause.integration.test.ts` ("if paid anyway, is not fulfilled").
- **Refund path:** `shop_order_paid_while_paused` is in `UNAPPLIED_MONEY_REASONS` and the fanout text. There is no DB CHECK on reasons, so it goes through the generic finance-task refund flow. N-B3 covers the wrong "reinstate" wording.
- **Every money-completion entry point has the pause:**
  - the webhook processor and checkout repository (`create-commerce-services.ts:80,143`);
  - the stale reaper, the money-pause sweep, and the ceiling settle (`create-shop-api-scheduler.ts:106-127` through `checkoutTransitions`).

### New findings (B)

**N-B1 [MEDIUM, reproduced]: the sweep expires orders that have no payment page, so a false alarm permanently cancels the buyer's order and hold.**
- **Where:**
  - `apps/shop-api/src/infrastructure/shop-checkout-money-pause-sweep.ts:35-56` selects every `pending_payment` order and checks only `orderHoldsPausedArtwork`, not whether a Stripe session exists.
  - `shop-checkout-stripe-expiry.ts:15` returns `not_expirable` for a null session, so `expireStripeBeforeLocalTransition` proceeds.
  - `expireShopCheckoutSession` (`drizzle-payment-event.processor.ts:1214-1304`) then sets `expired`, closes the delivery quote (`expired`), releases editions and restores the basket.
- **Scenario:**
  1. A buyer has an international-delivery order waiting for a quote. That is `pending_payment` with a long `holdUntil` and no session until they accept.
  2. Or a buyer has an order whose session has not been created yet.
  3. Zoho briefly shows Sold (wrong record, or a typo), and an item is raised.
  4. Within one scheduler tick (60 s) the order is expired and its quote closed.
  5. Staff click "It is not sold" a minute later. The buyer's order, hold and staff quote work are gone, and the artwork is buyable by anyone. The spec says *pause*; this is cancel.
  6. The guards already stop every way a no-session order could take money while paused: resume and accept-and-pay are both refused (tests "refuses to resume a pending order that has no session yet" and "refuses accept-and-pay on a delivery quote"). So expiring these orders buys no safety.
- **Repro:** a throwaway case in `checkout-money-pause.integration.test.ts` (not committed) passed, which confirms the bug. In it, the order's `stripe_checkout_session_id` is set to null and the pause turned on. The sweep runs and the pause is lifted. Then: no Stripe expire call, order status `expired`, and resume refused.
- **Fix:**
  - Restrict the sweep to orders with `stripe_checkout_session_id IS NOT NULL`. Pages that cannot be paid need no action.
  - Better still, end only the Stripe session and leave the order `pending_payment`. The existing resume guard keeps it unpayable while paused and lets the buyer continue after an override. If expiring the order is kept deliberately, document it in the spec and notify the buyer.
  - Add tests: a no-session or quote-pending order is untouched by the sweep, and an order whose session was ended can be resumed after the pause is lifted.

**N-B2 [LOW-MEDIUM, least privilege]: `shop_app` has table-wide UPDATE on `artwork_register_sold_attention`, and `worker_app` has the same.**
- **Where:** `packages/db/src/migrate-roles.ts:1027-1029` (`SELECT, UPDATE` for shop) and `:1139-1141` (`INSERT, SELECT, UPDATE` for the worker).
- **Probe (Postgres, as `shop_app`, rolled back):**
  - shop can run the real override (UPDATE of the status, resolution, resolved_by, override_reason and resolved_at columns, plus INSERT of the `artwork_register_event` row).
  - **shop can also run `UPDATE … SET zoho_product_id='other', place='bid_sale', status='resolved', raised_at=…`.** Any shop-api bug or injection could silently lift a money pause or re-point it, and no event would be written.
- **What each role needs:**
  - shop's only write is `override` (`drizzle-sold-attention.store.ts` `override`): `status, resolution, resolved_by, override_reason, resolved_at`.
  - the worker writes `status, resolution, resolved_by, resolved_at` on resolve or replace, plus INSERT.
- **Fix:**
  - Use `grantColumnUpdateIfExists` (already in `migrate-roles.ts`). For shop, that means SELECT plus UPDATE(status, resolution, resolved_by, override_reason, resolved_at). For the worker, SELECT and INSERT plus UPDATE(status, resolution, resolved_by, resolved_at).
  - Extend the role probe to assert that UPDATE of `zoho_product_id`/`register_id`/`place` is denied for both roles. The shop role is not probed at all today: `checkout-money-pause.integration.test.ts` runs the pause through a fake reader, and the store integration test runs as owner.

**N-B3 [LOW]: the finance task text promises an action that does not exist.**
- **Where:** `apps/worker/src/projectors/notification-fanout/unapplied-money-fanout.ts:39-40` ("…refund the buyer, **or reinstate the order** if staff have said the artwork is not sold"), and `packages/domain/src/unapplied-money.ts` ("reinstate").
- **Scenario:** no shop-api route or LAX Admin action reinstates a `payment_failed` order (grep finds "reinstate" only in an unrelated holds message). Finance cannot follow the second branch, and the basket has already been restored and the artwork returned to sale.
- **Fix:** say "refund the buyer; if staff have said it is not sold, contact the buyer to buy it again" (or build the reinstate action).

**N-B4 [process, blocks merge]: B does not merge with current `main`.** See the merge section. B needs to rebase after A, take idx 351, and resolve the persistence index conflicts. After resolution it must also drop `desc` from the repository's drizzle import, or `packages/persistence` fails TS6133.

**N-B5 [LOW]: the sweep cost and window grow with every pending order.**
- **Where:** `shop-checkout-money-pause-sweep.ts:35-46`. It reads up to 1,000 `pending_payment` orders oldest first, every tick, and for each runs one join query plus one `isPaused` query per artwork.
- **Scenarios:**
  - With more than 1,000 pending orders (long quote holds), the newest orders, which are the ones most likely to be paid, are never examined. Only the payment backstop is left.
  - A paused order with an async payment (`skip_async`) makes a Stripe `sessions.expire` call every tick until the ceiling.
- **Fix:** start from the open items. Select pending orders joined to `shop_order_line → shop_artwork` where `zoho_product_id IN (SELECT zoho_product_id FROM artwork_register_sold_attention WHERE status='open')`. That is one query and has no window. Combine it with N-B1's session filter.

**N-B6 [LOW]: `findLive` may return an overridden item while an open one exists.** After the race B-5 describes, two live items can exist (one per status). `findLive` returns the newest, which can be the `overridden` one. The open item then stays open, and keeps money paused, until the sweep or a later change reaches it. Prefer `open` first in the ORDER BY (`status = 'open' desc, raised_at desc`).
