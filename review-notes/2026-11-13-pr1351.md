## Findings

### F1. Medium (test gap): purchase invoices while viewing a personal account are untested
`apps/web/src/lib/purchases/purchase-sources.server.ts` `invoicesFor`. Removing the `!account.isImpersonation` condition sends the staff member's own `/payments/me` invoices into the viewed client's Purchases, and no test notices. The code is correct today. Add a test: for a personal scope with `isImpersonation: true`, it reads the entity payments and never `payments.listMine`.

### F2. Low: the view-as organisation context carries the raw entity row
`apps/web/src/lib/legal-entity/per-org.gateway.server.ts` `viewedOrganisationOf` now uses the body of `GET /legal-entities/:id`. For a view session the API builds that body from the raw repository row (`legal-entity-access.service.ts`, impersonation branch). Members get `toMemberLegalEntity`. So `context.entity` can hold fields members never receive, including the Stripe Connect account id. Only staff with a valid view session can reach this, so the exposure is small. Fix it either way:
- map the impersonation answer through `toMemberLegalEntity` in the API, or
- pick the `MemberLegalEntity` fields in `viewedOrganisationOf`.

Also make sure nothing passes `entity` whole to a client component.

### F3. Low (pre-existing, not in the diff): download routes outside `recordRefusalStatus`
- `organisation/documents/agreements/[submissionId]/route.ts` turns an API 403 into 502. It is not an existence oracle: the API's 403 is a role check made before the record is read, the same for every id. But it disagrees with the new helper, and a role refusal reads as an outage. Use `recordRefusalStatus` here too.
- The payout-statement API (`lib/payout-statement-http.ts`) returns the stored `statementGenerationError` text as `detail` to members. The web route hides it with a redirect, but the API answers browsers directly. Drop `detail` from the client response and keep it in logs.

### F4. Low (copy): a missing telephone booking reads like an outage
The detail page shows "couldn't be loaded / Try again" for a booking that is missing or someone else's. Neither case is confirmed, so this is not an oracle. But Try again can never help, and the case is answered as 404 everywhere else. Consider wording such as "We can't find this telephone booking", with Back to bids first.

### F5. Info: per-request audit while viewing as a client
Under the existing policy, view sessions are audited at session level: `admin.impersonation_started`, `admin.impersonation_ended`, and the timeout or reconcile endings. Individual acted reads are not audited. The PR does not change this. It routes more reads (a personal account's bids, purchases, amounts owed and invoices) through the same validated session, so the audit trail is unchanged. If policy expects one audit row per acted request, that gap was already there before this PR.

### F6. Info: timing
"Not yours" makes one more lookup than "missing" (the payment-authority or membership check after the row is found). Status, body and headers are identical. The timing difference is one indexed query, the same class as other reads. Acceptable.

### F7. Info: personal purchases with no `buyerLegalEntityId`
Viewing a personal account now reads `/users/me/account/purchases`, which filters by `buyerLegalEntityId`. Older personal wins without that column set would not show in the staff view. This is not a privacy problem. Worth a quick check against production data.

## Checks that passed

**(1) 404 parity**
- These now answer someone else's record exactly like a missing one, with the same status and the same JSON body (code and message): the record-account resolver (purchase, consignment, reoffer), lot fulfilment, cancel-pending, paying for a lot (`not_winner` and `not_member` → `purchase_not_found`), source-of-funds attach and submit, collection booking, change and cancel, and the web invoice, agreement and calendar downloads.
- The ownership check runs before anything is read into the response in each case.
- Role-only refusals (`insufficient_entity_role`, `not_payer` for a member) stay 403. They do not depend on the id, so they confirm nothing.
- Org-scoped API reads (invoice PDF, agreement PDF, calendar) were already `not_found` for another account's id.
- The purchase detail page now gives `notFound()` for a stranger's lot, not the access page.
- The private-sale deal and payout statement paths were already id-safe.

**(2) View as client**
- The API grants view access only when all three hold: `canAccessPlatformAdminRoutes`, a structured acting cookie for the same entity id, and a session validated for that actor and target with an expiry.
- A non-staff user's cookie is ignored. An expired session answers 403 and records the timeout.
- The cookie is unchanged by this PR. It is SameSite=Lax, Secure in production, has a bounded max age, and is httpOnly=false by design because it is sent as a header. It stays bound server-side to the actor.
- Writes stay blocked: the capability middleware refuses with the read-only message, the collection guard checks `read_only` before the new branch, and the seller context denies `entity.submissions.create` (tested).
- The web side only opens tabs on an API answer that is already a validated view session. The API keeps authorising every read, so the fix does not widen what staff can do.

**(3) Error states**
- No internal details in the new copy. There is a test that rejects "something went wrong", "submission" and "could not".
- Heading levels are right: h2 under the page h1, h3 inside the Payout statements and Your documents sections.
- Contrast was computed from the tokens:
  - title `--lax-danger-fg` on `--lax-danger-bg`: 6.2:1 in light, about 7.2–8.2:1 in dark over the dark surfaces;
  - body `--lax-fg`: 15.3:1 in light and at least 12:1 in dark.
  - All AA.
- The primary-button change is limited to call sites: the verify-identity `buttonClassName`, the acting tooltip `variant="primary"`, and the app-level `ConfirmActionButton` wrapper, which has 2 callers, both checked. `packages/ui` is not touched.
- The screenshots match.

**(4) Tests**
Each changed route has a theirs-vs-missing 404 parity test, and every ownership mutation is killed.
