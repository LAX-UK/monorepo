## What is good

- **Dry-run guarantee holds end to end.** `createBooksAccountingAdapters` (`finance-runtime/src/books/create-books-accounting-adapters.ts:35-50`)
  builds only `{ dry_run: createZohoBooksDryRunAdapter }` (line 48), and that adapter holds no HTTP client (`dry-run.ts:49`). No app or
  package outside the Books package imports the writing adapter or the client. The only env var is `ZOHO_BOOKS_ORG_CONFIG`
  (org settings JSON; no mode, no token). The sender only claims `targetModes = keys(portsByMode)` = `["dry_run"]`
  (`accounting-sender.service.ts:61-65`, enforced in SQL at `work-queue.ts:64-66` and `due-work.ts`), so a document aimed at
  `test_org`/`live` is never taken even if the switch says so. Integration test "a rehearsal-only sender never takes a document
  aimed at a test organisation" covers it.
- **Xero default untouched.** Seed stays `bid: xero live / books off`; with Xero live, `documentTarget` names Xero, so the
  projector skips (`books_not_selected`) and registers nothing. Legacy Xero code is not modified; `payment.captured`/`payment.refunded`
  only gain the `accounting` consumer.
- **Money.** Whole pence end to end: `(amount * 100)::bigint` in SQL (`drizzle-bid-accounting-facts.reader.ts`), line pence from
  `bid_invoice_line`, no floats. Bid lines are margin scheme (no VAT shown), an unmapped line kind is refused, a 0p line is dropped.
  A payment larger than its invoice is refused (no spread remainder). Refunds are replayed oldest first through
  `splitRefundTotal` + `buildCreditNoteFor`, so credit notes can never exceed what was paid. Non-GBP refunds are skipped.
- **Idempotency.** Every document is keyed by LAX reference (unique `product, legal_entity, lax_reference`); same payload = replay,
  different payload = refused (contacts excepted, `keep_held`). Deliveries are idempotent by `accounting:<event id>`. Claims use
  a lease token; a late answer from a lapsed lease is refused (integration "does not trust a late answer…"); concurrent claimers
  never share a document; two simultaneous transitions: one wins.
- **Retries / poison.** `retryDelayMs` 30 s doubling to 30 min, 8 attempts, then `escalate` to `needs_review`. The schedule lives
  in the domain and is spelled out per attempt count in SQL (`due-work.ts waited`), so they cannot disagree. Only rate-limit /
  budget refusals are retried; any other refusal waits for a person. A thrown send is `unknown` and looked up before any resend.
- **N1 — DONE.** New `IssueOutcome` `differs` (`ports.ts`); `writer.ts` returns it for a read-back mismatch after a fresh create
  and on adopt; `lifecycle.ts holdDifferingDocument` makes it `needs_review` with the provider id kept and the totals mismatch
  recorded; history row stores both totals (`accounting-document-move.ts transitionDetail`). Never `failed`, so never requeued.
  Covered by contract, sender and integration tests.
- **N2 — DONE.** `environment: "test" | "live"` is required per org (no default, `org-config.ts:159-161`); `WriteGate` refuses
  `test_org` → live org and `live` → test org (`write_allow_list_wrong_environment`, `write-gate.ts:52-62`), 3 tests.
- **N3 — DONE.** Documented in `accounting-domain/README.md` ("Vendors"): no domain `VendorPort` yet, no policy makes a bill,
  the sender sends customers only (`SenderPorts` has no vendor port).
- **Layers / secrets.** `accounting-domain` stays pure (projection and retry have no I/O or clock); `lint:layers` passes. Worker
  logs carry document id, LAX reference, mode and outcome only; thrown errors are logged by `error.name`; the dry run keeps no
  request body (names/emails); bad JSON config does not echo its content.
- **Grants.** No new grants needed; new probes assert worker_app SELECT on the facts tables and INSERT on `domain_events` /
  `projector_state`, and the store role contract includes the two new stores. All pass against a real database.

## Findings

### F1 — HIGH (cutover / idempotency): a rehearsed document holds its LAX reference forever, as `issued`, so it is never sent to the test or live org
- Where: unique index `accounting_document_reference_uid (product, legal_entity, lax_reference)` (`packages/db/src/schema/accounting.ts:65-69`)
  has no target; `drizzle-accounting-document.registry.ts:72-112` returns the existing row (`created:false`) whatever its target;
  `dry-run.ts:127` answers `issued` (`DRY-RUN`, `dry-run:<ref>`), which is final; `accounting-projection.service.ts:122-124` keeps a
  held contact.
- Scenario (reproduced with the probe above): Books `dry_run` for Bid → buyer contact and invoice are registered and become `issued`
  under the rehearsal identity. Switch moves to `test_org` (later `live`). The buyer wins another lot: `invoice.raised` re-projects
  the contact → `reference_in_use`/replay → the contact stays a `dry_run` row and is never queued for the test org. The new invoice
  goes to `test_org`, and the adapter refuses it (`contact missing`): **every invoice for any buyer seen during rehearsal fails** after
  the switch. Same for an invoice raised in rehearsal and paid after the switch (the payment's invoice is not in Books), and every
  refund credit note for such an invoice. It fails safe (refused, held for a person), but it is the whole migration path.
  It cannot be cleaned up later either: `accounting_document_event` is append-only even to the owner (triggers
  `accounting_document_event_no_change`/`_no_truncate`) and its FK to the document is `RESTRICT`, so rehearsal rows can only
  be removed by disabling triggers in a migration.
- Fix (before this is turned on anywhere with real data): make the reference unique per target, for example the unique index on
  `(product, legal_entity, lax_reference, target_provider, target_mode)` (with a rule for rows with no target), and have `register`
  look up by the current target. Or keep rehearsal documents in their own table. Add an integration test: "a reference rehearsed in
  `dry_run` is queued again, `pending`, for `test_org`, and the `test_org` sender claims it". At minimum, document that the dry run
  must not run against production data until this is decided.

### F2 — MEDIUM (double booking at cutover): turning Books off and on again projects the events of the gap, under today's switch
- Where: `apps/worker/src/projectors/accounting-projector.ts:25` returns before queueing when no product aims at Books, so the
  cursor does not move; `drizzle-projector-cursor-start.ts:25` (`onConflictDoNothing`) keeps an old cursor; `accounting-projection.service.ts:80-84`
  decides by the switch at processing time, and the registry aims the document by the switch at registration time.
- Scenario: Bid `books: dry_run` (Xero off in the switch) for a week, then back to Xero `live` for a month, then Books `test_org`/`live`.
  On the first tick all events of that month are queued and projected **into Books** although Xero booked them; with `live` the
  same invoices and payments would be in both ledgers.
- Fix: while inactive, move the cursor (or reset it to the newest event on each activation, as on first start), and make any history
  backfill an explicit command. Better still, record the target on the event (or decide by the switch history at the event's time).
  Add a projector test for off → on.

### F3 — LOW (operations): a Books rehearsal for Bid needs the switch to say "Xero off" while legacy Xero keeps posting
- `aimsAtBooks` (`accounting-projection.service.ts:63`) uses `documentTarget`, which returns Xero whenever Xero is `live`, so
  `bid: xero live, books dry_run` projects nothing. To rehearse Bid someone must set `xero_mode = off`; legacy Xero does not read
  the switch, so it keeps writing, and the switch then misstates reality (and is the setting F2 will later replay against).
  The sender uses a different test (`product.books` in its modes, `accounting-sender.service.ts:101-103`), so it reports `active`
  when the projector does not. Fix: decide whether a shadow rehearsal beside Xero live is wanted; document the procedure in the
  README and use one activation rule in both services.

### F4 — LOW (functional): `invoice.raised` refuses a zero-total invoice in its own schema
- `financial-payload-schemas.ts:11` `totalPence: positive()`, while `raise()` writes the event for any inserted invoice
  (`drizzle-bid-invoice.repository.ts:195-209`). A 0p invoice (fully discounted, or all lines 0) would write an event that
  `assertDomainEventConsumerContract`/`safeParse` refuses → dead letter. Fix: `nonnegative()`, and let the policy refuse
  an empty invoice with its own code.

### F5 — LOW (follow-ups, not blockers)
- A payment settled through **lookup** (unknown → found) is compared on totals only; the allocation check (`paymentMatches`) runs
  only on create/adopt. Same total, different allocation would be `issued`. Consider the same verify on the lookup path before
  `test_org`.
- `failed` (lasting refusal) and `needs_review` rows are not surfaced (no metric, alert or count in the sender tick). In rehearsal
  every Bid document is refused while the Bid org is not configured; that is silent. Add a gauge per state before `test_org`.
- Events skipped as "not built yet" (`invoice_voided`, `payment_in_group`) are marked `skipped`; when those flows are built
  they need a deliberate backfill from the delivery ledger (a refund on a voided invoice is otherwise never credited).
- `legacy_total` is booked as margin-scheme goods (`projection/bid.ts:83`); with hammer/premium this is listed for the accountant
  in the README, keep it on that list.

## Test quality
Good: fakes are the adapter's own contract, the sender is tested for lost answers, lapsed leases, backoff, poison, mode isolation
and the N1 path; the persistence tests run as `worker_app` against real Postgres; the Bid facts test raises a real invoice and checks
the event is in the same transaction. Missing: a mode change for an existing reference (F1), projector off → on (F2), a 0p invoice (F4).

## Verdict reasoning
Nothing in this PR can write to any Books organisation: the only adapter built has no HTTP client, no env var or switch value adds
one, and the claim is filtered by mode in SQL. Money handling, idempotency under replay and concurrency, retries/poison and N1–N3 are
correct and tested. But F1 means the rows this rehearsal writes take each LAX reference permanently as `issued` with a fake id, in an
append-only table, which breaks the dry_run → test_org step this PR exists to prepare for and cannot be undone later without
disabling the history triggers. That should be decided (and the key changed or the rehearsal kept apart) before the feature is
turned on; F2 belongs with it.

### Verdict: FIX FIRST

### Findings

- **F1 — FIXED.** Migration 0374 replaces `accounting_document_reference_uid` with
  `UNIQUE NULLS NOT DISTINCT (product, legal_entity, lax_reference, target_provider, target_mode)`; the constraint is added
  before the old index is dropped (`lock_timeout 5s`). Safe on existing rows: the old key was narrower, so the wider one cannot
  find a duplicate (proved on a DB with a row: rollback → re-migrate). NULL targets share one slot, and `ON CONFLICT` inference
  works with it (integration "keeps one document with no target per reference", plus a raw duplicate insert → `23505`). The
  registry inserts and replays under the switch's current target (`drizzle-accounting-document.registry.ts`), so the rehearsal
  row stays `issued` with its history untouched (asserted: `created → start_sending → complete_sending`) and `test_org` gets a
  new `pending` row that the `test_org` claimer takes. Dependents: every Bid projection lists `[contact, invoice, …]`
  (`projection/bid.ts:147,185,225`) and the worker test "after a rehearsal, re-projects the contact and invoice for the new
  target before what names them" covers the order. Leases are per row, so a rehearsal row in `sending` cannot block the new one.
  `findByReference` without a target returns the newest row; it has no production caller outside tests (the sender looks up
  through the provider port). The rollback refuses (changes nothing) once a reference is held twice — correct, and documented.
- **F2 — FIXED.** While no product aims at Books the projector calls `moveToLatestEvent` every tick
  (`greatest(current, max(domain_event.id))`, never backwards, same row lock as the queueing transaction) and lets queued
  deliveries settle as `skipped/books_not_selected`; an unreadable switch moves nothing. Off → on projects only new events
  (worker test, red under mutation). Backfill is documented as its own command (not built).
- **F3 — FIXED.** `booksTargetMode` (`source-switch.ts`) is the one rule for projector and sender; with Xero `live` (the
  default/seed) Books takes nothing whatever `books_mode` says, and the sender is now idle exactly then (test red under
  mutation). README "Rehearsing Books for Bid beside legacy Xero" gives the procedure (`xero_mode = off` only means the new
  pipeline does not aim at Xero; legacy Xero keeps posting under its own settings; stop legacy Xero before Books `live`).
  Nothing can double post in this phase: only the dry-run adapter is built.
- **F4 — FIXED (by proof, not by relaxing the schema).** `bid_invoice_total_check` (`0319_bid_invoice.sql:33`,
  `total_pence > 0`, never relaxed since) refuses a 0p Bid invoice, and `invoice.raised` is written in the same transaction, so a
  0p event cannot exist; `totalPence: positive()` therefore matches the table. New integration test raises a 0p invoice: the
  check refuses it and no event is written. The schema comment says to relax both together if Bid ever allows 0p.
- **F5 — unchanged follow-ups** (lookup-path allocation check, `failed`/`needs_review` gauges, backfill of `skipped` flows,
  `legacy_total` treatment). Still not blockers for a dry run.

### New findings

- **R1 — LOW now, must be decided before `live` (cutover):** switching Books **off** also drops events that happened while it
  was **on** but were not yet projected. `moveToLatestEvent` jumps past events not yet queued (`queueConsumerDeliveries` takes
  100 per tick), and deliveries already queued are skipped by the switch read at processing time, not the switch at the event's
  time. In `dry_run` this loses nothing real. After `live`, a Books → Xero rollback would leave those invoices/payments in
  neither ledger unless legacy Xero picks them up. Fix before `live`: skip only events newer than the switch change (record the
  change time / switch history and compare with the event time), or drain before honouring "off".
- **R2 — LOW, cutover rule:** "events of a time Books was off are never replayed" holds for the event, not for what it names. A
  payment or refund after Books goes `live` re-registers the contact **and the invoice** in Books (that is what fixes F1), so an
  invoice raised and booked by Xero before cutover and paid after it is booked in both ledgers. Same mechanism, wanted for
  `dry_run → test_org`, unwanted for Xero → Books `live`. Needs an explicit cutover rule (e.g. open invoices at cutover stay in
  Xero, or are migrated deliberately) before `live`; not reachable in this PR (no writing adapter).
- **R3 — note:** each `register` re-reads the switch in its own transaction, so a switch flip in the middle of one event's
  projection can aim its contact and invoice at different targets. Fails safe (the provider refuses a missing contact, a later
  event re-registers the contact) and needs a person to flip the switch mid-tick; worth folding into R1's switch-history work.

### Re-check reasoning
F1–F4 are fixed at the right layer (database key, registry, projector cursor, one activation rule), each with tests that go red
when the fix is reverted, and all suites, typecheck, layer/deps lints and the real-Postgres integration and role contracts pass.

they belong on the pre-`live` list with F5.
