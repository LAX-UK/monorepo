## Findings

### F1 — High — `lint:layers` fails on the PR head
`apps/api/src/services/seller-proceeds/record-signed-agreement.integration.test.ts` imports the Identity-owned `user` table directly, which the Bid API Identity boundary check rejects. It was introduced in the last commit (`eeb701e0`); the PR body lists `lint:layers` as passing, which was true before that commit only. This gate will be red in CI.
Fix: create the staff user through the Identity directory / test helper the other API integration tests use, or move the seeding into a helper that is already allow-listed.

### F2 — Medium — Settlement confirm amount is not guaranteed to be what the run pays
The confirm dialog says "Pay £X to <seller> now?", where £X is the sum of the preview's ready lines. Two ways the run can pay something different:
1. **Released private-sale deals are paid by the run but not shown.** `createSettlementCore` adds a line for every released, unsettled deal for the legal entity; `previewSettlement` (and therefore `sales`/`totals`) never includes them. A seller with a released deal is paid more than the dialog states. Also, a seller with only released deals and no waiting payments lands on "nothing to settle" although a run would pay them. (The old preview had the same gap, but it did not promise an exact amount in a confirm.)
2. **No binding between preview and run.** The run re-reads pending sales under its lock and does not receive the amount (or the list of payment ids) the person confirmed. A sale that becomes ready between preview and confirm — for example because someone recorded its agreement from another tab — is paid without having been shown.
Fix: include deal lines in the preview (same source as the run), and pass the confirmed net (or confirmed payment ids) to the run and refuse with a "figures changed, review again" error on mismatch.

### F3 — Medium — "Already on record / Administrator only" is decided outside the transaction
`RecordSignedAgreementService.record` reads the lot facts (agreement soundness, held state, payout) before `unitOfWork`, and `DrizzleSignedAgreementWriter.recordSigned` then locks and updates whatever row exists. Consequences:
- Two quick submissions (double-click, two staff on the same held sale) by non-Administrators: both pass the "no sound agreement" check; if the first commits before the second's writer runs, the second **overwrites the just-recorded agreement in place without `replace` and without Administrator rights**, writing a second audit event. If both insert at the same time, the second hits `consignment_agreement_submission_id_uidx` and surfaces as an unmapped 500.
- If a settlement run pays the sale between the fact read and the reprice, `repriceHeld` no-ops (good) but the service still reports `releasedSellerTermsId`/`sellerNetPence` and the audit payload says the sale was released, although it was already paid by the run.
Money is not mis-paid in either case (the store guard and the run's snapshot pricing agree), but the Administrator-only rule is bypassable by timing and the audit trail can be wrong.
Fix: re-read the agreement row `FOR UPDATE` inside the transaction and re-apply the soundness/`replace`/Administrator check there; take the seller-terms row lock (or the per-entity settlement advisory lock, in the same order the run uses: advisory → payment → terms) before deciding "held"; map the unique violation to a 409.

### F4 — Medium — Replacing an agreement rewrites the row a priced snapshot points at
"Replace with a corrected agreement" updates the consignment's single `consignment_agreement` row in place (commission, signed date, `signed_document_id`, source). A sale already priced on that agreement keeps its snapshot figures (verified by the integration test: snapshot stays 12%, agreement now 15%), but its `agreement_id` now resolves to a row and PDF that no longer match the figures it was paid on. Staff screens that label a sale with its agreement reference/date will show the corrected agreement beside the old rate. The previous values survive only inside the audit event payload.
Fix (pick one): version agreements (insert a new row, mark the old one superseded) so snapshots keep pointing at what they were priced on; or store the agreement's commission/document id on the snapshot and show those, not the live row. At minimum, show "priced on an earlier version of this agreement" when the snapshot rate differs from the row.

### F5 — Low — Snapshot immutability guard in the store is untested
Removing `eq(saleSellerTerms.basis, "held")` from `repriceHeld`'s `WHERE` (with persistence rebuilt so API tests use it) leaves every test green, including both Postgres integration suites. The PR describes a "held-row reprice guard" test, but that test is stopped earlier by the service's own checks. This guard is what keeps a concurrently priced or paid snapshot from being rewritten (F3), so it should have a direct test.
Fix: a persistence integration test that calls `repriceHeld` on an `agreement`-basis row and asserts the row is unchanged and the current row is returned.

### F6 — Low — Signed agreement PDFs are not malware-scanned
Upload handling is otherwise sound: the type is checked by magic bytes in the validation worker (not just the extension), the 20 MB limit is enforced at presign, by the worker's object-size check against the declared size, and again in the service; the service requires kind, owner, `active` status and PDF. However `signed_consignment_agreement` is not in the worker's `MALWARE_SCAN_KINDS`. These files come from sellers (scanned or emailed paper) and are meant to be opened by staff and finance, the same threat model as `consignment_message_attachment`, which is scanned.
Fix: add the kind to `MALWARE_SCAN_KINDS`.
Also noted: the PDF is never linked or claimed after use, nothing in the UI lets staff open the stored PDF, and the same upload id can be attached to several lots by its owner. Consider marking the upload as claimed and adding a staff-only signed-URL view next to the agreement.

### F7 — Low — Success toast promises a payout that may not happen
`recordedToast` always says "Agreement recorded. Lot N joins the next payout." The API returns `sellerNetPence: null` when the sale stays held (VAT setting missing, deductions over the hammer) or was not held at all (Administrator correction of a priced sale), and the dialog ignores it.
Fix: show the release wording only when the API reports a released sale; otherwise show "Agreement recorded." plus the remaining held reason.

### F8 — Low — Two sums of the settlement lines
The API now returns `pending.totals` (`previewTotals`), and the web adds the lines up again in `sumReady`. They are the same today, but the PR's rule is that nothing is recomputed on screen and there should be a single source. Use the API's `totals` (and keep the "totals equal the lines" test on the API side).

### F9 — Low — "Paid under the old rule" export
- Read-only view, `requirePayoutRead` on the API; the CSV contains only columns already shown, and cells go through the shared formula-injection escaping. Fine.
- The export covers the current page (50 rows); the kit menu says "shown of total", so this is consistent with other lists, but finance will usually want every row for this review.
- Negative "Difference" values are written as `-12.34`, which the shared escaper prefixes with `'`, so the most important column becomes text in a spreadsheet for every underpaid/overpaid row. Consider exporting signed amounts in a form the escaper leaves numeric, or a separate direction column.
- `old-rule-review.vm.ts` formats with a local `(pence / 100).toFixed(2)` and `poundsToPence` returns 0 on a parse failure, silently writing £0.00 for bad data; prefer the shared money formatter and an explicit blank.

### F10 — Low — Finance notice
Per-person dismissal is a cookie keyed by a hash of the user id, capped at the 30-day window, with no PII in name or value — matches the PR notes. It is per browser rather than per person across devices (documented). The cookie is set without `Secure`; add it. The go-live constant is today's date, so the notice starts showing on merge day regardless of deploy date.

### F11 — Low — `SettlementBreakdown` has no automated accessibility test
The kit component is well covered (26 tests) and the `index.ts` change only adds exports (no other kit piece restyled). Axe was run only by hand on an uncommitted review route. Add an axe assertion to the component test, as other staff kit components do where available.

### F12 — Low — "Mark as settled outside LAX" can be repeated
`MarkSettledOutsideService` only publishes an audit event and does not check for an earlier one, so every click adds another `lot.seller_settled_outside_lax` event. Refuse (409) when the lot already has one.

### F13 — Nit — Process
- The PR body ends with an AI-attribution footer ("Generated by …" line), which the project rules say must not appear. Commits are clean.
- `signedOn` has no lower bound (any real date up to today is accepted).

### Verdict: FIX FIRST

Blocking: F1 (CI gate red). Should be fixed in this PR: F2 (confirmed amount can differ from what is paid) and F3 (Administrator-only replacement bypassable by timing; unmapped 500). F4 should at least get a decision before merge. The rest can follow.
