## Verdict: **FIX FIRST** (two small items)

Every earlier finding is fixed on the current head. The security properties on the checklist hold:

- The issuer enforces the limits itself.
- Refresh cannot outlive the absolute limit.
- The cap is race-safe and never ends the sign-in that triggered it.
- Takeover ignores records that are already over.
- The sweep uses its indexes.

I verified the issuer-side clamp end to end through Better Auth 1.6.22, not only through the unit-tested hook. No new security defect lets a record live longer than the design allows.

Two items block merge. Both fail closed and both are small:

- **N1 (Medium, correctness against SD8):** a staff member kept busy only through product refreshes is signed out 12 hours after their last *issuer* visit, even though they were active minutes earlier. The clamp sets `expires_at` to last use + idle, but the touch that records product use never moves `expires_at`. I reproduced this against PG16.
- **N2 (Low, checklist):** the 0365 migration test asserts that 0365 is the last journal entry, both positionally and by `when`. It will break when a later migration lands or when the stack is rebased onto main.

The remaining items are low or informational and can follow.

## New findings

### N1 (Medium, correctness, fails closed): staff are signed out 12 hours after their last issuer visit, not 12 hours after their last use

- **Files:**
  - `apps/auth/src/infrastructure/drizzle-session-activity.store.ts:15`: touch writes only `last_seen_at`.
  - `packages/auth/src/auth-hooks/session-hooks.ts:27-52` and `apps/auth/src/infrastructure/drizzle-session-expiry-clamp.ts:36-55`: `expires_at` is clamped to `lastActive + idle`. It moves forward only when Better Auth renews, which needs an issuer request.
  - `apps/auth/src/infrastructure/session-lifetime.sql.ts:34`: `sessionHasEnded` (and so `findLiveIdentitySession`, refresh) treats `expires_at <= now` as over.
- **Scenario:**
  1. A staff member signs in at T0. The create hook stores `expires_at = T0 + 12h`.
  2. They work in a product (bid or shop admin), which refreshes tokens through the issuer's token endpoint. Each refresh passes `SignInLivenessGuard`, which touches `last_seen_at`, but nothing moves `expires_at`.
  3. At T0 + 12h the refresh is refused, and the sweep's `expires_at` scan ends the record with back-channel logout, although the person was active an hour ago. The design is idle 12 h / absolute 24 h.
- **Reproduced:** a throwaway PG16 probe (removed). Clamp at T0, touch at T0 + 11h, then `findLiveIdentitySession` at T0 + 12h + 1m returned **null**, with `expires_at = T0 + 12h` and `last_seen_at = T0 + 11h`.
- **Who it affects:** clients are unaffected in practice. Their idle limit equals Better Auth's 7-day `expiresIn`, which was already measured from the last issuer renewal before this PR. For staff, this PR moved the effective idle measure from "last use" to "last issuer visit". It is not a security hole: it ends sessions early, never late. It does contradict SD8, and it will sign staff out mid-shift.
- **Fix:**
  - In `touch`, also roll `expires_at` forward under the same clamp, never past Better Auth's own window:
    `expires_at = GREATEST(expires_at, LEAST(now + expiresIn, now + idle(person), coalesce(signed_in_at, created_at) + absolute(person)))`.
    This can reuse `clampedExpiresAt` with the new `last_seen_at`. The update stays HOT, because `expires_at_id_idx` is indexed: if HOT matters, write it only when it moves by more than the throttle.
  - Add an integration test: staff, touch at T0 + 11h, still live at T0 + 12h + 1m, ended at T0 + 23h + 1m idle or at T0 + 24h.

### N2 (Low, checklist): the 0365 migration test asserts that 0365 is the last journal entry

- **File:** `packages/db/src/migration-0365-session-lifetime-indexes.test.ts:19-27`
- **Detail:**
  - `expect(entry.when).toBeGreaterThan(other.when)` for *every* other entry means "0365 is newest". It fails as soon as any later migration is journalled.
  - `entries[index - 1].tag === "0361_oauth_token_sign_in"` and `idx === prev + 1` fail as soon as the stack is rebased onto main: main's `0362_artwork_register_zoho_price` (`when 1806307200000`, idx 350) sorts between 0361 and 0365.
- **Fix:** assert only what must stay true:
  - 0365's `when` is strictly greater than 0361's (its base predecessor).
  - The whole journal's `when` values are strictly increasing.
  - `idx` values are unique.
  - Do not compare positions or test against "every other entry".

### N3 (Low): a record whose stored `expires_at` was never clamped gets one more request served when the renewal clamps it into the past

- **Files:** `packages/auth/src/auth-hooks/session-hooks.ts:27-52`. This is Better Auth `getSession` behaviour (`better-auth/dist/api/routes/session.mjs:222-245`, which returns the updated session without re-checking its expiry). The integration test `renews a record already past a limit to a time that has passed, so Better Auth refuses it` (`drizzle-session-lifetimes.integration.test.ts:726`) overstates the result: the *renewing* request is still served.
- **Reproduced:** a Better Auth 1.6.22 probe with a memory adapter and an `update.before` that returns a past `expiresAt`. The renewing `getSession` returned a session; the next returned null.
- **When it applies:**
  - Records written before this release. Their `expires_at` was never clamped to `signed_in_at + absolute`.
  - A client promoted to staff. Their stored `expires_at` used client limits.
  - Post-deploy records hold `expires_at ≤ lastActive + idle` and `≤ signedIn + absolute`, so the clamp can never land in the past for them.
- **Exposure:** one issuer request, which can include an `/oauth2/authorize` code. Until the sweep reaches the record, Better Auth also serves non-renewing requests: the absolute scan is on `session_signed_in_idx` and runs at up to 20 batches a minute.
- **Fix (pick one):**
  - At rollout, run a one-off batched `UPDATE session SET expires_at = <clampedExpiresAt>` so every existing row satisfies the invariant.
  - Or have `update.before` return `false` (Better Auth then treats the update as failed and answers 401) when the clamp is `<= now`.
  - Re-run the update on staff promotion, or rely on the sweep's staff scan, which is ≤1 minute.

### N4 (Info, performance): `findOverCap` scans every session row each minute, on every instance

- **File:** `apps/auth/src/infrastructure/drizzle-session-cap.store.ts:17-28`
- **Detail:** at 400k sessions, `EXPLAIN ANALYZE` shows an Index Only Scan of all 400,000 rows plus a GroupAggregate, ≈170 ms, run after every sweep. It is acceptable now.
- **Fix:** if it grows, restrict it to users who signed in recently, for example `WHERE coalesce(signed_in_at, created_at) > now() - interval '2 minutes'` on the new index, plus staff markers for promotions.

### N5 (Info): access tokens can outlive the absolute limit by their own TTL

An `/authorize` or refresh just before the limit issues an access token valid for its full TTL. This is by design, and refresh is refused afterwards. Mention it in `05-identity-flow.md` if it is not already there.

## Checklist

- **The issuer enforces idle and absolute limits itself: holds** (staff caveat in N1, legacy rows in N3).
  - I verified end to end that Better Auth 1.6.22 `getSession` sets `ctx.context.session` before `internalAdapter.updateSession`, and that `updateWithHooks` hands the ALS endpoint context to `session.update.before`. The probe hook received the right session id and data `[expiresAt, updatedAt]`, and the clamped value was stored.
  - Create is clamped. The takeover stamp is clamped with the carried `signed_in_at`.
  - `/update-session` cannot write the lifetime columns: they are not Better Auth additional fields, so `parseSessionInput` drops them.
  - The cookie cache checks the cached `expiresAt` too.
  - `RecentSessionGuard`, the refresh guard, takeover and touch all use the exact predicate.
- **Refresh cannot extend past the absolute limit: holds.**
  - `findLiveIdentitySession` uses `sessionIsLive` (`oidc-session-adapters.ts:85`).
  - Refresh only touches `last_seen_at`, and only while live; it never writes `signed_in_at` or `expires_at`.
  - `planTakeover` carries the minimum `signed_in_at` of *live* same-person records only.
- **Cap eviction is atomic under concurrent sign-ins: holds.**
  - The cap locks all of the person's rows `FOR UPDATE` in id order, and takeover locks in the same order.
  - Each sign-in enforces after its own insert has committed, so the later enforcer sees both inserts and the count converges to the cap: no lasting over-cap.
  - `keepSessionId` is excluded, and a concurrent fresh sign-in has the newest `lastActive`, so it is never the least recently used.
  - Eviction is scoped to `fresh.userId`.
  - A transient over-cap between insert and enforcement, or after a failed enforcement, is bounded by the next sweep (≤1 min) and alerted.
- **Takeover ignores expired or over records: holds** (M1 fix above).
- **The sweep uses its indexes: holds.**
  - Measured on PG16 with 400k client sessions and 50 staff:
    - `expires_at` scan: Index Scan on `session_expires_at_id_idx`, 0.03 ms.
    - Client absolute scan: Index Scan on `session_signed_in_idx`, 0.03 ms. The expression matches the index exactly.
    - Staff scan: marker seq scan (50 rows), then a nested Index Scan on `session_user_id_idx`.
  - Nothing indexes `last_seen_at`, so touches stay HOT.
  - The claim that "a client idle 7 days with live `expires_at` cannot arise" holds for clamped rows. Legacy rows fall back to `updated_at`, and Better Auth's expiry equals `updated_at + 7d`.
- **Times through @auction/datetime: holds** (not applicable).
  - The package covers calendar days, zones and formatting.
  - The PR does only fixed-duration arithmetic on UTC instants (12 h, 24 h, 7 × 24 h, 30 × 24 h). TypeScript and SQL agree (`make_interval(secs => …)`).
  - Clocks are injected everywhere, and there is no calendar or zone maths to route through the package.
- **Migration journal ordering: holds for the entry; the test does not.**
  - 0365 is idx 352, `when 1806566400000`. That comes after the base branch's last entry (0361, idx 351, `1806220800000`) and is strictly greater.
  - The journal is strictly increasing and the idx values are unique.
  - The test asserts last-entry: see N2.
