### Per finding

- **S1 (MEDIUM): fixed.**
  - **Signed out by the person or by a reset.** This covers signing a browser out from the devices list (`deleteSession`), "sign out everywhere else" (`deleteOtherSessions`), the support two-step reset and `revokeAllSessions` (`deleteAllSessions`), and a password reset (`createPasswordResetSessionRevoker`). In each case, the same transaction that deletes the session:
    - deletes the browser's marker row in `auth_known_device`, keyed by the session's `device_hash`;
    - writes an "owes a notice" row (`fingerprintMarkerOwingNotice`).
    - The next sign-in from that browser is therefore emailed **even though its label and country were seen minutes ago**. Forgetting the marker on its own would not be enough, because the label rule would still say "known". After the email is queued, the owing row is cleared.
    - Code: `retireRevokedBrowserMarkers` (`apps/auth/src/infrastructure/drizzle-known-device.store.ts`) and `DrizzleIdentitySessionRepository`.
  - **Sign-out from the browser itself** (the issuer's `/sign-out`, which RP-initiated logout also uses): a new `databaseHooks.session.delete.after` (`packages/auth/src/auth-hooks/session-hooks.ts`) forgets that browser's marker, read from the request's own cookie.
    - It applies only on path `/sign-out`. For example, a password change that ends *other* sessions runs in the browser that stays, so it must not forget that browser.
    - No owing row is written here, because a person signing themselves out is not news. The 90-day label rule decides the next sign-in.
    - A failure is logged as `device_marker_forget_failed` and never fails the sign-out.
  - **`hasSeen` now applies the 90-day `KNOWN_DEVICE_WINDOW_MS` window** (`lastSeenAt >= at - 90d`).
  - **Integration test:** `apps/auth/src/infrastructure/known-device-sign-out.integration.test.ts`, real Postgres, 4 tests. It also passes as `auth_app`.
    - Devices list: sign in from X (email), sign in from X again (quiet), sign X out, sign in from X again → **email**, then quiet.
    - "Sign out everywhere else": X is emailed again. The kept laptop stays known.
    - Password reset: the next sign-in from X is emailed.
    - Self sign-out: the marker row is forgotten, and the label rule then decides (quiet).
  - **Unit tests:** `session-hooks.test.ts` (3 new) and the store window and forget tests in `drizzle-security-notices.integration.test.ts`.

### Finding

**B1 (LOW, existed before this PR, follow-up): the opposite ordering. A raise that commits after the buyer default read its facts leaves a pending payment and a payment-due notice on a defaulted lot.**
- **Where:**
  - `apps/api/.../buyer-default.service.ts:79` (`readFacts`, which runs outside the transaction) and `:122` (`paymentId: facts.payment?.id ?? null`)
  - `packages/persistence/src/repositories/drizzle-buyer-default.repository.ts:133-140` (only `input.paymentId` is voided)
- **Scenario:**
  1. The lot has no payment yet, for example because the lot-end raise was skipped or failed.
  2. Staff submit a default, and `readFacts` sees no payment.
  3. A checkout, the cron or the projector raises and commits an invoice and a pending payment.
  4. The default transaction locks the lot. The winner and account still match, so it passes. It voids the invoice, but it leaves the new pending payment, because `paymentId` is null.
- **Reproduced against Postgres** with a scratch test (not committed): `{outcome:"recorded", winner:null, invoices:[voided], payments:["pending"], staged:1}`. On the checkout path, the request that won the raise then goes on to open a Stripe checkout (`create-pending-for-winner.pipeline.ts:575`).
- **How likely:** the window is milliseconds.
- **Fix:** in `DrizzleBuyerDefaultRepository.record`, after the lot lock, read the open payments for `(lot_id, buyer_legal_entity_id)` again. Refuse with `BuyerDefaultConflictError` if any open payment other than `input.paymentId` exists (or cancel every `pending` one). Add an integration test that raises, then records the default with stale facts, and expects a conflict or no open payment.
