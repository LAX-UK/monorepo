## Findings

### F1. `api_app` gets ALL on the token table. **High, blocking.**
- **Where:** `packages/db/src/migrate-roles.ts:508-512` (the `WORKER_ZOHO_BOOKS_TABLES` doc comment) and
  the `api_app` loop at `migrate-roles.ts:~1002` (default: every table not in `API_DENY_TABLES`
  gets everything). The test `packages/db/src/migration-0369-zoho-books-connection.test.ts:63-70` only
  checks the worker side.
- **Scenario:** the comment says "Only the worker ... may read and change them ... No other role is
  granted anything". In fact `db:roles` gives the internet-facing API role SELECT, DELETE and
  TRUNCATE on the sealed refresh tokens (see the table above). Any SQL injection or bug in the API
  can read every Books refresh-token envelope, or delete/truncate the connections. Then every org
  has to be re-authorised. The tokens are sealed, so this is not plaintext exposure. But the API
  process is also likely to hold the envelope key that opens them, because Xero sealing uses the same
  envelope there. So the sealing alone is not a real boundary.
- **Fix:** add `"zoho_books_connection"` to `API_DENY_TABLES` (nothing in the API uses it yet). Add
  role-contract assertions that `api_app`, `shop_app` and `auth_app` have no table privilege on it.
  `api_app` is the one that matters, because it is a default grant. If the staff "connect Books"
  flow later lives in the API, grant only what it needs, e.g. column-level
  `INSERT/UPDATE (organization_id, refresh_token_sealed, connection_status, last_refresh_error_code, updated_at)`
  and no SELECT on the sealed columns, and never DELETE/TRUNCATE. Also correct the doc comment.

### F2. `markNeedsReauth` can flag a freshly reconnected org as broken. **Medium.**
- **Where:** `packages/accounting-zoho-books/src/token-manager.ts:173-177`; the port in `src/ports.ts:41-55`.
- **Scenario:** process A loads the old refresh token (R1) and starts a refresh. Meanwhile staff
  reconnect the org: `saveConnection` writes R2 with status `healthy`. Zoho revokes R1, so A gets
  `invalid_grant` and calls `markNeedsReauth(org, ...)`. That overwrites the healthy R2 row with
  `needs_reauth`, and every later call fails `reauth_required` until someone reconnects again.
  `saveRefreshed` has the same last-writer-wins shape.
- **Fix:** make these compare-and-set. Pass the sealed refresh token that was used (or a row
  version / `updated_at`) to `markNeedsReauth` and `saveRefreshed`. The adapter then updates
  `WHERE organization_id = $1 AND refresh_token_sealed = $used`. Add a contract test in
  `src/testing/contract.ts` so every store adapter must honour it.

### F3. The token endpoint is retried after a timeout. **Low.**
- **Where:** `token-manager.ts:213-238` (`sendWithRetry`, "safe to repeat").
- **Scenario:** a refresh POST times out after Zoho has minted a token, and it is retried up to 3
  times. Zoho caps how many access tokens one refresh token may mint in a window, so a timeout storm
  across replicas can hit that cap. If Zoho ever rotates the refresh token, a lost response burns it.
  The code supports rotation, so the "safe to repeat" claim is only true while Zoho does not rotate.
- **Fix:** retry only connection failures that happen before the request is sent. Treat a timeout as
  one failed refresh and let the next call refresh again. Or keep the retry, but soften the comment
  and count the extra attempts in a metric.

### F4. Single-flight, rate, concurrency and budget only work within one process. **Low now. Must-do in the runtime PR.**
- **Where:** `token-manager.ts:43-48` (says the cross-process lock is "the store's job (an advisory
  lock in the adapter's runtime)"); `call-budget.ts:3-6` (`InMemoryCallBudget` is the default in
  `client.ts:88`); `gate.ts` (per-process window).
- **Scenario:** with N worker replicas, Zoho's per-org 100/min and the daily budget become N×.
  Refreshes are not single-flight across processes. Restarts reset the daily budget.
- **Fix:** before production use, the runtime PR must supply a shared `CallBudget` (DB/Redis,
  fail-closed as documented) and a cross-process refresh lock (e.g. `pg_advisory_xact_lock` on
  the org row). It should also refuse to build `ZohoBooksClient` without an explicit `budget` when
  `NODE_ENV=production`, so the in-memory default cannot ship by accident. Checked within one
  process: the gate, the budget and the per-org single-flight are race-free. The gate uses FIFO
  hand-over and a serialised rate tail, budget `consume` is synchronous, and concurrent 401s share
  one refresh (`getAccessToken` with `rejected`).

### F5. `expires_in` units. **Low.**
- **Where:** `token-manager.ts:181`.
- **Scenario:** older Zoho accounts responses send `expires_in` in **milliseconds** next to
  `expires_in_sec`. If only `expires_in` (ms) is present, the token is cached for the 24h cap
  instead of 1h. After that, each expiry costs one 401 and a refresh/replay. It recovers, but wastes
  budget and logs warnings.
- **Fix:** prefer `expires_in_sec`, and treat `expires_in > 86_400` as milliseconds. Or cap the
  lifetime at 3600s, which is Zoho's documented lifetime.

### F6. Dead retry branch. **Nit.**
- **Where:** `client.ts:338-339`. `shouldRetry` matches `unknown` + `request_timeout`, but a timeout from
  `sendWithTimeout` is `ZohoNetworkError{code:"timeout"}` (`http.ts:24`). Only an HTTP 408 produces
  `request_timeout`. The behaviour is right (GET timeouts are retried as `network`; a 408 GET is
  retried), but the comment at `client.ts:71-74` should say "408", not "timeouts".

### F7. Log scrubbing hides Zoho ids. **Nit.**
- **Where:** `redact.ts:66` `LONG_DIGITS`. `redactingLogger` scrubs every log string, including `path`. So
  `/invoices/460000000012345` is logged as `/invoices/[number]`, which loses the id you need for
  support. Consider not scrubbing `path`: it is already restricted by `PATH_PATTERN` and holds ids,
  not PII.
