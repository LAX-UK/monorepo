### F1 (blocking): a re-raise against a live `legacy_total` invoice now throws, so the buyer cannot pay

- **Where:** `packages/finance-runtime/src/seller-terms-at-raise.ts:64` calls `hammerAndPremiumOf()`, which throws `InvoiceInvariantError` when an invoice has no `hammer` line (lines 32-43). Both pipelines call it with no handler:
  - `apps/api/src/services/payment/create-pending-for-winner.pipeline.ts:313`
  - `packages/finance-runtime/src/lot-invoice-initiation.service.ts:191`
- **Scenario:**
  1. Migration 0319 backfilled some invoices with one `legacy_total` line, where the payment total was below `lot.current_price`. Those invoices are still live: `voided_at` is null.
  2. The buyer's payment on such an invoice expires.
  3. The buyer returns to checkout, or lot end or the sweep runs `ensureForLot`.
  4. `InvoiceRaiser.price()` correctly returns the stored lines (`invoice-raiser.ts`, `existing`), which here are just `[legacy_total]`.
  5. `forInvoice` throws. The API returns a generic 500 and the worker job retries for ever.
- **Impact:** before this PR, these lots raised a payment, because the legacy fee needs only the total. That breaks the rule that the buyer's payment is unchanged in this PR. The unit test `seller-terms-at-raise.test.ts:55` asserts the throw, so this was intended for the helper, but neither pipeline handles it.
- **Fix:** do not refuse the raise; store a **held** snapshot instead.
  - Add a held reason such as `no_hammer_line` (or `legacy_invoice`) to `SellerTermsHeldReason`, `sale_seller_terms_held_reason_ck` (0372), and the re-offer `HELD_MESSAGES` map.
  - In `SellerTermsAtRaiseService.forInvoice`, return `{basis:'held', heldReason:'no_hammer_line', hammerPence:0, premiumPence:0}` when there is no hammer line, still computing the legacy fee on the total.
  - Add an integration case to both pipelines: a live legacy_total invoice with an expired payment, then a re-raise.
  - The alternative is to show that prod has no live legacy_total invoice without an open payment. If you go that way, document it and turn the throw into a typed error that both pipelines report, not a 500 or an endless retry.

### Checked and correct

- **Arithmetic** (`packages/domain/src/seller-proceeds.ts:65-68`, `vatForLine` in `accounting-domain/src/money.ts:36-50`):
  - Integer half-up `floor((x*bps+5000)/10000)` with no float step.
  - Commission is on the hammer only; VAT is on the commission; net = hammer − commission − VAT.
  - Negative net is held; 0% gives 0 commission; 100% with VAT is held as negative_net.
  - I probed these values:

    | Hammer | Rate | Result |
    |---|---|---|
    | 4p | 12.5% | commission 1 (0.5 rounds up) |
    | 3p | 12.5% | commission 0 |
    | 25p | 10% | commission 3, VAT 1 (0.6 rounds up), net 21 |
    | 333p | 12.5% | commission 42, VAT 8, net 283 |
    | 1001p | 15% | commission 150, VAT 30, net 821 |
    | £1000 | 83.33% | net 4p |
    | £1000 | 83.34% | held negative_net (standard VAT); not_registered gives net 16660 |
    | £1bn | 12.5% | exact (hammer × bps = 1e15, inside safe integers) |
    | £1bn + 1p | any | RangeError; unreachable because the payment-tier limit is checked first in both paths |

  - `commissionPercentToBps`: "12.5" and "12.50" give 1250; "100.00" gives 10000; "100.01", "-1", "12.505" and null give null, so the sale is held as no_commission. No 5% fallback appears anywhere in the new path.
- **Atomic and idempotent:**
  - The terms row is inserted inside the same `db.transaction` as the invoice and payment (`drizzle-bid-invoice.repository.ts:210`).
  - A failed raise stores neither the payment nor the terms (integration test). There is one row per payment (unique `payment_id`).
  - A retry or re-raise on a live invoice gets a new payment with its own terms, priced from that invoice's **stored** lines: `price()` returns `existing.lines`.
  - Both pipelines are covered by tests, and the API's joined path reuses the existing payment.
- **Held reasons:** the order is LAX-owned, then agreement presence, then other_seller, then not_accepted, then no_commission, then VAT setting, then negative_net. Each has an integration test, and the invoice is still raised.
- **LAX-owned:** detected from `legal_entity.subkind = 'lax_stock'` (`drizzle-seller-terms-facts.reader.ts:26-33`), never from config. It gives no commission and no figures, and the shape check enforces that. The `REOFFER_LAX_OWNED_SELLER_ENTITY_IDS` env var was removed; zod strips unknown variables, so a deployment that still sets it does not crash.
- **Re-offer:** `reoffer-seller-proceeds.ts` prices through `SellerTermsPolicy`, so it uses `sellerProceeds`. A held sale throws `ReofferError('seller_terms_unavailable')` (409) with a reason-specific message, and it does so **before** `offers.create`, so nothing is written. LAX-owned gives proceeds of 0.
- **Buyer and platform_fee unchanged:** `platformFee` is still `PlatformFeePolicy.computePlatformFeeFromPence(seller, totalPence)` in both paths, and the integration test asserts this.
- **Grants:**
  - api_app and worker_app get only INSERT and SELECT on `sale_seller_terms`; I checked live that UPDATE and DELETE are false. Both get SELECT only on `bid_finance_setting`.
  - No other app role has access, and Shop is excluded. Contract tests cover all of this.
- **`bid_finance_setting`:** seeded with `standard` using `ON CONFLICT DO NOTHING`. If the row is missing or the value is unknown, the reader returns null and sales are held as `vat_setting_missing` while the invoice is still raised (tested). The CHECK constraints restrict both key and value.
- **DB shape check:** the agreement row must satisfy hammer − commission − VAT = net, net ≥ 0, VAT = 0 unless standard, and other_charges = []. Held and LAX-owned rows carry no figures.

### Minor (non-blocking; suggest folding into this PR or PR 2)

1. **The drift-guard lint is narrow** (`scripts/check-seller-commission.mjs:28-34`). It only flags one-line `<…hammer…> * <…commission|bps…>`. It does not catch:
   - `packages/domain/src/private-sale-deal/money.ts:12` (`amountMinor * bps`). This is a second commission calculator for private sales; arguably out of scope, but the lint cannot see it.
   - The deleted fallback shape `Math.round(amountPence * 0.05)`.
   - Expressions split across lines, and SQL.

   Suggestion: also flag `* 0.05`, `/ 10_?000` next to `bps` outside an allowlist (the calculator, `money.ts`, the platform-fee policy, private-sale), and scan `.sql` views.
2. **The agreement lookup ignores the seller in SQL** (`drizzle-seller-terms-facts.reader.ts:35-52`). `item_submission.converted_lot_id` is not unique. If two submissions point at one lot, the most recently accepted agreement wins whoever's it is, and the sale is held as `other_seller` even when an accepted agreement from the same seller exists. Suggestion: order `legal_entity_id = :seller` first, or filter on it, keeping `other_seller` for when none match.
3. **Worker SELECT on `consignment_agreement` is table-wide** (`migrate-roles.ts:366`). That includes `reserve_price`, the estimates, `record_reason` and `signed_document_id`. The rule needs only `id, submission_id, legal_entity_id, accepted_at, proposed_at, commission_percent`, so a column-level grant is possible and would match the "least privilege" brief.
4. **`sale_seller_terms.legacy_platform_fee_pence` is never written** (0372 line 24; `seller-terms-row.ts` leaves it out; the test expects null). Either write the legacy fee there now, so PR 2 can reconcile old against new per sale, or drop the column until it is needed.
5. **The facts and VAT setting are read outside the raise transaction**, on `db`, not on `tx`. The window is tiny and the snapshot still matches what was read, so this is acceptable. A comment saying so would help.
6. **No backfill for payments raised before deploy.** PR 2's settlement must treat a missing terms row as held, never as 5%, and must pick the row of the live payment, not of an expired earlier one on the same lot.
7. **Timing of acceptance:** an agreement accepted *after* the hammer still prices the sale. If the owner wants only agreements accepted before lot end, this needs a check.
