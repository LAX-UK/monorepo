## Verdict: SHIP

The PR's own code keeps every money rule. I found nothing in the diff that has to change before merge. The worker
never charges, never awards, and never sets `reawarded_at`. An expired offer can never be re-awarded, and an
accept racing an expiry settles exactly once. One **medium** hazard needs a follow-up ticket before this sweep
sees real volume. It is a stale read in the finance runtime's `ensureForLot`, which existed before this PR. The
PR makes it reachable through a new caller, on exactly the lots most likely to be defaulted a second time
(finding F1).

## Findings

### F1: MEDIUM (existed before this PR, newly reachable). A stale-read invoice after a second default leaves a live pending payment for the defaulter

- **Where:** `apps/worker/src/jobs/reoffer-sweep.ts:85-92` calls `ensureForLot`. The cause is in `packages/finance-runtime/src/lot-invoice-initiation.service.ts:124-212`: it reads the lot through `lots.findById`, with no lock. `packages/persistence/src/repositories/drizzle-bid-invoice.repository.ts:130` (`raise`) then inserts the invoice and payment without locking or re-checking `lot.winner_id` / `buyer_legal_entity_id`.
- **Scenario (reproduced against real rows as `worker_app`):**
  1. The sweep lists re-awarded lot L (winner B, no invoice).
  2. `ensureForLot` reads L with winner B.
  3. Staff record a default against B. `paymentId` is null because no invoice exists. `DrizzleBuyerDefaultRepository.record` locks L, voids B's live invoices (none exist) and clears the winner. It commits.
  4. `ensureForLot` carries on with its stale lot and raises a live `bid_invoice` and a **`pending` payment for B**, then stages B's "payment due" notice.

  Probe output: `lot { winnerId: null } payments [ { status: 'pending', buyer: 'defaulter(B)' } ]`.

  `pending` is not `paymentIsPaidOrBeingPaid`, so the next re-offer and re-award to C are not blocked. C is then invoiced as well. B holds a live invoice for a lot they no longer own and could pay it. That is a double collection on one lot.
- **Likelihood:** low. It needs a staff default on a lot whose invoice was missed, landing inside the window between `ensureForLot`'s read and its insert. The general `ensure-lot-invoices` cron already has the same race for first defaults. But this sweep exists for re-awarded lots, and those are the population that gets defaulted again.
- **Fix:** follow-up in finance-runtime/persistence; the PR can merge first. Inside the `raise` transaction, run `SELECT … FROM lot WHERE id = $1 FOR UPDATE` (lot lock first, the same order as default and re-award). Require `winner_id = paidByUserId` and `buyer_legal_entity_id = buyerLegalEntityId`, and `status = 'ended'`. Otherwise throw a "lot moved" error, which `ensureForLot` maps to `{ created: false, reason: "lot_moved" }`. Add an integration test for the interleaving above. Check that `worker_app` keeps the UPDATE column grant on `lot` that `FOR UPDATE` needs (it has one today).

### F2: LOW. `acceptedWithoutInvoice` keeps re-listing rows that can never be raised

- **Where:** `packages/persistence/src/repositories/drizzle-reoffer-sweep.reader.ts:40-76`
- **Scenario:** the query has no `lotNotDeleted()`, but `ensureForLot` goes through `lots.findById`, which does filter deleted lots. A soft-deleted re-awarded lot therefore comes back as `lot_not_found` every 15 minutes, forever. The same happens with `payment_amount_exceeds_limit`, `missing_seller_legal_entity` and `invalid_payment_amount`. These rows are not failures, so nothing alerts on them. They are ordered `reawarded_at ASC` with `LIMIT 200`, so once 200 dead rows pile up they would crowd out new missed invoices.
- **Fix:** add `lotNotDeleted()` to the query. Log or alert on any non-`raised` outcome. Consider marking dead rows, or ordering by `reawarded_at DESC`.

### F3: LOW. The missed-invoice query does not pin the lot's buyer account and matches payments of any status

- **Where:** `drizzle-reoffer-sweep.reader.ts:57-71`
- **Scenario:** the query checks `lot.winner_id = offered_user_id`, but not `lot.buyer_legal_entity_id = offered_legal_entity_id`. `ensureForLot` invoices `lot.buyer_legal_entity_id`. Today re-award sets both values and default clears both, so they cannot drift. Any future flow that changes the buying account would make the listing and the invoice disagree. Separately, `NOT EXISTS` matches a payment in any status, including `cancelled` or `failed`. An earlier dead payment for the same account on this lot would hide a genuinely missed invoice forever. That fails safe (no charge), but the invoice is silently never raised.
- **Fix:** add `eq(lot.buyerLegalEntityId, lotReoffer.offeredLegalEntityId)`. Restrict `NOT EXISTS` to open statuses plus `refunded`, matching `findOpenByLotAndBuyerAccount` and `findRefundedByLotAndBuyerAccount`, so the listing and `ensureForLot` agree.

### F4: LOW / INFO. The seller reminder time is recomputed from `requestedAt`, not taken from the stored deadline

- **Where:** `packages/domain/src/reoffer-sweep.ts:33`
- **Scenario:** the lapse time uses the stored `due_at`, but the reminder uses `sellerConsentWindow(requestedAt).reminderAt`. If staff ever change `due_at` (or a calendar change shifts working days), the reminder can fall after the deadline (so no reminder is sent) or well before it. Silence still means no, so this is not a money issue.
- **Fix:** store `remind_at`, or derive the reminder as one working day before the stored `due_at`.

### F5: INFO

- `offerReminderCopy` hard-codes "ends tomorrow". If the worker is down and the sweep runs after midnight on the last day, the title is wrong. The body states the correct time.
- `OutboxReofferNotices.toAccount` reads recipients on a separate pool connection while holding the lot and offer row locks. This is fine at a batch size of 200. Worth knowing if the pool gets tight.
- The job fails when `failed > 0`, and BullMQ then retries the whole sweep (3 attempts). This is safe because every step is idempotent.

## `ensureForLot` idempotency under concurrency

Two concurrent `ensureForLot` calls for the same lot and account are safe:
- `bid_invoice` uses `ON CONFLICT DO NOTHING` on the partial unique index `(lot_id, buyer_legal_entity_id) WHERE voided_at IS NULL`.
- `payment` has the partial unique indexes `payment_lot_buyer_open_unique` and `payment_lot_buyer_open_account_unique` over `pending`, `authorized`, `captured` and `requires_manual_review`. The loser gets `isOpenPaymentUniqueViolation` and returns `payment_already_exists`.

It is idempotent against itself. It is **not** safe against a concurrent default (F1).
