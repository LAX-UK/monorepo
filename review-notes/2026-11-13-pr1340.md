## What is good

- **N2 is sound and fails closed in every configuration I could construct.** The ways to misconfigure it, and what happens:
  - binding unset or empty: nothing is bound, so every `test_org`/`live` document is refused and held;
  - unknown mode or product, or a blank, padded or non-string id: start-up error;
  - id that is not the configured organisation for the product's entity: start-up error;
  - live organisation bound to `test_org`, or the reverse: start-up error (environment check);
  - same id in both modes: start-up error;
  - a typo in the variable name: it is unset, so nothing is bound;
  - invalid JSON: start-up error.
- A `test_org`/`live` document whose adapter reports `none` (a rehearsal adapter) is refused. A `dry_run` document whose
  adapter reports any organisation is refused, so the real Books adapter (which always reports one) can never serve
  `dry_run`.
- The check runs **before** the send and before the lookup. The lookup check matters too: a lookup in a foreign
  organisation could adopt someone else's document.
- A refused document goes to a person (`needs_review`) with a precise reason and is never requeued on its own.
- **Mode switch mid-flight:** the mode is fixed per document (`target.mode`). The ports and the binding are chosen from it,
  not from the current setting, and the binding is read once at start-up, so nothing changes between the check and the call.
- **Cached token for another org:** the client keys tokens, limits and budget per `organizationId`. That id comes from the
  same `orgs` the destination is computed from (`orgFor`), and the contract pins the destination to the fixture
  organisation per product (M15 is caught).
- **N1, synchronous path:** the writer returns `differs` (never `rejected`) for a fresh create or an adopt that reads back
  different. The domain now checks `differs` before the lease check, so a late but still-leased answer is held as
  `needs_review` with Books' id, `lookup: "clear"`. `requeue` refuses a record with `issued !== null`, so it is never
  recreated. This is tested at three levels (domain, in-memory sender, Postgres sender) and M1 is caught at all three.
- Layering is respected:
  - the policy (`checkDestination`, `parseDestinationBinding`) and the port (`DestinationPort`) live in
    `accounting-domain` with no I/O;
  - the Books knowledge (`booksDestination`, `parseBooksDestinationBinding`) lives in the adapter package;
  - the worker only orchestrates.
  
  The new port is a small single-purpose interface. `SenderPorts`/`AccountingPorts` are extended, not reshaped.
- Nothing in the monorepo builds `test_org`/`live` ports yet (`byMode` is `dry_run` only), so N2 is a guard that is in place
  before it is needed.

## Findings

### F1 — HIGH (money correctness; N1 only half closed): a differing read-back is recorded as `issued` whenever the answer does not reach `completeSending` on the original lease

- Where: `packages/accounting-domain/src/lifecycle.ts` `completeSending` (checks the token and `status === "sending"` before
  `differs`), `applyLookup` → `acceptProviderDocument` (totals only); `packages/accounting-zoho-books/src/adapter/lookup.ts`
  `findByReference` (no `verify`); `DocumentLookupPort` has no `differs` outcome.
- **Path A, the lease is swept while the send is in flight.** Any other claimer (a second replica, or the old and new worker
  during a deploy) runs `claimNext`, which turns an expired `sending` row into `unknown` (`expire_lease`). The late
  `differs` answer then hits `wrongState`, and the sender only logs `accounting_sender_complete_refused`. After the settle
  grace the lookup finds the payment, `acceptProviderDocument` compares totals only, and the record becomes **`issued`**.
- **Reproduced (probe P1, in-memory store):** the payment `recordPayment` moves time past the lease and calls
  `store.claimNext(...)` as another worker would, then returns `differs` (`zoho_books_payment_mismatch`). The record went
  `unknown`, then after the next tick `{"status":"issued","issued":{"providerId":"7000000000009",…}}`.
- **Path B, the lost answer.** The POST commits in Books but the reply times out, drops, or is unreadable
  (`zoho_books_unreadable_document`), or `sendThrough` throws after the POST. The record becomes `unknown`, the lookup finds
  the document, and it becomes `issued`. Again the `paymentMatches` checks (customer, date, currency, per-invoice
  allocation) never run.
- The contract encodes this gap: `adapter-contract.ts` "a payment Books makes but reads back different…" asserts that
  `lookup.findByReference` returns `found` for the differing payment.
- Impact: no duplicate is made (the identity is adopted). But a payment applied to the wrong invoice, date or customer is
  recorded in LAX as cleanly issued, and nobody is asked. Lost answers are the usual reason a record is `unknown`, so this is
  the common failure path, not an edge case. While the README still lists the read-back field names
  (`invoices[].amount_applied`, …) as unconfirmed, the outcome depends on the path: the same payment is `needs_review` on
  the synchronous path and `issued` on the timeout path.
- The PR's own text overstates the guarantee: the README row says "even when the answer arrives after the lease", and
  `lifecycle.ts` says "lease or no lease". Both hold only while the lease has expired but nobody has swept it.
- Fix (domain port change; the owners decide the shape):
  1. Let the lookup verify, either by `findByReference(product, kind, reference, expected document)` or by a Books lookup that
     runs the kind's `verify`.
  2. Add `LookupOutcome` `differs`, so that `applyLookup` → `holdDifferingDocument`.
  3. Add a sender test for each path: a swept lease and a lost answer. P1 can serve as the swept-lease case.
  4. Until then, correct the README and the comment so they describe only the narrower guarantee.

### F2 — MEDIUM (duplicates; existed before this PR, in scope): nothing ties the Books write to the lease, so a POST can start after the lease has been swept and the record requeued

- Where: `SENDER_LEASE_MS = 2 min` (`accounting-sender.service.ts:21`) and `SETTLE_GRACE_MS = 60 s`. In the client, a call can
  run for longer than that before the POST goes out:
  - `requestTimeoutMs` defaults to 15 s and may be set up to 120 s;
  - `maxAttempts` defaults to 3 and may be set up to 6;
  - `maxRetryAfterMs` defaults to 30 s and may be set up to 600 s, for 429 retries of the POST;
  - the per-organisation concurrency gate (`gate.acquire`) waits with no limit;
  - the dependency GETs (contact or invoice resolution) all run before the POST.
- Scenario (needs two claimers, as in F1): A's document waits on the rate limit or gate past `lease + grace`. B sweeps it, then:
  1. The lookup says `not_found`, because nothing has been posted yet.
  2. The record goes back to `pending`, and B claims it and POSTs.
  3. A's POST then also goes out.
  
  Two creates are now in flight. **Only** the Books unique custom field plus the configured `duplicateValueZohoCodes`
  prevent a second document, and both are still listed as unconfirmed in the README (open items from PR #1321).
- Fix (before any test-org send): pass a deadline, the lease expiry minus a margin, through the ports into the client, and
  refuse to *start* a POST/PUT after it. That refusal is known-not-sent, so it can be `rejected` with a transient
  prefix. Also validate at start-up that `requestTimeoutMs` (and the 429 wait) fit inside the lease. Confirm in the test
  organisation that a second create with the same reference is refused with the configured code.

### F3 — LOW (wrong org): the environment of an organisation is self-declared, so the binding is two hand-typed copies of the same id

- `parseBooksDestinationBinding` checks `ZOHO_BOOKS_DESTINATIONS` against `ZOHO_BOOKS_ORG_CONFIG`: the same id, and
  `environment: "test"`. Both values are typed by the same person. If the live organisation is entered in the org config with
  `environment: "test"` and the same id is put under `test_org`, every check passes and test sends go to the real books.
  The binding does stop the common mistakes (a typo, a mode label, a second org config), and that is real value.
- Fix (wiring PR): before the first write in a process, `GET /organizations/{id}` and compare its name or currency with an
  expected value in the binding, or refuse when it is not marked as a sandbox or test company. Keep the live org config
  out of every non-production deployment.

### F4 — LOW (robustness): `holdUnsent` is two transitions (`complete_sending: rejected` → `failed`, then `escalate`), not one

- If the second `apply` is refused or the process dies between them, the record sits as `failed`. `settle` then requeues
  it, it is claimed, the check fails again, and the loop repeats until `attemptsExhausted`. It never sends (M4 shows the
  tests notice it), but it uses up attempts. It also puts a provider-style `failed` row in the history, while
  `lifecycle.ts` documents `failed` as "the provider refused it outright". A single domain transition `sending → needs_review`
  (not sent, `issued: null`) would make the hold one atomic step.

### F5 — LOW (test quality)

- The contract case above (F1) asserts the gap, a lookup that returns `found` for a differing payment. Change it to expect
  `differs` once F1 is fixed.
- There is no sender test for a swept lease or a lost answer followed by a differing document (F1), or for a POST that
  would start after the lease (F2).
- The integration `beforeEach` cancels only `pending`/`sending` rows. `failed`/`unknown` rows left by earlier runs are
  settled by later runs (`settleDue`), so cases can interfere. During the mutation runs, one integration case failed under a
  mutant that cannot reach it (M7, a dry-run case), after earlier mutants had left 12 `failed` rows behind. It passed 3/3 on
  clean code. Cancel or scope those rows per case as well.

### F6 — INFO

- A bad `ZOHO_BOOKS_DESTINATIONS` throws while the worker container is built, so the whole worker fails to start, not just
  accounting. That is fail-closed and acceptable, but say so in the deploy runbook.
- `ZOHO_BOOKS_DESTINATIONS` is documented in `env.ts` and the domain README, but not in any env example or runbook.
- Every org-binding check runs on an object the adapter itself reports (`destinationFor`). The adapter computes it from the
  same `orgs` the gateways use, and M15 is caught, so it is consistent today. Keep `booksDestination` and the gateways on
  one `orgs` instance in the wiring PR, so the two cannot drift apart.

## Verdict reasoning

N2 does what it says. Every way I tried to point a send at the wrong organisation either fails at start-up or is refused
and held before any call, and dry run cannot resolve to an organisation. Each of the 16 behavioural mutants is caught.

N1 is closed only for an answer that comes back on its own lease. When the lease is swept, or the answer is lost (the usual
reason a record is `unknown`), the differing document is adopted by a totals-only lookup and recorded as **`issued`**.
That is silent and reproduced (F1). It is worse than the original N1, which at least showed `failed`. The PR's README
and comments promise more than the code delivers. No new duplicate path was introduced. F2 is an existing window in which
the only duplicate guard is a Books behaviour that has not yet been confirmed.

The PR's stated purpose is to make test-org sends safe. F1 should be fixed, or at minimum the claim corrected and F1/F2
made explicit blockers of the test-org wiring PR, before this merges as "N1 done".

### Verdict: FIX FIRST
