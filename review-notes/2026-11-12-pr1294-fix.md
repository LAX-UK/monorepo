# PR #1294 fix review (security): staff sign-in renewal loop

- Scope: `git diff 162a5d1c..origin/sd3-session-lifetimes-cap`, one commit `4ee0f9d9` ("Sign-in: reading who a cookie signs in no longer renews the record"), 9 files, +213/-14.
- Reviewed on: 2026-11-12
- Better Auth: pinned at exactly `1.6.22` in `apps/auth/package.json`, with `patches/better-auth@1.6.22.patch`. The patch does not touch session refresh.

## Verdict: SHIP

I found no path where `disableRefresh` lets an expired, revoked or over-limit session authenticate. The fix is correct for the failure it targets. Its real-handler test fails without the fix and passes with it. The full auth suite passes against real Postgres 16. Three residual items are listed below. None blocks the merge.

## Checks

### 1. Is expiry/revocation still enforced on an identify-only read? Yes.
In `better-auth/dist/api/routes/session.mjs` (1.6.22), `getSession` runs `findSession(token)` and then checks `!session || session.session.expiresAt < new Date()`, returning `null` if either is true (lines ~179-191). The `dontRememberMe || ctx.query?.disableRefresh` early return comes after that check (~195). `disableRefresh` therefore skips only the renewal write and the cookie it sets. It does not skip the liveness check.
- Revoked or capped records are deleted rows, so `findSession` returns null.
- Idle and absolute limits live in `expires_at`. The clamp and `DrizzleSessionExpiryClamp` hold it to the person's limits, and Better Auth's own comparison still applies.
- Cookie-cache path (reads without `disableCookieCache`): it checks the cached `expiresAt` and the cache's own max age (300 s). `cookieRefreshCache` is `false` here because the setup is stateful and `refreshCache` is unset, so this path never writes. Its up-to-5-minute staleness after a revocation existed before this PR and is unchanged by the diff.
- Probed with the real Better Auth handler (scratch test, not committed): an expired record gives `null` from `readSession`; a deleted record gives `null` from both `readSession` and `readCachedSession`; an identify-only read returns no `Set-Cookie`. All pass.

### 2. Does staff idle-from-last-use still advance? Yes.
`device-session-hook.ts:83-85` calls `readCachedSession`, which is now identify-only, and then `activity.record(id)`. `DrizzleSessionActivityStore.touch` sets `last_seen_at` and moves `expires_at` to `GREATEST(expires_at, used + renewal)`, clamped to the person's idle and absolute limits. It is guarded by `sessionIsLive(now)`, so a record that has already ended is not revived, and the throttle is decided in the DB. Removing Better Auth's on-read renewal therefore removes no extension that `SessionActivity` does not already provide within limits. It also removes the old 7-day write that the clamp then trimmed back.

### 3. Remaining reads that can renew
App-side `auth.api.getSession` calls: all of them now pass `IDENTIFY_ONLY`. That covers `create-device-sessions.ts:51`, `create-auth-request-handler.ts:87,189`, `create-auth-app.ts:100` (feeds every `capabilities.getSession` in `mount-hosted-auth-pages.ts`), `mount-oidc-routes.ts:185,364,541` (`readBrowserSession` also feeds the account-action routes), `passkey-request-policy.ts:107` and `two-factor-authorize-gate.middleware.ts:92`. No plain call remains.

Better Auth still renews through its own `getSessionFromCtx`. This is by design and outside the diff. It covers `/oauth2/authorize`, `/oauth2/consent`, everything behind `sessionMiddleware` (two-factor, passkey, `link-social`, JWT `/token`), and `sensitiveSessionMiddleware`. Over HTTP these calls carry `ctx.request`, so the oidc-provider after-hook does not throw "request not found". Two server-side calls with no `ctx.request` can still renew a staff record and so hit the same failure, but only while an `oidc_login_prompt` cookie is still present. That cookie lasts 10 minutes and is expired by the first sign-in that sets a session cookie. See R1.

### 4. Is the `as` cast safe? Yes for 1.6.22, and guarded against upgrades.
`IDENTIFY_ONLY = { disableRefresh: true } as unknown as { disableCookieCache?: boolean }`. In 1.6.22, `disableRefresh` is in `getSessionQuerySchema` (`cookies/session-store.mjs:165`, `z.coerce.boolean().optional()`), so it passes validation and is read at `session.mjs:195/206`. The cast only hides the key from the narrowed app-side `Auth.api.getSession` type in `packages/auth/src/server.ts:128`. If an upgrade renamed or dropped the flag, the cast would turn that into a silent no-op. The new real-handler test would catch it, because it drives the real Better Auth through `createSessionReaders`, which spreads the same constant. A cleaner long-term option is to add `disableRefresh?: boolean` to the `Auth.api.getSession` query type in `packages/auth/src/server.ts` and drop the cast. This is optional.

### 5. Does the new test truly fail without the fix? Yes.
With `IDENTIFY_ONLY` changed to `{}` locally (reverted afterwards), `device-session-readers.better-auth.test.ts` "reads a short-lived sign-in under the hosted page's login prompt..." fails with `{ error_description: 'request not found', error: 'invalid_request' }`. The control case ("is what the plain read gets wrong") passes either way, which confirms the reproduction. With the fix, both cases pass.

## Residual (non-blocking)
- **R1 (low, availability; not an auth bypass).** `create-auth-request-handler.ts:250`: `auth.api.revokeOtherSessions` (`sensitiveSessionMiddleware`) and `mount-oidc-routes.ts:386` `auth.api.linkSocialAccount` (`sessionMiddleware`) are server-side calls with no `ctx.request`.
  - Scenario: a staff record (always under 6 days left, so it renews), a request that still carries `oidc_login_prompt`, and 2FA enable/disable or an account-action link.
  - Result: renewal, then `Set-Cookie`, then the after-hook throws "request not found".
  - For `revokeOtherSessions`, `settle` falls back to the durable job (`runSecurityEffect` → `operations.removeOtherSessions`, DB-direct), so the revocation still happens. `linkSocialAccount` would answer with an error.
  - Fix if wanted: strip the `oidc_login_prompt` cookie from the headers passed to these two server-side calls.
- **R2 (low, test coverage).** Only `createSessionReaders` is tested against the real handler. The other seven call sites are covered by mocks at most (`create-auth-request-handler.test.ts:228` asserts the query). Dropping `IDENTIFY_ONLY` at any of them would pass CI. A grep-style guard test would catch that, for example one asserting that every `auth.api.getSession(` in `apps/auth/src` passes `IDENTIFY_ONLY`.
- **R3 (info).** Identify-only reads no longer repopulate the `session_data` cookie cache, so staff reads hit the DB more often. This affects performance only.
