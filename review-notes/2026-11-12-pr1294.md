# Security review: PR #1294, session lifetimes and browser cap (`sd3-session-lifetimes-cap`)

- **Reviewed:** `git diff origin/sd2-sign-out-per-browser...origin/sd3-session-lifetimes-cap` (31 files, +1685/−38), on top of #1289 → #1278
- **Reviewer:** independent security review (automated, scheduled)
- **Date:** 2026-11-12

## Verdict: **FIX FIRST**

Most of the work is sound. The SQL and in-memory policies agree at the limit boundaries. Refresh is refused once the record is idle, past its absolute limit or expired, including through lineage. The sweep and cap end records with durable back-channel logout and delete their tokens. The invariants from PRs 1–2 still hold.

Two medium findings block merge:

- **M1:** a sign-in in a browser that still holds a record past its absolute limit (one the sweep has not yet deleted) inherits that record's old `signed_in_at`. The new sign-in is already over when it is created, and this repeats on each later sign-in in that browser. I reproduced this against Postgres.
- **M2:** idle and absolute limits are enforced only by the once-a-minute sweep and the refresh guard. The issuer's own session (Better Auth `getSession`, so `/authorize`), LAX Account's `RecentSessionGuard`, and takeover all still treat a record as live until `expires_at`. For staff, the 24-hour absolute limit holds only as long as the sweep is healthy.

## Findings

### M1 (Medium): Takeover carries `signed_in_at` from a record that is already over, so the new sign-in is ended on arrival

- **File:** `apps/auth/src/infrastructure/drizzle-session-takeover.store.ts:51`. `findLive` still filters on `gt(session.expiresAt, now)` instead of `sessionIsLive(now)`. The value is then carried at `apps/auth/src/services/session-takeover.service.ts:32` and written at `drizzle-session-takeover.store.ts:110`.
- **Exploit/failure:**
  1. A client's record passes 30 days from first sign-in, but its `expires_at` is still in the future (Better Auth renews it daily), so the takeover filter still sees it as live.
  2. Before the sweep deletes the record, the person signs in again in that browser. This happens within ≤1 minute normally. It lasts much longer while the sweep is backlogged (for example, the first rollout, when every legacy record older than 30 days becomes "over" at once) or failing.
  3. `findLive` returns the over record by cookie or by the same person's device hash. `planTakeover` takes the minimum `signedInAt`, so the new record gets the 31-day-old value.
  4. The new record is immediately non-live: refresh is refused, and the sweep deletes it.
  5. The next sign-in takes over this dead record and inherits the same old timestamp again. This continues until the sweep happens to delete the record between two sign-ins.
- **Reproduced:** a throwaway integration test against PG16 (removed afterwards). Three consecutive sign-ins `new1..new3` each ended with `signedInAt = now − 31d` and `findLiveIdentitySession(...) === null`.
- **Also:** the same path re-binds an ended sign-in's lineage and `oidc_rp_session` rows to the new record (`replace()` repoints them), so product `sid`s of an idle-ended sign-in become refreshable again. This is limited to the same person in the same browser, so it is low impact on its own, but it contradicts "refresh refused once the record ended".
- **Fix:**
  - For `sameSubject` matches, use `sessionIsLive(input.now)` in `findLive`, so an over record is neither carried nor renewed and is left to the sweep.
  - Keep ending another person's cookie-named record (with back-channel) whatever its state. Alternatively, ignore `signedInAt` from records whose `sessionEndReason` is non-null.
  - Add an integration test: re-sign-in over an absolute-over, unswept record produces a live record with a fresh `signed_in_at`.

### M2 (Medium): Idle and absolute limits are not enforced by the issuer itself, only by the sweep and the refresh guard

- **Files:**
  - `packages/auth/src/server.ts:304-310`: Better Auth checks only `expires_at`, and rolls it forward by 7 days on each `updateAge`; the cookie cache adds up to 300 s.
  - `apps/auth/src/services/recent-session-guard.ts:19`: `liveSessions` uses only `expiresAt`.
  - `drizzle-session-takeover.store.ts:51`: see M1.
- **Exploit/failure:**
  1. A staff record reaches 24 hours from first sign-in (or 12 hours idle). Its `expires_at` is still up to 7 days in the future.
  2. Until the sweep deletes it, the browser is still signed in at the issuer. `/oauth2/authorize` (including `prompt=none`) issues new codes and access tokens bound to the over record. Their refresh is refused, but each access token is valid for its full TTL.
  3. LAX Account's `findLive` and `findRecent` also accept the record.
  4. Normally the exposure is about 1 minute plus the 5-minute cookie cache. If the sweep is down or erroring (one failing `reserve` aborts the whole run, which retries every minute), there is no bound. SD9's 24-hour absolute limit then depends on a background job's health rather than on the issuer.
- **Fix (pick at least the first):**
  1. Clamp `expires_at` so Better Auth itself refuses the record: in `databaseHooks.session.create.before`/`update.before` (and in the takeover `replace` stamp), set `expires_at = LEAST(proposed, signed_in_at + absolute(person))`. Also clamp it to `last_seen_at + idle` when touching. Better Auth's own check then enforces SD8 and SD9 without the sweep.
  2. Make `RecentSessionGuard.liveSessions` apply `sessionEndReason` (needs `lastSeenAt` and `signedInAt` from `listSessions`).
  3. Alert on `session_expiry` sweep errors, or when its backlog is non-zero for N minutes.

### L1 (Low, performance/operability): The 0365 indexes do not narrow the sweep, and they prevent HOT updates on the busiest column

- **Files:** `packages/db/drizzle/0365_session_lifetime_indexes.sql:17-21`, `apps/auth/src/infrastructure/session-lifetime.sql.ts:36-47`
- **Detail:**
  - The prefilter uses the *staff* limits (12 h / 24 h), which nearly every client record older than a day satisfies.
  - With 400k live client sessions, `EXPLAIN ANALYZE` of the sweep query on PG16 chose a **Seq Scan** that removed 400,000 rows by filter (≈95 ms warm, 6.5k buffers). It did this every run, on every instance.
  - Meanwhile, indexing `coalesce(last_seen_at, updated_at)` means every activity touch (up to once per 15 min per active record) and every Better Auth `updated_at` bump becomes a non-HOT update that writes all session indexes. That adds write amplification and bloat for no read benefit.
- **Fix:** consider dropping `session_last_active_idx`, or splitting candidate scans per class (staff via a join on markers, clients via the 7-day/30-day constants) so the index ranges are selective. The `expires_at` index already serves the common case. The migration comment's claim that the indexes "narrow the scan" is incorrect for client-heavy tables.

### L2 (Low): Cap enforcement is best-effort, happens only at sign-in, and can deadlock with a concurrent takeover

- **Files:** `apps/auth/src/services/session-takeover.service.ts:143`, `apps/auth/src/infrastructure/drizzle-session-cap.store.ts:32-33`
- **Detail:**
  - The cap runs in its own transaction after `replace` commits. If it throws (deadlock, DB error, `reserve` failure), the sign-in stands and the cap is not retried until the next sign-in.
  - Two concurrent sign-ins of the same person in different browsers can deadlock: the cap's `FOR UPDATE` takes locks in id order, while the other request's `replace` deletes and updates rows in a different order. Postgres aborts one of them, and the cap is skipped.
  - A client promoted to staff keeps up to 20 browsers until the next sign-in. The idle and absolute limits still apply immediately through the SQL, which is correct.
  - **Racing sign-ins:** the read-committed `FOR UPDATE` snapshot plus "each sign-in enforces after its own insert" means the last enforcer sees every row, so the cap converges. Ties are broken by random id, so another person's browsers cannot be targeted. Eviction is scoped to `fresh.userId`, so one person can never force eviction of another person's browsers. The cap does not count records that are already over.
- **Fix:** catch, log and alert on cap failure separately (with a retry, or a durable "enforce cap for user" job). Optionally, run a cap check in the sweep.

### L3 (Low): The application clock is the time source for the sweep, the touch and the throttle

- **File:** `apps/auth/src/infrastructure/session-lifetime.sql.ts:10`, `drizzle-session-activity.store.ts:199`
- **Detail:** `now` comes from each instance. An instance whose clock runs ahead writes a future `last_seen_at`. That extends idle by the skew and suppresses other instances' touches; it also ends records early on its own sweep. An instance whose clock runs behind keeps over records alive for the skew. Neither is exploitable by a user (the clock is the server's), and the effect is bounded by NTP drift.
- **Fix:** prefer the database's `now()` (or `clock_timestamp()`) in the touch and sweep SQL, or clamp `last_seen_at` to `LEAST(app_now, now())`.

### I1 (Info): Migration and rollback details

- Grants are fine. Indexes need no grants, and `auth_app` already has SELECT on `identity_access_marker`, which `sessionPersonIsStaff` reads.
- The migration is idempotent (`IF NOT EXISTS`) and transactional per the runner. The 5-second `lock_timeout` caps lock waits, but the plain `CREATE INDEX` holds a SHARE lock for the whole build. Run it at low traffic.
- `0365_rollback.sql` uses `SET LOCAL lock_timeout` without `BEGIN`. Run through `psql -f`, this has no effect (a warning only). Wrap the rollback in `BEGIN; … COMMIT;`. The rollback does not remove the ledger row either, so re-applying requires manual ledger cleanup. Document this.
- **Journal:**
  - `idx 352` and `when 1806566400000` are later than every entry on `origin/main` (the latest there is 0358, `1805961600000`). The runner fails closed on gaps, so 0365 cannot be silently skipped.
  - **Stack-level (outside this diff, PR #1278):** 0356's `when` (`1805788800000`) is earlier than main's already-merged 0358. Any environment that has applied 0358 will stop with "missing … before applied timestamp" when the stack lands. Rebase the stack onto main and re-stamp 0356/0361/0365, or register 0356 in `LATE_REGISTERED_FOLDER_MILLIS` (it is additive). The stack also does not yet contain main's 0352–0358 journal entries.

### I2 (Info): The integration tests interfere when run in parallel locally

- Running `drizzle-session-lifetimes`, `session-takeover` and `drizzle-browser-sign-in` integration files together without `CI` set gives 7 failures. Each file passes alone, and the full suite passes. The broader sweep predicate now ends other files' fixtures, which use old `created_at` or `updated_at`.
- CI serialises DB tests (`vitest.config.ts`), so this is not a CI break. Scoping sweep assertions to the test's own users would make it robust.

## Checked and holding

- **Absolute limit across lineage:** `planTakeover` takes the *minimum* `signedInAt` of same-person records, never the fresh time, so a renewal cannot extend it. Another person's record never contributes. Refresh through an old `sid` resolves to the replacing record and is checked with `sessionIsLive`. Product refresh never creates an Identity record. (M1 is about the opposite direction: shortening the limit and reviving lineage.)
- **`last_seen_at` manipulation:** it is written only for a record named by a verified session cookie (`readCachedSession`, signed) or by a refresh that already passed the liveness and subject check. The device marker plays no part. The write is refused once the record is over (`sessionIsLive` in `touch`). The throttle is decided in SQL on the stored value, so instances racing each other write once. The in-memory map only skips repeat requests and is set only after a successful call. Staleness is at most 15 minutes and ends records early, never late.
- **Legacy records** (`last_seen_at` NULL, falling back to `updated_at`): Better Auth bumps `updated_at` only together with `expires_at`. A legacy record idle for 7 days by `updated_at` is therefore already expired, and Better Auth refuses it, so it cannot be revived through `updated_at`. I tested this.
- **Staff detection:** it reads the same marker source as the two-step policy (`kind='staff'`, product `bid`/`shop`), and the triggers on `bid_user_profile.role` and `shop_staff_member` keep it in sync. It is evaluated live in SQL, so a promotion applies staff limits on the next sweep run, and a demotion relaxes them. Neither the sweep nor the cap can treat a staff member as a client. `NOT (…)` cannot become NULL because all inputs are NOT NULL or `EXISTS`.
- **Sweep:** `FOR UPDATE SKIP LOCKED` with `LIMIT`. Running it twice, or on many instances, is idempotent. Removing `ORDER BY` is safe because taken rows are deleted. Back-channel jobs are reserved durably before delete and `run()` after commit, and tokens under the record and every earlier id are deleted in the same transaction.
- **Cap eviction:** it uses the same `endLockedSessions` path, with `session_revoked` published per id and no security notice, as approved. The new sign-in is never chosen.
- **Invariants from PRs 1–2:**
  - Recency is checked on the exact id only: `RecentSessionGuard.findRecent` is unchanged.
  - Lineage renewal keeps `auth_time`/`acr`/`amr`: those files are unchanged, and the tests pass.
  - The device marker never authenticates: the new activity path reads the cookie session only.
  - Refresh is refused once a record has ended or expired: `findLiveIdentitySession` now uses `sessionIsLive`.
