## What I checked and found correct

- **Refund states**: `stripe-payment-group.gateway.ts:27` now counts only `succeeded`. `pending`, `requires_action`, `failed` and `canceled` are all excluded, and the gateway unit test covers all five. A pending refund is counted later through `charge.refund.updated` (`stripe-payment-event-registry.ts:44`, `payment-group-charge-events.ts:80`), which reconciles against Stripe's live refund list.
- **pending→failed no longer sticks for groups**: nothing is recorded while the refund is pending. A later real refund of the same amount is announced once. Both the unit tests (`payment-group-refund-status.test.ts`) and the DB integration test (`payment-group.integration.test.ts:578`) cover this.
- **Replays and out-of-order events**: each event is claimed (`claims.claim`). Recorded totals only rise to Stripe's list, so the deltas never go negative. I also traced two concurrent events whose lists were fetched at different times: whichever commits second sees delta ≤ 0 or only its own increment, so nothing is double-counted or lost. Buyer record, seller ledger (capped at the invoice), courier quote and unattributed excess all use the same rise-only rule.
- **Notices exactly once**: `payment.refunded`, `payment_group.delivery_refunded` and `payment_group.refund_unattributed` are published only when a total rises, in the same transaction. Idempotency keys are `${event.id}:${paymentId}`.
- **Non-group `charge.refund.updated`** returns `not_a_group_charge` with HTTP 200 (`stripe-webhook-ingress-application.service.ts:112-123` returns 500 only for `payment_not_found`, `amount_mismatch` and `missing_charge_id`), so Stripe will not retry storms.
- **PaymentIntent id on capture**: the service only passes the id when the row has none (`payment-capture.service.ts:140`), and the SQL is `coalesce(nullif(existing,''), new)` (`drizzle-payment.repository.ts:314`). An existing id is never overwritten, and an empty string is treated as missing. Refunds are still created by charge id (`stripe-payment-gateway.ts:135`), so refund routing does not change.
- **Transfer progress math**: integer pence end to end. The DB raises with `least(greatest(old,new), round(amount*100))` and only when the new value is strictly higher, under status `pending|authorized`. `payProgressOf` clamps again, `remaining = total - received`, and the percentage uses floor, so a payment 1p short never shows 100%. The CHECK `>= 0` constraint matches the Drizzle schema. The migration is additive (default 0, NOT VALID then VALIDATE), and the rollback is correct.
- **Seller settlement/payout code**: none changed. The diff only calls the existing `addPaymentLineToOpenPayoutOrCreateClawback`. No payout or transfer services are touched.

## Findings

### 1. Medium (deploy gate): group refunds that go pending→succeeded are never counted unless the endpoint subscribes to `charge.refund.updated` first
- Where: `apps/api/src/services/stripe/stripe-payment-group.gateway.ts:27`, `docs/runbooks/stripe-connect-go-live.md:15`
- Scenario: the release goes out before the Stripe Dashboard payments endpoint adds `charge.refund.updated`. Staff refund £25 on a grouped invoice and Stripe returns `pending`. `charge.refunded` then reconciles to 0. On main this refund would have been counted at that point. When it succeeds, no event arrives, so the seller is never clawed back and no `payment.refunded` is announced. This is a missed announcement, a regression compared with main. It is also permanent if a `charge.refund.updated` delivery is lost after Stripe's retry window, because no sweep re-reconciles groups.
- Fix: subscribe the endpoint **before** deploying (verify in the Dashboard or via `stripe webhook_endpoints retrieve`). Follow-up: add a periodic reconcile of groups that have non-terminal refunds, or a startup check that the endpoint's `enabled_events` includes it.

### 2. Medium (pre-existing, outside this PR's stated scope): single-invoice and other paths still use the old counting
- `apps/api/src/services/stripe-webhook/checkout-refund-handlers.ts:72` uses `charge.amount_refunded`, which includes pending refunds. Rise-only deltas are recorded, so a pending→failed refund on a single card invoice still sticks: the seller is clawed back and `payment.refunded` is announced for money that never left. A later real refund of the same amount adds nothing.
- `apps/api/src/services/stripe-payment-webhook.service.ts:228-233`: `charge.refund.updated` is ignored for non-group charges, so a failure is never seen there.
- `apps/api/src/services/payment/refund-execution.ts:62-72`: a staff refund records the full amount and announces it as soon as Stripe returns a refund id, whatever its status. If it later fails, the record stays.
- `apps/api/src/services/stripe-webhook/deal-payment-webhook-handlers.ts:159` and `apps/api/src/services/stripe-webhook/unapplied-money-refund.handler.ts:42` also read `amount_refunded`.
- `COUNTED_REFUND_STATUSES` exists only in the group gateway; there are no other copies.
- Fix (follow-up PR): give the single-invoice webhook the same treatment as groups. List the charge's refunds filtered to `succeeded`, or subtract pending and `requires_action` amounts from `amount_refunded`, and route `charge.refund.updated` for non-group charges to the same reconcile. For staff refunds, record when the refund reaches `succeeded`, or reconcile a failure down through a compensating entry.

### 3. Low: no repair for group totals already inflated under the old counting
- Groups where a pending refund was counted and then failed before this release keep high buyer and seller totals, delivery `refunded_pence`, and `refund_unattributed_pence`. The PR does not change these and there is no report for them.
- Fix: run a one-off read-only report comparing each refunded group's stored totals with Stripe's succeeded refunds, and let finance correct any mismatches by hand.

### 4. Low: `transfer_received_pence` is not tied to a PaymentIntent and is never reset
- Where: `packages/persistence/src/repositories/drizzle-payment.repository.ts:249-271`, `apps/api/src/services/organisation-buying/pay-progress.resolver.ts:37-40`
- Scenario: an invoice receives £30 of £100 by transfer, then leaves the `authorized` state, for example to `requires_manual_review` and then back to `pending` through release (`drizzle-payment.repository.ts:329`), and then a new transfer moves it back to `authorized` through `payment_intent.processing`. The Pay page shows "£30 received" from the earlier attempt even if that money was returned or applied elsewhere. These are edge paths. Usually Stripe re-applies the cash balance to the new PI, so the figure is often still right.
- Fix: reset the column to 0 on cancel and on release to pending, or store the PI id next to the figure and show progress only when it matches the row's current PI.

### 5. Info: group members now get the group's PaymentIntent id on their rows
- Group settlement passes `stripePaymentIntentId` into `captureInTransaction` for every member (`payment-group-settlement.service.ts:150`), so member rows now carry the shared group PI. They already carried the shared group charge id, so lookups by PI (`payment-webhook-lookup.ts:67`, dispute reader fallback) give the same rows as lookups by charge. There is no unique index on `payment.stripe_payment_intent_id`, so nothing breaks. The commit message only mentions single checkout card invoices, though, and no test asserts the group-member behaviour. Add one so the behaviour is deliberate.

### 6. Info (test quality)
- Good: the pending→failed→real-refund case is covered at unit and DB integration level, along with replays, out-of-order events, the never-negative rule, the courier-quote path, and all five statuses in the gateway filter.
- Gaps: no integration test drives `requires_action → succeeded` through `charge.refund.updated`. No test covers a refund that Stripe reports `failed` after `succeeded` (totals cannot come down, which is by design; it should be documented as a known limit). No test covers stale `transfer_received_pence` across a status round-trip (finding 4).

### Original findings

**Finding 1: pending→succeeded counted without `charge.refund.updated`. FIXED** (but see N1 for the reversal side).
- Each refund seen `pending`/`requires_action` goes into `stripe_refund_watch`. Every `listChargeRefunds` call adds it through `StripeChargeRefunds.watchUnsettled`, and a staff refund adds it through `deferUnlessRefundSucceeded`. The group gateway gets the watching reader from the container (`create-payments-services.ts` → `create-payment-group-services.ts`).
- Worker cron runs every 15 min → `POST /internal/cron/stripe-refund-reconcile` → `StripeRefundReconcileService`. Due rows are leased with `FOR UPDATE SKIP LOCKED` plus a 10-min lease, with backoff from 5 min to 6 h. Each final refund is settled through the webhook's own `handleChargeRefunded` under its own id `refund_reconcile:<re>:<status>`.
- Exactly once: integration tests drive the job alone, job then late webhook, and webhook then job, for single-invoice and group. All record 1 row and 1 notice. A startup check also logs a warning when the endpoint lacks `charge.refund.updated`.
- Failed/cancelled refunds are never counted (`isCountedRefund` is `succeeded` only). The mutation check confirms the tests would catch a regression.

**Finding 2: every refund path uses settled-only counting. FIXED.**
- `stripe-refund-status.ts` is the one rule. No production code in `apps/api/src` reads `amount_refunded` any more.
- Single invoice (`checkout-refund-handlers.ts`), deal (`deal-payment-webhook-handlers.ts:162-167`), unapplied money (`unapplied-money-refund.handler.ts:40`), deal reversal and staff refunds (`refund-execution.ts` `deferUnlessRefundSucceeded`) all go through it.
- `charge.refund.updated` for non-group charges now re-reads the charge and settles it (`stripe-payment-webhook.service.ts:239-250`).
- A staff refund that is still pending records nothing and is watched with its staff context. It is recorded once it succeeds (`completeDeferredStaffRefund`). If the webhook records it first, the job sees `status = refunded` and writes nothing, and `applyRefundedInTransaction` under the payment lock blocks a concurrent duplicate.

**Finding 3: explicit, dry-run, idempotent, audited repair. NOT FIXED (partly delivered).**
- Delivered: `pnpm --filter @auction/api repair:group-refund-totals` is dry-run by default (`--apply` to write), never scheduled, and per group under lock. It only takes back what failed or cancelled refunds explain and flags the rest as UNEXPLAINED.
- **Not idempotent** when an unexplained excess exists (N3 below; reproduced). The comment "Safe to run again … a second run reports nothing left to repair" is false in that case.
- Audit is partial. Member corrections publish `payment.refund_reversed` (`via: refund_repair`). The lowered courier `refunded_pence` and `refund_unattributed_pence` are written with no event or record of any kind. No operator identity is recorded (`actorUserId: null`), and the run's output exists only on stdout.

**Finding 4: `transfer_received_pence` tied to its PaymentIntent. FIXED.**
- New column `transfer_received_payment_intent_id`. A notice for another intent replaces the figure instead of raising it, and a late notice for an earlier intent is ignored (the `coalesce(stripePaymentIntentId, pi) = pi` guard).
- `updateStripePaymentIntentId` clears the figure when the intent changes. Cancel, reopen-from-cancelled and release-from-manual-review reset it to 0/NULL.
- The Pay page reader shows the figure only while its intent matches the row's current one.
- Integer pence throughout, capped at `round(amount*100)`.
- Migration safety: 0374 is also new in this PR (main ends at 0373), so no deployed row holds a non-zero figure without an intent.

### New findings

**N1. Medium-High (money record): the reversal limit is not cumulative, so the job and the webhook both take back the same failed refund.**
- Where: `stripe-refund-status.ts` `refundCorrectionPence`, used by `checkout-refund-handlers.ts:101-117` and by the repair.
- The downward correction is limited by `returnedNothingPence`, the total of failed or cancelled refunds on Stripe's list. It does not subtract what `refund_reversal` rows have already taken back. Every event with a new id therefore takes back up to that amount again, until the record reaches Stripe's succeeded figure. Webhook event ids and `refund_reconcile:<re>:failed` are different ids, so the webhook and the job for the **same** failed refund each reverse.
- Reproduced (temporary DB integration test, single invoice): £10 recorded by staff outside Stripe (the "left for finance" case, as in the existing test) plus £25 counted by the previous release while pending. Then the refund is reported failed and the refund is watched.
  - `charge.refund.updated` → record goes from £35 to £10. Correct.
  - Reconcile job run for the same refund → record goes from £10 to **£0**. Rows: `+1000 staff, +2500 card_webhook, -2500 refund_reversal, -1000 refund_reversal`. `payment.refund_reversed` is announced twice.
- Seller-side variant: whenever the seller's refund lines are above Stripe's succeeded figure for any reason other than this failure, the second pass also writes a positive payout line. That gives the seller money that was really refunded.
- Fix: take back at most `returnedNothingPence − (reversals already recorded)`. One option is to sum `refund_reversal` rows (and positive refund payout lines) under the lock. Another is to key the reversal by Stripe refund id (`reversal:<re>`) with ON CONFLICT DO NOTHING, so a failed refund is reversed at most once, whichever path sees it.

**N2. Medium (concurrency): Stripe's list is read before the lock, and a stale list now reverses a real refund.**
- Where: `checkout-refund-handlers.ts:50` reads `totals` outside the transaction. Under the old rise-only rule a stale list was harmless. With downward corrections it is not.
- Reproduced: R1 £25 failed, R2 £25 pending. Event X reads the list (counted 0, failed 25). R2 succeeds and event Y commits +£25. X then takes the lock: recorded 25 > counted 0, so it takes back min(25, 25). Final buyer record £0 and seller net 0, so the seller is credited back the £25 that really went to the buyer, and `refund_reversed` is announced.
- It corrects itself only if a later event or a still-unsettled watch row re-reads the charge. If the job had already settled R2, nothing does, and a payout run in between pays the seller.
- The window is the network call (ms to s), with the webhook and the job running side by side.
- Fix: re-read Stripe's list after taking the payment lock (or re-check it before writing a negative correction), or limit reversals to the refund ids that are final at the time of the event (`reversal:<re>` as in N1).

**N3. Medium: repair `--apply` is not idempotent when there is an unexplained excess.**
- Reproduced (temporary group integration test): invoice a has a £25 pending-then-failed refund plus £10 recorded outside Stripe. The first `--apply` gives £10 (flagged UNEXPLAINED, as intended). The second `--apply` gives **£0**: another `-1000 refund_reversal` row and another notice.
- The idempotency key `refund_repair:<payment>:<recordedBuyer>:<recordedSeller>:<succeeded>` changes after each run, so it does not stop a repeat.
- This has the same root cause as N1, and the same fix applies. Add a test that runs `--apply` twice with an unexplained excess.

**N4. Low (audit): repair lowers `payment_group_delivery.refunded_pence` and `payment_group.refund_unattributed_pence` with no domain event or audit row, and records no operator for any correction.**
- Fix: publish an event for these too, and take `--operator <staff id>` (or similar) into `actorUserId`.

**N5. Low (rollback scripts): `0374_rollback.sql` and `0376_rollback.sql` use `SET LOCAL lock_timeout` without `BEGIN`.**
- psql prints `WARNING: SET LOCAL can only be used in transaction blocks`, so the 5 s lock timeout does not apply when they are run as files. 0375's rollback wraps itself correctly.
- Fix: wrap them in `BEGIN; … COMMIT;`.

**N6. Info:**
- When a deferred staff refund's `charge.refund.updated` arrives before the job, the refund is recorded once, but as `card_webhook` / `via: stripe_webhook`. The staff member and reason kept on the watch row are dropped. The money is right; the audit trail is weaker.
- `payment.refund_reversed` has no consumer apart from the admin label. The Xero refund credit note from the original staff refund is not reversed, so accounting needs a manual step whenever a reversal happens.
- worker_app has no grants on `stripe_refund_watch`. That is correct: the worker only calls the API over HTTP, and `api_app` holds the table. `payment_refund` remains INSERT/SELECT for api_app, so compensating rows are appended, never updated.
- Partial refunds (£25 of £100, £40) and pence handling (integer pence, `toFixed(2)` from integer pence, currency upper-cased on write) check out. The 0375 backfill change (`round(-SUM(amount)*100)` instead of `SUM(round(abs(amount)*100))`) only ever adds top-ups when the sum is > 0, so with the signed sum it cannot add more than before.
