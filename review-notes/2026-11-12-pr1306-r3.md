## New and carried items (not blocking; settle in or before the runtime PR)

### N1. Low: the claim does not carry the claimer's mode, so the sender must use `stored.target.mode`

- **Where:** `packages/persistence/src/interfaces/accounting.ts:107-121`. `ClaimRequest` has only `provider`. The claim matches the target against the switch's *current* mode, not against the mode the calling process is configured for.
- **Scenario:** a Books worker that chose its organisation and credentials from its own config (`test_org`), or from a switch read it cached earlier. Books is now `live` for Shop, so the claim hands it a `{books, live}` document. The worker then issues that real invoice in the test organisation. The table records `issued` with a test-org `provider_id`, and the live ledger never gets it.
- **Fix:** pick one; both are small.
  1. Add `readonly mode: TargetMode` to `ClaimRequest`, and add `eq(accountingDocument.targetMode, request.mode)` next to `:62`. The claim then needs the claimer's mode **and** the switch to agree with the target.
  2. Or state in the `IAccountingDocumentWorkQueue` comment that the sender must choose the organisation, credentials and dry-run behaviour from the returned `target.mode`, never from its own config.

  I recommend option 1, because it makes the round-2 wording ("equals the claimer's current provider and mode") true at the database.

### N2. Low: real documents created while no source is live are aimed at a rehearsal (or at nothing) for good

- **Where:** `accounting-domain/src/source-switch.ts:94-101` (`documentTarget`).
- **Scenario:** Shop has no provider today. The planned rollout is Books `test_org` for Shop. Every real Shop sale registered during that phase gets target `{books, test_org}`.
  - Those documents are issued only in the test organisation.
  - When Books goes `live`, they are never sent to the live ledger, because there is no re-aim.
  - Probe: a doc registered with both providers `off`, or with both in rehearsal, gets target NULL, and it is never claimed, even after a provider goes live.
  - Nothing reports either set.
- **Why it is not a D4b regression:** D4b was about a rehearsal *consuming a live document*, and that cannot happen now. This is the other side of "never re-aim": it is correct for the queue, but the revenue still has to reach the live books somehow.
- **Fix, before the runtime registers real Shop or lax.art documents:**
  - **Either** do not register real documents for a product until it has a live source.
  - **Or** add an owner-only, audited re-aim or backfill for documents that are `pending` with NULL or rehearsal targets. The pending ones are re-aimable; the ones issued in a test org need a fresh live document.
  - **And** add a monitoring query: count of pending documents with NULL target, or whose `target_mode` does not equal the provider's current mode.

### N3. Low (carried from round 2, D4b "related"): Bid's seed is still Xero `live` for the new pipeline

- **Where:**
  - `0368_accounting_tables.sql:198-201` seeds `('bid', 'live', 'off')`;
  - `accounting-persistence.integration.test.ts`, "hands a live document only to the live provider", asserts that Xero claims a Bid document.
- **Scenario:** the legacy `finance-runtime` path already writes Bid invoices to Xero. The first runtime that registers Bid documents and calls `claimNext({provider: "xero"})` sends each one to Xero a second time.
- **Fix:** do one of the round-2 options before any runtime registers Bid documents:
  - seed `bid` as `xero = off` for this pipeline;
  - or add an explicit rule that the new pipeline does not serve `bid` until the legacy writer is retired.

  In either case, add the test "Bid on Xero live: the new pipeline's Xero claim gets nothing".

### Info

- **Forged targets.** `worker_app` can INSERT a row with any valid target, for example `{books, test_org}` while Bid is Xero `live`, because INSERT is not column-limited and no trigger checks the target against the switch. The registry is the only writer, so this needs code that bypasses it. A `BEFORE INSERT` trigger (or column-limited INSERT plus a DB default) would close it, but it is not needed for this PR.
- **Comment placement.** `0368_accounting_tables.sql:65-66`: the `provider_sent_ck` comment now sits above `target_ck`, with the target comment at `:67-69`. Move the `:65-66` comment down to just before `provider_sent_ck` at `:76`.

## What is good

- The target is a fixed fact of the row, and the DB backs it up three ways:
  - the CHECK ties `provider` to `target_provider`;
  - no app role holds UPDATE on the target columns;
  - the claim needs the target **and** the current switch to agree.

  That rules out the round-2 hazard, and it also rules out re-aiming on a flip.
- A requeue keeps the original provider and target, so lookup-before-retry and a retry both go to the same place. A lapsed lease is still settled whatever the switch says, and calls no provider.
- SKIP LOCKED plus the stamped provider held under a concurrent flipper: no duplicates, and no cross-provider claims.
- The tests are now explicit per mode pair. They reset state themselves and pass in any order.
