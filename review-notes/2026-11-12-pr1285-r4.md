### N-B1: the sweep only expires orders with a payment page

**The fix.** `apps/shop-api/src/infrastructure/shop-checkout-money-pause-sweep.ts:37-43` now filters on `status = 'pending_payment' AND stripe_checkout_session_id IS NOT NULL`. An order with no page stays `pending_payment`, and its quote and hold are untouched. It cannot be paid while paused:
- resume, retry, accept-and-pay and the guest links all go through `assertOrderNotPaused` (`drizzle-checkout.repository.ts:99-108`);
- a new checkout goes through the basket check (`:245-250`).

**The branch's own test** (`checkout-money-pause.integration.test.ts`, "is left alone when the order has no payment page yet, and recovers after a false alarm") passes. It nulls the session on a normal order, pauses, sweeps, lifts the pause, and resumes.

**My reproduction with the real delivery-quote flow.** This was a throwaway file, never committed. It used the real request, staff and acceptance services, a real `createDrizzleCheckoutMoneyPause` with a Zoho-linked artwork, and the real sweep:
- **R4-1, quote requested** (the order has no session):
  1. Pause, then sweep. The order stays `pending_payment` and the quote stays `requested`.
  2. Staff clear "It is not sold".
  3. Staff send the quote, and the buyer accepts and pays. A page opens and the quote is `accepted`. **The false alarm is recovered.**
- **R4-2, quote sent, not yet accepted:**
  1. Pause, then sweep. The order stays pending and the quote stays `quoted`.
  2. Accept-and-pay is refused with 409, no Stripe session is created, and the session stays null.
  3. Lift the pause and sweep. Accept-and-pay now opens a page. **Recovered.**
- **R4-3, quote accepted with an open page** (accepted residual, not new):
  1. Pause, then sweep. The page is ended at Stripe and the order is `expired`.
  2. The quote stays `accepted`, because `closeDeliveryQuoteForOrder` cannot withdraw an accepted quote. That is the same thing that happens when the hold simply runs out, so it is existing behaviour, and the buyer's basket is restored.
  3. This is round 3's optional "end only the session, keep the order" step. It was not done, and it is not needed to ship.

**Money safety after the change:**
- Every order with a session is still ended through `expireShopCheckoutSession`, which asks Stripe first and reconciles `already_complete` payments.
- The `applyShopPayment` backstop is unchanged. If an order is paid while paused, it is recorded as `paid_while_money_paused`, sent to finance, and never fulfilled.
- An order that gains a session after a tick is caught on the next tick. Opening that session is itself refused while paused.
- Narrowing the filter can only expire fewer orders, never more, so **a paid or being-paid order is never expired**. Already-complete and async-pending sessions still go through the existing reconcile and ceiling paths.

### N-B2: shop_app and worker_app can update only the columns they write

**The fix.** `packages/db/src/migrate-roles.ts` adds `SHOP_SOLD_ATTENTION_UPDATE_COLUMNS` and `WORKER_SOLD_ATTENTION_UPDATE_COLUMNS`. Each role's table-wide UPDATE is revoked and replaced by `grantColumnUpdateIfExists`.

**Grants on a migrated, roled database** (from `information_schema`):

| Role | Table-wide | UPDATE on columns |
|---|---|---|
| shop_app | SELECT | status, resolution, resolved_by, override_reason, resolved_at |
| worker_app | SELECT, INSERT | status, resolution, resolved_by, resolved_at |

Running `db:roles` again is idempotent.

**SQL probe** (run as each role with `SET ROLE`, inside a transaction that was rolled back):

| Role | Statement | Result |
|---|---|---|
| shop_app | UPDATE of `zoho_product_id`, `place`, `raised_at` or `register_id` | **permission denied** |
| shop_app | INSERT, DELETE | **permission denied** |
| shop_app | the real override (`status='overridden'`, `resolution`, `resolved_by`, `override_reason`, `resolved_at`, then `RETURNING`) | works |
| worker_app | UPDATE of `zoho_product_id`, `place` or `override_reason`, and DELETE | **permission denied** |
| worker_app | resolve with `RETURNING`, and INSERT … ON CONFLICT DO NOTHING | work |

The store's writes use only the granted columns:
- worker: `replace` and `resolve` set `status`, `resolution`, `resolved_by` and `resolved_at`, and `raise` is an INSERT;
- shop: `override` sets the five shop columns.

**Role contract tests.** The new cases in `packages/db/src/shop-app-role.contract.test.ts` and `worker-app-role.contract.test.ts` compare `has_column_privilege` against the column lists exactly, and assert that `zoho_product_id`, `register_id`, `place` and (for the worker) `override_reason` are denied. Both pass.

**Residual (LOW, accepted).** Column grants cannot limit *values*. `shop_app` can still `SET status='resolved'` on an open item without writing an event. Shop has to write `status` to perform the override, so this is the narrowest grant possible. The only further step would be a trigger or CHECK tying `status` to `resolution`, for example `overridden` ⇔ `staff_override` with `override_reason` not null. That is an optional hardening, not a blocker.
