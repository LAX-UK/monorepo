## Attack on the new code (cookie on every SSR API call)

The API reads `Cookie` in exactly five places (grep of `apps/api/src`, and there is no `hono/cookie`/`getCookie`):

1. `require-legal-entity-context.ts` `resolveLegalEntityContextFromHeader` (strict and submissions middleware): it reads the cookie only when an `X-Legal-Entity-Id` header is present, the caller is **not** a member, is staff, `e === header`, and `validateForRequest` passes (row exists, actor, entity, not ended, not expired). `skipActingLegalEntityHeader` callers send no header, so the cookie is ignored. The submissions middleware falls back to the personal entity and the optional middleware sets no context. **No scoping change for unscoped calls.**
2. `routes/legal-entities.ts:206` `GET /legal-entities/:id`. The cookie applies only when the path `id === e`, the caller is not a member, and the session validates. Staff on their own account: the membership branch wins first, so the cookie is ignored. The effect is exactly the intended "view as client" read of the one entity the session targets.
3. `routes/admin.ts:100-108` reconcile on every platform `/admin/*` request. It is audit-only, never grants or scopes anything, and is now owner-checked (F2).
4. and 5. `/admin/impersonation/start` and `/end`: owner-checked (F1).

There is no other admin route that reads the acting cookie, and no admin route takes its entity from it. Admin routes take their entity from path or body under `requirePlatformShell` and the per-route guards, whatever the cookie says.

**Audit spoofing.**
- End/replace audit the entity from the DB row.
- Timeout events (`onImpersonationExpired`, `recordSessionTimedOut`) still use the cookie `e`. They do so only after `validateForRequest` has matched the actor **and** `targetLegalEntityId === header/path === e`, so `e` is the row's entity.
- `recordFailedEnd` is driven by the body, not the cookie, and is actor-scoped via `findStartedEvent({sessionId, actorUserId})`. It is unchanged.
- No new spoofing path.

**Hosts.** `withViewSessionCookie` sits only in `buildAuthedSsrHeaders`, whose callers (`authedServerFetch`, `createServerHc`) target `getServerApiBase()`. The cookie goes only where the bearer already goes.

**Account switching.**
- `viewSessionCookieHeader` requires a decodable `i.sid`, so a plain choice (a bare UUID, or `{v,e}` without `i`) is never forwarded (tested).
- Switching still travels only as `X-Legal-Entity-Id`, membership is checked first, and a non-member header without a session gets `not_a_member_of_legal_entity`.
- Web suites for account, switch and acting all pass. One fail-closed oddity is in N3.

## New findings

### N1: LOW (audit accuracy, residual of F2): reconcile still records "cookie cleared" from events only, without ending or consulting the session row
`apps/api/src/services/impersonation-audit.service.ts:55-95` (`reconcileFromAdminRequestCookie` → `recordLatestOpenSessionAsCookieCleared`)

1. **Expired session mislabeled.** The view times out while staff are on admin pages. The SSR call now carries the expired sid, which is not in `listActiveByActor` (`expires_at > now()` filter). The code falls through and emits `admin.impersonation_ended` / `cookie_cleared_after_failed_end` for that session, but the row's `ended_at` stays NULL. Later, `validateForRequest` ends the row with `timeout` and `recordSessionTimedOut` skips because `hasEndedEvent` is already true. The DB then says `timeout` while the audit event says `cookie_cleared_after_failed_end`.
2. **Second browser or device.** Staff have a live view in browser A and open any admin page in browser B, which has no cookie. A "cleared" event is written for the live session, the row stays open, and browser A keeps acting under a session that the audit log already shows as ended.

**Not a privilege issue:** access is always decided by `validateForRequest`. **Fix:**
- For a cookie sid the actor owns that is expired and not ended: end it with `timeout` and call `recordSessionTimedOut` instead of writing "cleared".
- In `recordLatestOpenSessionAsCookieCleared`, either end the row in the same transaction (`endForActor(id, actor, "cookie_cleared_after_failed_end")`, as `recordFailedEnd` already does), or skip sessions that `listActiveByActor` still reports as live.

Either way, the audit log and access must agree.

### N2: LOW (fail-closed): on SSR, the acting header and the forwarded view cookie can come from different duplicate cookies
- `apps/web/src/lib/data/http/server-request-headers.ts` `withViewSessionCookie` takes the **first** raw `lax_acting_legal_entity_id`.
- `apps/web/src/lib/legal-entity/acting-context.server.ts:82-84` `readBrowserChoice` (`cookies().get()`, the **last**) feeds `X-Legal-Entity-Id` and `findViewedAccount`.

In round 1 both came from one value, so this round introduced the divergence.

**Scenario.** A host-only cookie and a `Domain=` cookie both exist, for example one planted from a sibling subdomain or left over from an older deploy:
- The first is the view session for C and the last is a plain choice X. The header says X and staff act as their own member account X. That is safe, but the view banner state and the API disagree.
- The first is plain and the last is the view for C. The header says C but no session cookie is forwarded, so the API returns 403 `not_a_member_of_legal_entity`, which the fallback callers then retry into the staff member's own account.

A foreign sid always fails `actor_mismatch`. **Never another entity's context; at worst a confusing state or a DoS of the view.**

**Fix.** Pick the duplicate once. Either have `readBrowserChoice` parse the raw header with the same first-match rule as `viewSessionCookieHeader` and the API, or forward the exact value `readBrowserChoice` used. Add a test asserting the header `e` and the forwarded cookie come from the same pair. Keep `expireSharedActingCookie`.

### N3: INFO: switching to the viewed client's account while a view is live orphans the session
`apps/web/src/lib/legal-entity/acting-context.actions.ts:79-104` (`switchActingLegalEntity`)

The membership probe `GET /legal-entities/:id` now carries the view cookie (this was already true in round 1 for this default-flag call). For staff viewing C, `switchActingLegalEntity(C)` gets 200 (an impersonation detail) and overwrites the view cookie with a plain choice for C. Without a sid that choice is never forwarded, and the API refuses the non-member header, so this fails closed. But the session is never ended (it times out, or N1 mislabels it). **Fix:** treat `data.membership.isImpersonation === true` as `not_a_member` in the switch action, or end the view first.

### N4: INFO: test gaps
- `authed-server-fetch.fallback.test.ts` has only the "plain 403 retries" case. Add "does **not** retry on `impersonation_session_expired` / `invalid_impersonation_session`" and "retries on a non-JSON 403".
- `endForActor` has no persistence test, unit or integration. My throwaway integration test (below) passed, and it is worth committing as `drizzle-impersonation-session.repository.integration.test.ts`.
