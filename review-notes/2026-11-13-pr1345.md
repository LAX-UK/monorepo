## Findings

### F1. Medium (regression): dispute lines now deadlock with a refund on the same payment

- Where: `PayoutAdjustmentService.postLine` → `lockOpenPayout` (`packages/finance-runtime/src/payout/payout-adjustment.service.ts`). The doc comment says "Callers already hold the payment's lock … so the order is settlement advisory lock, then payment, then payout". That is not true for the dispute paths. `DisputeCaseRecorder.record` (Stripe dispute webhooks) and `DisputeAllocationService.allocate` (staff) lock the dispute case, not the payment, and then call `addPaymentLineToOpenPayoutOrCreateClawback(kind: "dispute")`.
- Mechanism: the dispute transaction now takes `payout FOR UPDATE` first. Its `INSERT INTO payout_line (payment_id …)` then needs `FOR KEY SHARE` on the payment through `payout_line_payment_id_fkey`. A refund transaction (staff refund, card webhook, refund reconcile job, give-back) holds `payment FOR UPDATE` and then waits for the payout row. That is a cycle.
- Reproduced (probe E, real Postgres): the refund path locks payment P, the dispute line-add for P runs, then the refund continues. Result: one transaction is aborted with **`40P01` deadlock detected**. With M1 (no early payout lock, i.e. main's behaviour), the same interleaving completes with no error. On main the dispute transaction blocked on the FK before it touched the payout row, so there was no cycle.
- Effect: there is no money error. Postgres aborts one side. A dispute webhook is retried by Stripe (the event claim rolls back). A staff refund whose ledger transaction is the victim is queued in `paymentRefundReconcile`. A staff dispute allocation gets a 500 and must be retried. This is a new failure mode on a money path, and the code documents a lock order that does not hold.
- Fix (small): make the order self-enforcing. In `postLine` (or in `addPaymentLineToOpenPayoutOrCreateClawbackFull`/`giveBackFailedRefund`), take the payment row lock (`lockPaymentInTransaction`, or a repo `FOR UPDATE` on `payment.id`) **before** `lockOpenPayout` whenever `paymentId` is set. Re-entrant locks make this a no-op for paths that already hold it. Alternatively, have `DisputeLineEffects.reconcile` lock every line's payment in id order before moving payouts. Add probe E as a regression test.

### F2. Low: after an unknown Stripe outcome the payout reopens for lines, so record and Stripe can still diverge (now loudly)

- With `keepScheduledOnTransferFailure` (the bulk run), a `StripeConnectionError`/`StripeAPIError` after retries moves the payout back to `scheduled`, even though Stripe may already have created the transfer. A line can then land. The next run's `decideConnectTransfer` finds the existing transfer at the old amount and blocks it.
- Reproduced (probe D): Stripe created a £820.00 transfer but the response was lost. The payout returned to `scheduled`. A £100 part refund then took the payout net to £754.40. The next run gave `transfer_blocked` (amount_mismatch). The record says £754.40, but Stripe sent £820.00.
- It is safe: no second transfer, and a person is alerted. But the PR's guarantee that payout net equals the Stripe amount holds per attempt, not across an attempt with an unknown outcome. Fix (follow-up): do not count a payout whose last attempt ended in a non-definitive error as open. For example, park it in a distinct status, or exclude `scheduled` payouts with `failure_reason LIKE 'stripe_transfer_failed:%'` from `findOpenPayoutForEntity`, so new lines go to a new payout. Until then, the runbook for `transfer_blocked`/amount_mismatch should mention "lines added after a failed attempt".

### F3. Low (pre-existing): the idempotency key is reused with a different amount after a refused attempt

- `transferIdempotencyKey` is `payout:transfer:<id>` for every non-`retryFailed` attempt. Probe C: the first attempt was refused with `balance_insufficient` and the payout stayed `scheduled`. A £100 refund landed. The second attempt sent the **same key** with amount 75440 instead of 82000. Stripe stores 400 responses against the key, so for up to 24h it answers `idempotency_error` (parameters differ), and the payout fails every run until the key expires. There is no money risk (`decideConnectTransfer` still prevents duplicates). Fix: include the amount in the key, e.g. `payout:transfer:<id>:<amountCents>`. The transfer-group decision already guards against a second live transfer.

### F4. Info: the payout row lock is held across Stripe HTTP calls

`withLockedPayout` holds the transaction (and a pool connection) through `decideConnectTransfer` (for pre-June-2026 payouts the legacy scan can be up to 100 list pages) and `createConnectTransfer`, each with up to 3 attempts and 2 s/4 s backoff. Line-adds for that seller's payout wait for this time while they hold their payment lock. The bulk run sends transfers one at a time, so only one payout is held at once. This is acceptable. Consider a `lock_timeout` on the line-add side, or document it.

### F5. Info: the `findOpenPayoutForEntity` change is not tested on its own

M4 (query back to `scheduled, in_transit`) fails no test. The re-check under the lock in `lockOpenPayout` masks it. That is good defence in depth, but a persistence test asserting that an `in_transit` payout is not returned would pin the query.

### F6. Info: `lineExistsForSourceEvent` runs only on the open-payout branch

The new-payout branch does not check the source event, and `payout_line_source_event_uidx` is per payout. With `in_transit` no longer open, more replays reach that branch. No double line was found or reproduced: refund lines are gated by measuring against the `payment_refund` records under the payment lock, give-backs by the `stripe_refund_reversal` claim, disputes by the allocation's clawback state, and the admin reconcile by its queue row. Noted so that a future caller does not rely on the source-event id alone.

## Summary

The R2-1 fix works end to end against real Postgres. Only `scheduled` payouts take lines, both sides take `FOR UPDATE`, the net is re-read under the lock, and the Stripe amount equalled the payout net in every interleaving I ran (refund vs transfer, give-back vs transfer, concurrent line adds). Lines that arrive after the transfer go on a new payout that the next run sends. #1338's commission rules, grants, typecheck and lints are all fine. Every key fix has a test that fails when it is reverted, except the query change (F5).

The early payout lock adds a **new deadlock** (F1) between dispute lines and refunds on the same payment, because the dispute paths do not hold the payment lock that the new code assumes. It self-heals through retries, so no money is wrong. But it is a regression on a money path, the documented lock order is false, and the fix is a few lines plus one test. F2 and F3 are Low follow-ups. F4 to F6 are info.

### Verdict: FIX FIRST

### F3 idempotency key

- No path produced two live transfers. The payout row lock serialises attempts (bulk run, resume loop, staff retry), and `decideConnectTransfer` runs before every create.

### Other notes

- **N2 (Info, test gap).** The id order in `lockPaymentsInTransaction` is what keeps a dispute and a group refund on the same group from crossing. Reversing it fails no test. A one-line assertion on the SQL order, or a two-payment test against a group-refund lock, would pin it.
- **N3 (Info, pre-existing).** Two transactions that each move payouts for **two sellers**, in opposite seller order, can still deadlock on the payout rows. An example is two group-charge disputes or group refunds whose invoices span the same two sellers. Probe **P3** gets 40P01. With main's line-add behaviour (no payment lock, no payout `FOR UPDATE`, rebuilt), the same probe also gets 40P01 on the totals `UPDATE`, so this is not a regression. Postgres aborts one side, and the webhook retry or reconcile queue recovers it. It could be closed later by moving payouts in legal-entity id order.
- **N4 (Info, pre-existing; corrects the first review's checklist).** A payout created with a negative net, for a line that found no open payout, stays `scheduled`. `listScheduledPayoutsAwaitingTransfer` takes only net > 0, so the run never moves it to `clawback_pending` (probe **P8**). It nets only against later lines for that seller, or through staff action. Because `transfer.created` marks a payout `paid` within seconds, this PR only slightly increases how often such payouts appear. Consider a follow-up that surfaces or nets negative scheduled payouts.
