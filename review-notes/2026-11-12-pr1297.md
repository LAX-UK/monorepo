### F2: MEDIUM: Accept doesn't re-check the bidder account's standing (Send does)
- **File:** `apps/api/src/services/reoffer/reoffer-response.service.ts:153-175` (compare `reoffer-offer.service.ts:159`)
- **Scenario:** staff send an offer to underbidder account X (active). Before X answers, X defaults on another lot, and the buyer-default flow restricts X's account. Alternatively, X is suspended, archived, or asks for deletion. X's member still has an active membership, and `requireLegalEntityContext` (header path) doesn't check entity status. `acceptLocked` checks the window, the transition, consent, ATG, the place guard and the pause hook, but never `accountState`. `reawardGuard` doesn't check it either. Refuse with `bidder_unavailable` unless `accountState === "active"`, as `sendLocked` does. ### F4: LOW: Accept isn't idempotent for the same account
- **File:** `reoffer-response.service.ts:155-158`
- **Scenario:** a double-click or network retry of `POST /legal-entities/reoffers/:id/accept` from the account that already accepted gets `409 offer_not_open` ("This offer is no longer open."). The integration test "two accepts of one offer award the lot once" pins this. Money is safe (one award, one invoice), but the buyer who has just bought is told the offer is closed.
- **Fix:** when `offer.status === "accepted"` and `offeredLegalEntityId === actor.legalEntityId`, return the stored `AcceptOfferResult` (from `respondedAt`) with 200 and don't re-record events. Keep 409 for any other account.

### F5: LOW: the `invoiceDueAt` returned by Accept can differ from the stored invoice due date
- **File:** `reoffer-response.service.ts:86,204`
- **Scenario:** the response says due = `invoiceDueAt(acceptedAt)`. The invoice is raised after commit with `invoiceDueAt(raisedAt)`. If `raiseFor` fails and the backfill raises the invoice later (another London day), or if the accept lands just before London midnight, the buyer is shown a due date one or more days earlier than the stored one.
- **Fix:** either raise the invoice with `raisedAt = respondedAt`, or return the stored invoice's `dueAt` when `raiseFor` succeeds and omit or soften the figure otherwise.

### F6: LOW: the bidder workspace takes the lot row lock before the ownership check; small existence oracle
- **File:** `reoffer-response.service.ts:141-145`, `reoffer-lock.ts`
- **Scenario:** any signed-in buyer with any `reofferId` makes the API take `FOR UPDATE` on someone else's lot before getting `offer_not_found`. A deleted lot answers `404 lot_not_found` instead of `offer_not_found`, which tells the caller the id exists. Impact is minimal (UUIDs, short locks), but it isn't the "simply not there" behaviour the docstring promises.
- **Fix:** do an unlocked `findForBidderAccount(actor.legalEntityId, id)` first and 404 when it's missing, then lock. Map `lot_not_found` to `offer_not_found` on member routes.

### F8: INFO: the accept-vs-pay race test models a lock the real payment writers don't take
- **File:** `reoffer.integration.test.ts:906-946`
- In the test, the payment path holds the lot's `FOR UPDATE`. The real capture paths (Stripe webhook, bank-transfer apply) don't lock the lot row. Under READ COMMITTED, the re-award's payment read sees only committed rows. ## What I attacked and found sound
- **Two accepts / accept vs withdraw / send vs withdraw / staff vs bidder:** every step uses `lockLotAndOffer` (lot, then offer, the same order as the re-award), and `changeStatus` carries a `from` guard. Both race tests pass and I re-read the code paths. No deadlock order inversion.
- **Accept vs new default:** a new default needs a winner, and the lot has none until the re-award. The re-award refuses `offer_superseded` against the latest default under the lock, and `already_reawarded` is honoured only while the default is still the latest.
- **Money rules:** `reawardBlock` refuses any paid, being-paid or held payment and any other accepted offer. A refusal throws inside the transaction, so the acceptance rolls back (tested). Nothing writes a charge to the defaulter. The claimable shortfall is staff-only and never in member shapes.
- **Price derivation:** `placedBids` selects `bid.amount` only (`max_auto_bid_amount` is never read). Send re-verifies source bid id, user, entity and amount. Pence come from `decimalToPence`. The bidder total comes from `InvoiceRaiser.price`, the same pricing the invoice uses, and the strict schema enforces total = lines.
- **Window:** `offerEndsAt` gives London 17:00 on day N (sends after 17:00 start the next day), validated 1–7 at the zod and service layers. DST is handled by `londonInstant` (PR 2 domain, already reviewed).
- **Authorisation:** start, send and withdraw need `BUYER_DEFAULT_ACCESS` at route and service. Seller answer needs `auction.manage` and a note. All four are in `DANGEROUS_STAFF_ACTIONS` with `requireStepUp`. Members: accept and decline need `entity.bid.place` and `requireBuyerRole`. Impersonation is refused (`entityActorCan` denies writes). Seller answer needs `entity.consignments.after_sale`, and seller reads need `entity.consignments.read`.
- **IDOR:** bidder reads and answers are scoped by `offeredLegalEntityId`, and the seller's by the lot's `sellerLegalEntityId`, each returning 404 for another account. No GET mutates (email links cannot accept).
- **Identity leakage:** member views are `.strict()` zod shapes. The seller view has no bidder and the bidder view has no seller or defaulter. Events carry ids and amounts only and are consumed by admin labels only.
