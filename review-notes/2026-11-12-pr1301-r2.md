## The new count endpoint: permission and scope

- **Auth:** the route sits under `admin.use("/private-sales/*", requireDealsRead)` (`routes.ts:82-83`), the same read guard as the list. It is declared before `/:ref`, so it is never parsed as a deal reference. The new route tests check that administrator, sales_manager, specialist, finance and client_services get 200, that cataloguer, saleroom_clerk and read_only get 403 with the service not called, and that `detail` is never invoked.
- **Scope:** `attentionCount(viewer)` → `countSettlementFollowUps(viewer.scope)` applies the same `scopeConditions` (owned, stages or all) as the list and as `needs_attention`. The `needs_attention` criteria (`stages:["settled"]`, `ownedByViewer:false`, follow-up predicate) match the aggregate, so the badge equals the view total for the same person. Only two integers are returned; no references or IDs leak.
- **Web:** the count is gated on `PRIVATE_SALE_DEALS_READ_ACCESS` before fetching, is fetched per person with the user's own token (`authedServerFetch`), and is not written to the shared nav cache. Unchanged from round 1.

## Regressions looked for, none found

- `list()` still returns the same shape. `dealViewCounts(stages, total)` takes the same argument as before, now uncapped.
- `unraisedOnly` only changes the cron's input. The UI list, the deal page and the counts do not pass it. The cron result's `open` now means "not yet raised at current severity". It is only logged and returned from the internal route.
- The `EXISTS` subquery on `domain_events` is served by `domain_events_aggregate_idx`, and it runs only in the daily check.
- `desc(urgent)` cannot see NULL, because `offer_state` is NOT NULL and both ref comparisons are NULL-safe.
- No migration, no schema change. The audit log stays the record for "raised".

## Optional nits (LOW, do not block)

1. **The committed matrix test checks the urgent aggregate only with `>=`.** `…follow-up.integration.test.ts:327-328`. An SQL urgent predicate that over-counted (for example, one that also counted `held`) would still pass. The fix is to take `countSettlementFollowUps` before inserting the cases and assert `after − before` with `toBe(expectedTotal)` and `toBe(expectedUrgent)`, as my ad-hoc run did, or to count under an `owned` scope for a fresh user. The current code is correct; this only strengthens the guard.
2. **Old 2-argument marker calls remain** at `…follow-up.integration.test.ts:247,253,255` (`claimInTransaction(db, id)` with no severity). Test files are excluded from `packages/persistence` `tsc`, so CI does not catch this. At runtime `undefined` severity behaves as `"normal"`, so the tests still pass. The fix is to add `"normal"` so the calls match the new signature.
3. (Cosmetic) The truncation log fires when exactly 500 deals are open and unraised, even if nothing was cut off. This is harmless.
