# Review — PR #1324 `bs1-reoffer-public` (underbidder re-offer, PR 9: public result)

Reviewed: `origin/bs1-reoffer-public` @ 638f9025 against `origin/main`, 2026-11-12. Independent review covering privacy, money and design. The PR branch was not changed.

## Verdict: FIX FIRST

The core design is right. One SQL predicate (`lotResultPendingSql`) decides whether a result is pending, and an API presenter (`withPublicLotResults`) removes the winner, buyer entity and price. Staff reads skip the presenter. The covered paths are correct and tested.

**However, three non-staff read paths never go through the presenter.** They leak the defaulter's hammer to the public, and to any watcher or losing bidder. After a re-award they also leak the new buyer's ids and the re-offer price. RA17 says the default, the original hammer and every identity must never show for a pending lot, so these three must be fixed before merge.

### Why the leaks exist

`DrizzleBuyerDefaultRepository.record` (`packages/persistence/src/repositories/drizzle-buyer-default.repository.ts:164-168`) clears `winner_id` and `buyer_legal_entity_id` but **keeps `lot.current_price`** (the defaulter's hammer). The re-award (`drizzle-lot-reaward.repository.ts:165-175`) then writes a winner, a buyer entity and the offer amount back.

So any read that skips the presenter shows a pending lot in one of two ways:
- **Before re-award:** no winner, but `currentPrice` is the defaulter's hammer.
- **After re-award, unpaid:** a fully sold lot, with the new buyer's ids and the offer price.

## Blocking findings

### B1. `GET /sales` preview lots skip the presenter (public, cached)
- **Where:** `apps/api/src/services/sale-list-read.service.ts:76-110`.
- **What happens:** `previewLots` comes from `lotRepo.findPreviewLotsBySaleIds`, which takes the first 4 public lots per sale, ended lots included. The lots go through `mapLotToSummary` only, never `withPublicLotResults`.
- **Scenario:** lot 1 of an ended sale defaults. `/sales` now returns:
  - before re-award: `currentPrice` = the defaulter's hammer;
  - after re-award: `currentPrice` = the offer amount, plus `hasWinner: true`.
- **Visibility:** the home page and sales index read this, and it sits behind Redis (20s) and CDN (s-maxage 30, swr 60) caches. The `resultsSummary` beside it *is* covered, so the page contradicts itself.
- **Fix:** for non-preview viewers, wrap `previewLots` in `withPublicLotResults(publicLotResults, …)` before filter/map. Wire `publicLotResults` into `SaleListReadService` in the container.
- **Same gap, unused:** `listSalesForPublicApi` in `apps/api/src/services/sale/sale-read.ts:110` has it too. Nothing calls it, but it is exported on SaleService, so fix it or delete it.

### B2. `GET /users/me/watchlist` returns the raw lot (any signed-in user)
- **Where:** `apps/api/src/services/user-dashboard-read.service.ts:56-104`. `listWatchlistForUser` → `attachEnrichedLots` → `withCheckoutPricing` never calls `presentForPublic`, and never calls `maskLotForPublicView` either.
- **Scenario:** a watcher of a defaulted lot gets `currentPrice` and `checkoutPricing` built from it.
  - **After re-award:** they get `winnerId` and `buyerLegalEntityId` of the next bidder, and the web page reads "sold for £{offer}" (`apps/web/src/lib/watching/watching.vm.ts:86-93`; `standingOf`/`figureFor` ignore `resultPending`).
  - **Before re-award:** the page says "not sold", which is wrong and contradicts the later "Sold for".
- **Fix:**
  1. In `attachEnrichedLots`, run the lots through `withPublicLotResults` for every lot the viewer is not the buyer of.
  2. Strip `winnerId` and `buyerLegalEntityId` unless they belong to the viewer (see P1).
  3. In `watching.vm.ts`, map `resultPending` to an "Ended" standing.

### B3. `GET /users/me/bids` returns the raw lot (every bidder on the lot)
- **Where:** `user-dashboard-read.service.ts:37-40`, the same `attachEnrichedLots` path as B2.
- **Scenario:** every losing bidder sees the defaulter's hammer while the lot is pending. After the re-award they see the offer price and the new buyer's `winnerId` and `buyerLegalEntityId`.
  - These are exactly the people best placed to infer the default: they watched the hammer fall.
  - Invoices are correctly scoped to the viewer's own lots (lines 110-123).
- **Fix:** same as B2. Present for public unless `lot.winnerId === viewer.userId` or `lot.buyerLegalEntityId === viewer.accountId`. The new buyer must still see their own price.

**Tests to add with the fix:** one API test per path above (sale list, watchlist, my bids) with a stubbed reader returning the lot as pending. Also add an integration test for both the pre-re-award and the post-re-award-unpaid states.

## Non-blocking findings (fix in this PR if cheap, otherwise follow up)

- **N1. Price sorts order by the real price** (low, but a real side channel).
  - **Where:** `/lots?sort=hammerDesc` (`packages/persistence/src/repositories/lot/lot-list-filters.ts:158`) and the sale lots page `priceAsc`/`priceDesc` (`lot-list-filters.ts:124-126`) sort on the real `current_price`.
  - **Scenario:** a pending lot shows its starting price but sits where its hammer puts it. "Ended" at the top of a "highest hammer" archive gives the hammer away.
  - **Fix:** in those ORDER BYs, use `case when <pending> then null else current_price end` (nulls last).
- **N2. `GET /lots?winnerId=<uuid>&status=ended` is accepted on the public list** (`packages/validators/src/lot/list-query.ts:38`, applied in SQL at `lot-list-filters.ts:78`, before the masking). If the next bidder's user id is known, a match shows they are the buyer of a re-awarded pending lot. This works the same way for every sold lot (see P1). **Fix:** honour `winnerId` only for staff viewers.
- **N3. `reserveMet` reads `false` for a pending lot.**
  - **Cause:** `asResultPending` sets `currentPrice = startingPrice`, so `toPublicLotView` works out `reserveMet` from the starting price. A lot that sold above its reserve now says "reserve not met", which contradicts the later "Sold for".
  - **Fix:** in `asResultPending`, return `reserveMet: null` (or drop `hasReserve`/`reserveMet`) for pending lots.
- **N4. Web caches are not refreshed after a re-award or payment capture.**
  - **What is refreshed:** only on recording the default (`apps/web/src/lib/actions/admin/admin-lots.ts:326-329`), and only when the lot has a `saleId`.
  - **Effect:** after a re-award or payment capture, the switch to "Sold for [new hammer]" waits for the 60s fetch revalidate. This is not a leak, only a delay.
  - **Also:** after the default, `/lots` and `/sales` keep showing the old hammer for about 1–2 minutes (Redis 20s, CDN 30+60s). The plan accepts this, but the runbook should say it.
  - **Fix:** call the same revalidation from the re-award and payment-captured paths.
- **N5. The underbidder notification stores the defaulter's price in `meta.amount`** (`notification.factory.ts:293`). It goes only to the offered underbidder, and the offer itself is that amount, so I consider it acceptable. Confirm `/me/notifications` returns only the caller's own rows.

## Money

- **Archive total:** excludes pending lots, and includes a re-awarded lot at its new price once paid. Correct.
- **Results summary:** a pending lot is `excluded`, counted neither as sold nor as unsold, and adds nothing to the total. Correct. Sell-through moves when the result becomes final, as expected.
- **Seller views** (Sold & payouts, payout detail, CSV "Sold after the auction", statement PDF): use `lotSoldAfterAuctionSql`. The statement now says "sold after the auction to the next bidder" instead of the next bidder's name (`payout-statement.renderer.ts:33-36`). Good.
- **Predicate:**
  - Only the latest default counts.
  - If the lot went back to inventory and sold again, `end_time > bd.created_at`, so it reads as any other lot.
  - A re-awarded buyer is matched on both user and legal entity.
  - Payment is checked as captured for that buyer entity.
  - The 9 integration cases cover these.
  - One edge is untested: a captured payment from the **defaulter's** entity, if the same entity is later re-awarded. This cannot happen given that the offer goes to a different bidder; noting it only.

## Grant (least privilege)

- `WORKER_REOFFER_READ_COLUMNS` adds `outcome` as a **column-level** SELECT. Verified on the throwaway DB: worker_app's column privileges on `buyer_default` are exactly `id, lot_id, created_at, outcome`, with no table-level grant. The contract test passes. The hammer, buyer and reason stay hidden.
- **Nit:** no worker code in this PR calls `lotResultPendingSql`. The worker only uses `lotSoldAfterAuctionSql`, which reads `lot_reoffer`, already granted. The commit message ("so a public total leaves out an open result") names no worker caller. Either point to the worker query that needs `outcome`, or drop the grant until one exists. Harmless either way: `outcome` is a non-identifying enum.

## Copy and design

- "Ended" badge, card and rail labels, and "Result: Ended" match RA17. Good.
- **"The result will be published here when it is final"** (`packages/domain/src/lot-page/price-block.ts`, `endedPending` subLine) is builder wording, not approved copy, and I recommend **removing it**:
  1. A normally ended lot shows "Sold for" or "Not sold" at once. Only a defaulted lot carries this sentence, so it signals that something went wrong, which RA17 exists to hide.
  2. "Published", "final" and the passive voice are bureaucratic, and the house style does not use them.
  - **Recommendation:** no sub-line at all, which is what RA17 specifies. If design wants a line, it must go through design review. It should be neutral and not imply a pending process, and it should not be added on this PR.
- Seller copy: "Sold after the auction to the next bidder" is clear and anonymous. The CSV column "Sold after the auction" with "Yes"/blank is fine.

## Pre-existing issue: `winnerId` on public lot payloads

**Verdict: yes, it is a privacy leak. Severity: medium-high.** It is not caused by this PR.

**What is exposed.** `toPublicLotView` (`apps/api/src/lib/lot-public-view.ts`) removes only `reservePrice`. So `GET /lots/:id` (and list rows before `mapLotToSummary`) carries, for every sold lot:
- `winnerId`: the buyer's internal user UUID;
- `buyerLegalEntityId`;
- `sellerId` and `sellerLegalEntityId`.

**How it links to a person or account.**
1. **Full bidding history.** Public bid rows carry `bidderRef = sha256(lotId + ":" + userId)[:16]` (`apps/api/src/lib/lot-bidder-ref.ts`), unkeyed. With a `winnerId`, anyone can compute that buyer's `bidderRef` on every other lot via `GET /lots/:id/bids` (optionalAuth, i.e. public). That gives every bid they placed platform-wide (amounts, times, lots lost), not just their wins.
2. **Every purchase.** `GET /lots?winnerId=<uuid>&status=ended` is accepted publicly, so one id lists everything that person bought.
3. **Buying linked to consigning.** The same UUID appears as `sellerId` on lots they consigned.
4. **From pseudonym to name.** The profile is pseudonymous, but one outside fact ("I bought lot 42", a paddle seen in the room, a press piece) names the person and unlocks the whole history. Under UK GDPR a stable cross-context identifier is personal data, so this is profiling exposure.

**Minimal fix** (separate PR; not trivial enough to fold in here, because web components read `winnerId`):
1. In `toPublicLotView` / `maskLotForPublicView`, drop `winnerId`, `buyerLegalEntityId`, `sellerId` and `sellerLegalEntityId` for non-staff. Send `hasWinner: boolean`, plus `viewerIsWinner: boolean` when the viewer is the buyer.
2. Switch the web consumers (`lot-state-pill.tsx`, `lot-status-badge.tsx`, `onsite-lot-hero.tsx`, `home-view-models.ts`, `sales-view-models.ts:52`, `saleroom-lot-catalog-overlay.tsx`, `watching.vm.ts`) to `hasWinner` / `viewerIsWinner`.
3. Restrict the `winnerId` list filter to staff (N2).
4. Defence in depth: key `lotBidderRef` with a server secret (HMAC) so refs cannot be computed from a user id.
5. Check the realtime `lot_ended` / saleroom live patch (`saleroom-catalog-lots-live.tsx:90` reads `patch.winnerId`), which broadcasts `winnerId` at close.
