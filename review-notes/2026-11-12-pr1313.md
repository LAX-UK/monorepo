### `7e6f3a7f` expiry ends and audits in one transaction. pr1303 **R2**: ✅ matches
- `apps/api/src/services/impersonation-session.service.ts:70-74`: `validateForRequest` only reports
  `expired` and no longer ends the row in autocommit. `recordSessionTimedOut`
  (`impersonation-audit.service.ts:28-39`) goes through `endAndRecord`. It ends the row and publishes
  in one transaction, and publishes only if this call ended the row. That removes both R2 failure
  modes: N duplicate events, and an ended row with no event after a crash.
- **Regression check:** without `validateForRequest`'s own `end()`, the row must be ended by the caller. I
  checked every caller that passes `impersonationSessions` also wires `onImpersonationExpired` →
  `recordSessionTimedOut`. They are `container/create-platform-identity-services.ts:109-112`,
  `container/create-user-profile-services.ts:117-121`, `routes/payments.ts:55-64` (both
  middlewares), and `services/legal-entity-access.service.ts:77-90` (direct). The middleware passes
  `actorUserId = input.userId`. `validateForRequest` has already refused `actor_mismatch` and
  `entity_mismatch`, so `endExpiredForActor`'s actor predicate always matches on this path, and the
  expired row is ended. The request is still refused with `impersonation_session_expired`, as before.
  There is no window where an expired session is usable: `validateForRequest` checks `expiresAt` on every
  request, whether or not the row was ended.
- Rolling-deploy overlap with the old release is harmless. The old release ends the row and writes its
  event. A new instance then finds the row ended → no second event.

### `58b6d2c0` refuse a credit note when a prior one is missing. pr1305-r2 **F7**: ✅ matches
- `packages/accounting-domain/src/document.ts:480-489`: after the priors are replayed, for each role
  (goods, delivery), it refuses with `bad_invoice` when the credited gross is lower than
  `buckets.refunded{Goods,Delivery}Pence`. It refuses only when lower, as the review allowed. The
  README (`README.md:70-71`) and the docstring state the runtime contract: every credit note except
  `cancelled`/`failed`, in creation order. The test `document.test.ts:469-486` reproduces the review's
  omission and also has a positive case.
- `buckets.refunded*` is "refunded before this request" (`refund.ts:39-46`, `planRefund` subtracts it),
  so a normal second credit note with all priors passes, as the test shows.
- **Operational note (Low, for the runtime PR):** the check also fires when a refund exists that has no
  credit note counted among the priors. Examples: a credit note in `failed` (until it is requeued
  and issued) or in `cancelled`, or a refund made before the invoice was issued. All further credit
  notes for that invoice are then refused until staff resolve it. That is fail-closed and correct for
  money. The runtime should show `bad_invoice` with this message in the staff review queue rather than
  retry it.
