## JOB A: invoice raise locks the lot (fixes F1 from the PR #1310 review)

### Per finding

- **F1 (MEDIUM): fixed.**
  - `DrizzleBidInvoiceRepository.raise` (`packages/persistence/src/repositories/drizzle-bid-invoice.repository.ts`) now starts its transaction with `lockLotSoldTo`. That runs `SELECT status, winner_id, buyer_legal_entity_id FROM lot WHERE id = $1 FOR UPDATE`. The lot is locked first, the same order buyer default and re-award use.
  - It then requires `status = 'ended'`, `winner_id = winnerId` and `buyer_legal_entity_id = invoice.buyerLegalEntityId`. If any of these fails it throws `BidInvoiceLotMovedError` (`packages/persistence/src/interfaces/bid-invoice.repository.ts`) and stores nothing.
  - `ensureForLot` (`packages/finance-runtime/src/lot-invoice-initiation.service.ts`) maps the error to `{ created: false, reason: "lot_moved" }`. It stages no notice, does no Xero write and records the metric `invoice_raise_lot_moved`.
  - Checkout (`createOrJoinPaymentRecord`) maps it to `409 lot_moved` rather than a 500.
  - **Deviation from the brief, and why.** The brief asked for the check `winner_id = paidByUserId`. The check is instead against a new required `winnerId` input, which `InvoiceRaiser` fills from the lot it read. At lot end (`ensureForLot`) `winnerId` and `paidByUserId` are the same value. At checkout `paidByUserId` can be one of an organisation's payers, not the winner (`createPendingForWinner` docstring). A literal `winner_id = paidByUserId` check would refuse every organisation-payer checkout.
  - No migration was needed.
- **F2 (LOW): not done.** `acceptedWithoutInvoice` (`drizzle-reoffer-sweep.reader.ts`) and the re-offer sweep job are not on `origin/main`, because PR #1310 has not merged. To pick up after #1310 lands: add `lotNotDeleted()`, and alert on, or mark, any outcome that is not `raised`. `lot_moved` from this PR is one more of those terminal reasons.
- **F3 (LOW): not done,** for the same reason. After #1310: add `eq(lot.buyerLegalEntityId, lotReoffer.offeredLegalEntityId)`, and restrict `NOT EXISTS` to the open payment statuses plus `refunded`.

## JOB B: PR #1314 security review (signed-in devices plan, PR 5)

- **Branch:** `auth/new-device-email-export-cookie-page` @ `654e1b33`. Its merge base with `origin/main` is `a2dd250a`. The branch was read only and nothing was pushed to it.

### Verdict: FIX FIRST

The marker handling itself is sound:
- The raw marker is never stored or logged.
- The hash is a keyed HMAC.
- The marker check is scoped to each person.
- A browser that does not hold the person's own marker cannot use one to suppress their alert.

Two medium issues should be fixed before merge. Both are small.

### Findings

#### S1: MEDIUM. A browser the person signs out from the devices list stays "known" forever, so the attacker's next sign-in from it sends no email

- **Where:**
  - `apps/auth/src/services/security-notice.service.ts:247-254` (`knownBrowser` short-circuits with no time window)
  - `apps/auth/src/infrastructure/drizzle-known-device.store.ts:49-60` (`hasSeen` ignores `lastSeenAt`)
  - `apps/auth/src/services/account-identity.service.ts:131` and `:153` (`revokeSession` and `revokeOtherSessions` never forget the marker row)
- **Scenario:**
  1. An attacker with the password signs in from browser X, and the person gets the alert.
  2. The alert now says "Open your signed-in devices, sign out any you don't recognise" (`new-device-login.tsx`), so the person signs X out.
  3. The marker row for X is still in `auth_known_device`, so every later sign-in from X (password not yet changed, or obtained again) is `knownBrowser = true`, with no email, and with no time limit.
  4. Before this PR, the label rule also went quiet, but only while X kept signing in at least every 90 days. The marker makes that permanent.
- **Fix:**
  1. When a session is revoked by the person (one device, or all others), and on password reset or change, delete the `auth_known_device` row `fingerprintMarker(userId, session.device_hash)` for the revoked sessions.
  2. Give `hasSeen` the same `KNOWN_DEVICE_WINDOW_MS` window (`lastSeenAt >= at - 90d`).
  3. Test: sign in from X, sign X out, sign in from X again, and expect an email.

#### S2: MEDIUM. The new token-table reader sits outside the export exclusions contract, so the guard on `oauthAccessToken` no longer covers what the export reads

- **Where:**
  - `apps/auth/src/infrastructure/drizzle-session-clients.reader.ts:1-44` reads `oauthAccessToken`.
  - `exclusions.queries.contract.test.ts:12-14` scans only `categories/*.category.ts`, and it pins `oauthAccessToken` as a forbidden table ("access and refresh tokens").
  - The reader is injected into `SignInAndSecurityExportCategory` from `create-account-subject-export-categories.ts`. "No reader reads oauthAccessToken" still passes on this branch.
- **Is it within the contract's intent?** The current query is: it selects only `sid` and `clientId`, filtered by the subject, and maps them to four product names. The placement is not. A later edit to this file (for example `select()` or `accessToken`) would put token values into the "Download my data" file, and no test would fail.
- **Fix:**
  - Bring the reader under the contract. Add the file to the scanned set (or move it to `categories/`).
  - Replace the blanket table ban with a column rule for it. Allow `oauthAccessToken.sid`, `.clientId` and `.userId` only in this file, and forbid `oauthAccessToken.accessToken`, `.refreshToken`, `.id` and any bare `.select()` or `.selectDistinct()` without fields.
  - Add an assertion to the integration test that the export JSON does not contain the seeded `access-`/`refresh-` token strings.

#### S3: LOW. "New-device email enabled when APP_ENV=test": the test-site recipient allowlist that the code comment relies on is not in this repo, and the change is a no-op for deployed images

- **Where:** `apps/auth/src/services/new-device-email-policy.ts:5-9`. The comment says "the email service only delivers test-site mail to seeded and owner addresses".
- **What I checked:** no recipient allowlist or redirect exists in the worker's email path (`apps/worker/src/services/send-email.use-case.ts`, `register-email-worker.ts` → `PostmarkEmailSender`), nor in `packages/email`, the workflows, `docker-compose*` or docs. The only recipient filter is suppression.
- **However:** `apps/auth/Dockerfile:56` sets `ENV NODE_ENV=production` for every deployed auth image, including test. So the email was already on in the test environment before this PR, and `APP_ENV === "test"` changes only a non-production `NODE_ENV` run with `APP_ENV=test` (none in CI).
- **Exposure:** the recipient is always the signing-in account's own address (at most 3 per day), so this sends no mail to a third party beyond what test-site sign-up already does.
- **Fix:**
  - Either point the comment at where the restriction really lives (for example a Postmark test-server setting outside the repo), or remove the claim.
  - Consider dropping the `APP_ENV` clause, since it does nothing.
  - If an allowlist is meant to exist, add it in the worker sender for `APP_ENV=test`, with a test.

#### S4: LOW. The marker is remembered before deciding whether to email, so a capped or failed notice still marks the browser as known

- **Where:** `security-notice.service.ts:251-258`.
- **Scenario:** `remember` runs before the per-day cap (`NEW_DEVICE_NOTICES_PER_DAY = 3`) and before `send()`. `notify` swallows a send failure, and there is no retry for `sign_in`. An attacker who signs in from 3 fresh browsers in a day (the person gets 3 emails) can then sign in from a 4th, which gets no email, is remembered, and stays silent permanently (see S1). A transient queue failure has the same result for the first browser.
- **Fix:** when a notice is due, remember the marker only after `send()` succeeds (next to `markNotified`). Remember it unconditionally only when no notice was due.

#### S5: INFO

- **Isolation test gaps:** the test does not seed another person's token on the subject's own sid (the `userId` filter is what protects that case). It also does not assert that token values are absent from the output (see S2). `afterAll` leaves the five `oauth_application` rows and relies on cascades for tokens and sessions.
- **Marker rows appear in the export:** they show up as extra `kind: "device"` entries (`mapKnownDevice`), duplicating each browser. Either filter them out or describe them.
- **Cookie policy row (`apps/web/src/app/(marketing)/cookies/page.tsx`):** the purpose given is only "replace that browser's sign-in". It now also decides whether the new sign-in email is sent, so say that. It says "renewed when you sign in", but `device-session-hook.ts` also renews the cookie on page navigations. The strictly-necessary classification still holds, since this is security.
- **Marker rows count towards `hadOtherDevices`** in `touch`. This is harmless: the first sign-in has no marker yet.
