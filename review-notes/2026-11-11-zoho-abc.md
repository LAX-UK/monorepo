## A #1284 ic-a-zoho-status-compare-and-set: FIX FIRST

The core design is sound:
- `decideStatusWrite` writes only when Zoho shows null, Available, or what LAX last wrote. Anything else becomes a conflict.
- The Product is read again just before the write, and the write is dropped if Status or Modified_Time changed.
- A Product modified after the facts were read is treated as stale.
- Withdrawn becomes Available after 30 days through the same compare.
- The migration backfill and rollback were exercised against a real database and pass.

### A-1 [HIGH, prior finding still true]: staff's Sold/Reserved is recorded as LAX's own written value, and is later overwritten
- **Where:**
  - `apps/worker/src/integrations/zoho/artwork/status/zoho-status-sync.ts:243-250`. In the `in_sync` case, `recordCatalogueStatusWritten({ status: wanted })` runs whenever `ledger.written !== wanted`.
  - `packages/persistence/.../drizzle-artwork-register.repository.ts:~472-480`. This sets `catalogueStatusWritten = input.status` even when LAX sent nothing.
  - The test at `zoho-status-sync.test.ts:179` ("records the written Status when Zoho already held it, without sending") asserts this behaviour.
- **Failure scenario (reproduced):**
  1. Staff set Sold in Zoho by hand. The LAX register is also `sold`, so it wants Sold. The decision is `in_sync`, and `written` becomes "Sold" although LAX never wrote it.
  2. Later the register moves on, for example the sale is reversed and the artwork is put back on lax.art. LAX now wants Available. Zoho shows "Sold", which equals `lastWritten`, so the decision is `write`.
  3. **LAX writes Available over staff's Sold.**
  4. The same happens with staff Reserved while LAX is `private_sale` (wanted Reserved), followed by a move to `bid_sale`: LAX writes "In Auction" over staff's Reserved.
- **Fix:**
  - In the `in_sync` branch, never set `catalogueStatusWritten` from a value LAX did not send. Split the repository call so the `in_sync` path only closes an open Status conflict (and may refresh `catalogue_status`), and `catalogue_status_written` changes only after an actual `products.write`. One way is a `closeCatalogueStatusConflict(registerId)` method, or a `{ wrote: boolean }` flag on `recordCatalogueStatusWritten`.
  - Flip the test at :179 so `written` stays null.
  - Add a two-step regression test: staff Sold with LAX sold, then register lax_art, must give a conflict and no write.

### A-2 [MEDIUM]: the nightly Status reconcile, and so Withdrawn → Available after 30 days, only runs when the *listing* mode is on
- **Where:** `apps/worker/src/container/create-zoho-artwork-listing.ts:40`, `:65-75`, and `create-worker-container.ts:~391`. `ZohoStatusReconcile` is built only inside `createZohoArtworkListing`, which returns `undefined` when `ZOHO_ARTWORK_LISTING_MODE=off`. The only schedule for it is `runZohoListingNightlyCheck`.
- **Failure scenario:** set `ZOHO_ARTWORK_WRITEBACK_MODE=live` and `ZOHO_ARTWORK_LISTING_MODE=off`. Both default to `off`, and each environment chooses them separately. An artwork is withdrawn and LAX writes Withdrawn. No register event fires on day 30, and the nightly status check never runs, so **Zoho shows Withdrawn forever**. Drift where a register event was missed is also never repaired.
- **Fix:**
  - Schedule the Status reconcile on its own, gated on the writeback mode. For example, build it in `createZohoArtworkWriteback` or `createZohoStatusSync` and register its own nightly job.
  - Alternatively, fail startup or log an error when writeback is live and listing is off.
  - Add a container test for "writeback live, listing off ⇒ status nightly scheduled".

### A-3 [LOW]: the migration backfill misses Statuses written before the column existed when no event was recorded
- **Where:** `packages/db/drizzle/0359_artwork_register_status_written.sql:14-24`. Seeding uses only `zoho_writeback_recorded` events. The old `recordCatalogueStatusWritten` returned `unchanged` without an event when the inbound sync had already copied the value.
- **Failure scenario:** after deploy, such rows have `catalogue_status_written = NULL`. Zoho shows "In Auction" (written by LAX), and LAX now wants Available. Because Available is wanted and Zoho shows a non-Available value LAX "never wrote", the result is a **false From Zoho conflict** and no write. This fails safe, but staff see noise and the artwork stays "In Auction" in Zoho.
- **Fix:** also seed from `catalogue_status` where it equals the Status LAX's mapping would give for the row's current place, for the known LAX values (In Auction, Withdrawn). Otherwise, document the expected one-off conflict count and give a bulk "accept" path.

### A-4 [LOW]: when staff set Zoho to LAX's value, the auto-closed Status conflict is recorded as `kept_lax`
- **Where:** `drizzle-artwork-register.repository.ts:564-567`.
- **Scenario:** staff resolve the disagreement *in Zoho* by setting Zoho to the value LAX wants. History says "kept LAX", which is the opposite of what happened.
- **Fix:** use a distinct resolution, for example `agreed` or `zoho_matched`, or record the closing reason in the event payload.

### A-5 [LOW / process]: migration order with B
- A uses 0359 (when 1806048000000) and B uses 0360 (when 1806134400000). Both are idx 348, so the journal conflicts.
- If B deploys first, `migrate-runner.ts:139-147` throws "Migration history is missing … before applied timestamp", and A's deploy fails.
- **Fix:** merge A before B, or have whichever lands second renumber and re-stamp its journal entry.
- Nit: the header of `0359_rollback.sql:1` still says "Rollback for 0352_…".

### A-6 [LOW]: the `stale` check depends on clock skew between Zoho and the worker
- **Where:** `zoho-status-sync.ts:191`. `modifiedAt > observedAt` compares Zoho's clock with the worker's.
- **Scenario:** if Zoho's clock runs ahead of the worker's by a few seconds, a Product LAX itself just touched (for example a listing field write) reads as `stale`. The writeback event then throws retryably until the skew passes. This is harmless but noisy.
- **Fix:** allow a small tolerance (a few seconds), and rely on the re-read just before the write, which is already there.

## B #1285 ic-b-zoho-sold-while-live: FIX FIRST

What is good:
- The copy matches the spec: "Zoho says Sold, but this artwork is still for sale", plus the Reserved variant.
- Nothing is withdrawn automatically.
- Items resolve when Zoho returns to Available or In Auction, or when the listing is withdrawn.
- "It is not sold" needs a trimmed reason of at most 500 characters. It is audited as a `sold_while_live_overridden` event with `staff:<id>` and is gated on `artwork_register.review`.
- Checkout is guarded on a fresh checkout, on an idempotent replay, on the idempotency race and on resume. The 8 Postgres tests cover these.

### B-1 [HIGH, prior finding still true]: LAX's own Reserved write-back for a private sale raises a false "Zoho says Reserved" item and pauses money
- **Where:**
  - `packages/artwork-register-contracts/src/sold-while-live.ts:30-57` (`PLACE_FOR_STATE` includes `private_sale`, and Reserved counts as a situation).
  - `apps/worker/src/integrations/zoho/artwork/writeback-mapping.ts:13` (`private_sale: "Reserved"`).
  - `zoho-artwork-sync-service.ts` `checkSoldWhileLive`, which runs on every product processed live, not only on a change.
- **Failure scenario (reproduced with `SoldWhileLiveMonitor` + `zohoStatusForOffer("private_sale")`):**
  1. Staff start a private sale and the register becomes `private_sale`.
  2. The writeback sends Reserved to Zoho, and `recordCatalogueStatusWritten` (or the inbound copy) sets `catalogueStatus = "Reserved"`.
  3. The next inbound sync of that Product (LAX's own write bumped Modified_Time) calls `reconcile`. `assessSoldWhileLive` returns `{Reserved, private_sale}`, so the item is **raised and isPaused becomes true**.
  4. Staff see a false danger item on every private sale. Any lax.art checkout for that Zoho Product is refused until someone overrides it.
- **Fix:** do not treat Reserved as a situation when it is LAX's own value. Either:
  - (a) for `place === "private_sale"`, only `Sold` counts; or
  - (b) once A lands, ignore the status when `catalogueStatusWritten === catalogueStatus`, which means LAX wrote it.

  Add a test: private_sale with LAX-written Reserved gives no item and no pause.

### B-2 [MEDIUM]: the re-offer Send/Accept guard is not wired, and `bid_reoffer` is never detected
- **Where:**
  - `packages/artwork-register-contracts/src/money-pause.ts:37-39` says "The re-offer API calls this before it sends an offer … and before it accepts one". But no caller of `assertMoneyNotPaused` exists outside shop-api checkout: `git grep assertMoneyNotPaused` finds only `checkout-money-pause.ts`.
  - `apps/worker/.../sold-while-live-monitor.ts:35` calls `assessSoldWhileLive(entry)` without `{ reoffer }`, so the place is never `bid_reoffer`.
- **Failure scenario:** a lot is in the re-offer phase and Zoho says Sold. The item says "in a LAX Bid sale" with "Withdraw the lot" instead of "offered to the next bidder … / Withdraw the offer". When the re-offer Send/Accept endpoints are added, nothing forces them to call the guard. Today the re-offer exists only as domain code (`packages/domain/src/reoffer-*.ts`), with no app endpoint, so the exposure is latent. Still, the spec item "guard re-offer Send/Accept" is not delivered.
- **Fix:**
  - Either wire `assertMoneyNotPaused(..., "reoffer_send" | "reoffer_accept")` into the re-offer service in this PR, or explicitly scope it out: fix the doc comment and open a tracked follow-up.
  - Pass `reoffer: true` from the monitor when the lot's re-offer state is active. That needs a reader for it.

### B-3 [MEDIUM]: a Stripe hosted checkout session opened before the item was raised can still be paid
- **Where:** `apps/shop-api/src/infrastructure/drizzle-checkout.repository.ts`. The guards at :233, :245, :354 and :385 only stop LAX *opening or returning* a session. Nothing expires open sessions when an item is raised, and `drizzle-payment-event.processor.ts:199` completes payment without asking the pause.
- **Failure scenario:**
  1. A buyer starts checkout at 10:00 and LAX creates a Stripe session with `expires_at` equal to the order hold.
  2. At 10:05 staff mark the artwork Sold in Zoho, and the item is raised.
  3. At 10:10 the buyer pays on the still-open Stripe page. The webhook marks the order paid, and **money is taken for an artwork Zoho says is sold**.
  4. Delivery-quote holds (`holdUntil`) can make this window long.
- **Fix:** when an item is raised, expire open hosted sessions for pending orders that hold that artwork's `zoho_product_id` (`shop-checkout-stripe-expiry.ts` already exists). This can be done through an outbox event that shop-api consumes. As a backstop, check the pause in the payment-completed processor and route paid-while-paused orders to refund or review. Add an integration test: open a session, raise the item, the session is expired.

### B-4 [LOW]: wrong resolution label when the artwork is sold in LAX
- **Where:** `sold-while-live.ts:166-170`.
- **Scenario:** Zoho says Sold, and the artwork then sells on lax.art (state `sold`). The situation becomes null while Zoho still says Sold, so the resolution is recorded as `"withdrawn"`. History says it was withdrawn when it sold.
- **Fix:** add a `no_longer_for_sale` or `sold` resolution, chosen from `entry.offer.state` (this needs a migration CHECK update).

### B-5 [LOW]: replace is not atomic, and `findLive` is unordered
- **Where:** `sold-while-live-monitor.ts:48-50` and `drizzle-sold-attention.store.ts:29-36`.
- **Scenario:**
  - When Sold changes to Reserved, `resolve` and `raise` run in separate transactions. For that moment nothing is open, so `isPaused` is false and a checkout can slip through.
  - `findLive` uses `limit 1` with no order. The unique index allows one live item per status, so after a race both a Sold item and a Reserved item can be live, and the monitor picks one at random.
- **Fix:** add a `replace` method on the store that resolves and inserts in one transaction, and order `findLive` by `raised_at desc`.

### B-6 [LOW]: the sweep never reaches past the first 500 live items
- **Where:** `sold-while-live-monitor.ts:54-60` and `drizzle-sold-attention.store.ts:155`. The sweep takes `listLiveRegisterIds(500)` ordered by `raised_at` with no cursor.
- **Scenario:** if more than 500 items are open or overridden (for example a bulk Zoho edit) and the oldest stay live, items after 500 are never auto-resolved by the nightly sweep. They resolve only when that Zoho Product itself changes.
- **Fix:** page with a cursor (`raised_at`, `id`).

## C #1286 ic-c-atg-sold-register: SHIP

What is good:
- A lot ATG reports sold is moved to `sold` through `ArtworkOfferLock.markSold`, which is a versioned write. This covers a lot still in `bid_sale` and a late result after the lot-ended path withdrew the artwork.
- An artwork offered elsewhere (lax.art, private sale, another lot) or already sold elsewhere is skipped. Staff get an offer-state conflict and the register is not overwritten.
- Repeats are idempotent. The projector maps "ended + no LAX winner + soldOnAtg" to sold.
- `ReturnLotToLaxArt` treats an ATG sale like a winner.
- `soldOnAtg` is exposed on `LotRegisterLink` and as `IAtgLotSoldReader`.
- All touched Postgres tests pass.

### C-1 [LOW]: the ATG conflict is suppressed while any other offer-state conflict is open, and can be lost after the 7-day poll window
- **Where:** `packages/persistence/.../drizzle-artwork-register.repository.ts:458-499`. The dedupe in `recordOfferConflict` matches *any* open `offerState` conflict, and `atg-sync-service.ts:47` only polls sales that closed in the last 7 days.
- **Scenario:**
  1. An unrelated offer-state conflict is open on the artwork.
  2. ATG reports the lot sold, but the artwork is now on lax.art, so no item is raised because one is already open.
  3. Staff resolve the other item 8 days later. The sale is no longer polled, so **the "Sold on ATG but now listed on lax.art" item is never raised**, and the artwork stays for sale on lax.art.
- **Fix:** when an open offer-state conflict exists, update its message or `lax_value` to include the ATG sale, or keep a pending marker. Alternatively, keep polling sales that have unrecorded ATG-sold lots beyond 7 days.

### C-2 [LOW]: a late result makes two register moves (withdrawn → bid_sale → sold)
- **Where:** `packages/artwork-register-contracts/src/offer-lock.ts:236-240`.
- **Scenario:** a late ATG result after withdrawal writes `offer_moved` to `bid_sale`, then to `sold`. Writeback and listing events may briefly send "In Auction" to Zoho before "Sold". With A this is a valid LAX-written value, so it is harmless but noisy. With B, a Zoho Sold catalogue status in that instant could raise a sold-while-live item.
- **Fix:** allow a direct withdrawn → sold move when the ref is the lot the artwork was withdrawn from, which gives one event.

### C-3 [LOW]: the `IAtgLotSoldReader` / `soldOnAtg` fact for re-offer eligibility has no consumer yet
- **Where:** `drizzle-lot-register-link.reader.ts:34`. `packages/domain/src/reoffer-eligibility.ts` already takes `soldOnAtg`, but no app code builds those facts, because no re-offer endpoint exists.
- **Fix:** none needed for this PR. When the re-offer service lands, feed `soldOnAtg` from this reader and add a test that an ATG-sold lot is blocked with `sold_on_atg`.

### C-4 [LOW]: an ATG offer conflict is stored with a LAX message as its "Zoho value"
- **Where:** `drizzle-artwork-register.repository.ts:488` (`zohoValue: input.message`, `zohoModifiedAt: now`).
- **Scenario:** in the "From Zoho" list, the item reads as if Zoho said "Sold on ATG but now listed on lax.art". The "Zoho modified" time is the poll time.
- **Fix:** add a source or kind to the conflict (or a separate field), and make sure the admin view model labels it "From ATG".

### C-5 [LOW, note]: a later ATG correction to unsold is not handled
- If ATG later reports the lot unsold (for example a buyer default on ATG), the register stays `sold`, and nothing tells staff.
- Consider raising a staff item when `sold` changes from true to false on a lot whose register entry is sold through that lot.
